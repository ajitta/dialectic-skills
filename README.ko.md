# Dialectic Skills (`dia`)

[English](README.md) | **한국어** | [日本語](README.ja.md) | [简体中文](README.zh-CN.md)

웹사이트: [ajitta.github.io/dialectic-skills](https://ajitta.github.io/dialectic-skills/)

추론과 검토를 위한 스킬 열두 개를 하나의 플러그인에 담았습니다. Agent Skills를 불러오는 모든 어시스턴트, 즉 Claude(웹, 데스크톱, 모바일, Claude Code), Codex, ChatGPT에서 수정 없이 실행되도록 작성했습니다. 패키지는 지침(Markdown, YAML, JSON)으로만 이루어져 있으므로 도구가 없는 채팅에서도 모든 스킬이 작동합니다. 스킬 파일은 영어로 작성되어 있으며, 각 스킬은 사용자가 쓴 메시지의 언어로 답합니다. 휴대폰에서는 `dia`만 입력하면 됩니다. 메뉴 스킬(`dia-menu`, 1.4.0에서 추가)이 스킬 목록을 보여 주고, 번호나 이름의 앞 글자, 또는 요청 내용으로 스킬 하나를 골라 시작합니다.

| 스킬 | 하는 일 | 시작 방식 |
|---|---|---|
| `dia-confirm` | 작업을 시작하기 전에 목표를 다시 정리하고, 중요한 가정을 밝히고, 사용자가 내려야 할 결정만 나열한 뒤 승인을 기다립니다. | 이름으로만 |
| `dia-elenchus` | 플라톤의 엘렝코스(논박술): "X란 무엇인가?"를 묻고, 한 번에 한 질문씩 전제에 합의하며, 모순을 드러냅니다. 수정할 때마다 그것이 사용자의 새로운 생각이 됩니다. 대개 아포리아로 끝나며, 조언은 하지 않습니다. | 이름으로, 또는 소크라테스식 대화를 요청해서 |
| `dia-brainstorm` | 현대적인 소크라테스식 질문을 한 번에 하나씩 던진 뒤, 사용자의 선택지와 표시를 붙인 최대 세 개의 제안, 기준에 따른 수렴, 결론, 요약서를 제시합니다. 구현은 하지 않습니다. | 이름으로, 또는 소크라테스식 브레인스토밍을 요청해서 |
| `dia-reductio` | 엄격한 귀류법을 한 번에 수행합니다: 표시를 붙인 전제, 줄마다 규칙을 밝힌 Q와 not-Q 도출, 등급을 매긴 강도, 선택지와 기록. | 이름으로, 또는 말로 요청해서 |
| `dia-negative` | 내부 비판(아도르노의 내재적 비판보다 좁은 의미)을 한 번에 수행합니다: 대상 자신의 기준, 사례와 "빠져나가는 것"을 갖춘 엄격한 간극, 반증 조건을 붙인 실제 작동 목적, 억지 종합 없는 선택지. | 이름으로, 또는 말로 요청해서 |
| `dia-warrant` | 툴민의 논증 구조와 월턴의 비판적 질문을 한 번에 적용합니다: 자료, 논거(드러나지 않은 논거는 보충하고 표시), 뒷받침, 한정어, 반박 조건을 정리하고, 질문마다 어느 부분을 시험하는지 표시한 뒤 가장 약한 고리를 짚습니다. 주장이 참인지는 판정하지 않습니다. | 이름으로, 또는 말로 요청해서 |
| `dia-conjecture` | 라카토슈의 증명과 반박을, 사용자가 내세운 "모든 / 언제나 / 절대" 주장에 대화로 적용합니다: 사용자의 논증을 단계로 나누고, 메시지마다 반례 하나를 검토 과정과 함께 내놓으며, 사례마다 사용자가 판정하고 수선 방법을 고릅니다. | 이름으로, 또는 말로 요청해서 |
| `dia-counterplan` | 메이슨의 변증법적 탐구를 계획이나 결정에 적용합니다: 핵심 가정, 가정마다 그럴듯한 반대 가정, 같은 사실 위에 세운 대안 계획을 제시한 뒤, 이제 어느 가정을 받아들이는지 사용자가 답합니다. 승자는 정하지 않습니다. | 이름으로, 또는 말로 요청해서 |
| `dia-refine` | 직전 답변이나 초안을 한 차례 검토합니다: 사실 오류, 논리적 비약, 누락된 요구 사항, 반복. 확인된 결함만 고칩니다. | 첫 단어를 `dia-refine`로, 또는 이름으로 |
| `dia-ratchet` | 검토 라운드를 반복하되, 외부 근거(검색, 도구 실행, 사용자가 준 자료)만 인정하고 어시스턴트 자신의 재도출은 인정하지 않습니다. 확인을 통과한 항목은 고정합니다. 퇴행, 결함 0건, 검증 수단 소진, 고정점 도달, `--max N`(기본값 3) 중 하나에 이르면 멈춥니다. 1.5.0 이전 이름은 `dia-iterate`입니다. | 첫 단어를 `dia-ratchet`으로, 또는 이름으로만 |
| `dia-adjudicate` | 사람이나 다른 어시스턴트가 어떤 글에 대해 쓴 보고서(비판, 리뷰, 검증 보고서)를 판정합니다. 글의 주장과 보고서의 모든 지적을 출처와 대조해 항목마다 판정을 내리고, 사람이 다시 확인해야 할 판정을 목록으로 줍니다. 글을 고쳐 쓰지는 않습니다. | 첫 단어를 `dia-adjudicate`로, 또는 이름으로만 |
| `dia-instruct` | 모델이 읽고 따를 글(스킬 파일, 에이전트 프롬프트, 에이전트 지침 파일)을 네 가지 규칙으로 점검하거나 씁니다: 조건과 대안을 품은 하나의 식인 문단, 뜻한 만큼만 좁은 범위 단어, 저마다 이유가 붙은 더 적은 지시, 한 대상에 한 이름. 검토만 요청하면 위반 사항을 나열하고, 사용자가 고를 때까지 아무것도 바꾸지 않습니다. | 이름으로, 또는 말로 요청해서 |
| `dia-menu` | 방법이 아니라 짧은 진입점입니다. `dia`는 번호가 붙은 메뉴를 보여 주고, `dia 4 …`나 `dia red …`는 번호나 앞 글자로 스킬을 시작하며, `dia <request>`는 알맞은 스킬을 골라 어떤 스킬인지 밝힙니다. `dia-confirm`, `dia-ratchet`, `dia-adjudicate`는 스스로 시작하지 않습니다. | 첫 단어를 `dia`로 |

```

```

```

```

claude.ai(웹): Customize › Plugins › Add › Add marketplace에 `ajitta/dialectic-skills`를 입력한 뒤, Discover › `dia` › Add를 선택합니다. 웹과 모바일 앱에서 쓸 수 있습니다. 자세한 단계는 아래에 있습니다.

그런 다음 이렇게 입력해 봅니다: `이 주장에 귀류법을 적용해 주세요: 재택근무는 언제나 생산성을 높인다.`

## 설치

**어디서 설치하느냐에 따라 dia가 보이는 곳이 달라집니다.** 웹(claude.ai, chatgpt.com)에서 설치하면 계정에 저장되어 웹과 모바일 앱에 나타납니다. 데스크톱 앱(Claude 데스크톱, ChatGPT 데스크톱 앱의 Codex)에서 설치하면 그 컴퓨터에만 남습니다. 모든 곳에서 쓰려면 웹에서 한 번, 그리고 쓰는 데스크톱 앱마다 한 번씩 설치하세요. 저장소 소유자도 이렇게 쓰고 있습니다.

### claude.ai 웹과 Claude 데스크톱

1. Settings › Capabilities에서 **Code execution and file creation**을 켭니다. dia 스킬은 코드를 실행하지 않지만, 스킬 기능 자체에 이 설정이 필요합니다.
2. **마켓플레이스 추가.** Customize › Plugins › Add › Add marketplace를 열고 다음을 입력합니다.

   ```
   ajitta/dialectic-skills
   ```

   Git URL `https://github.com/ajitta/dialectic-skills.git`을 넣어도 되고, Claude 데스크톱에서는 로컬 폴더(이 저장소를 클론한 폴더)도 지정할 수 있습니다. 직접 타이핑하지 말고 복사해서 붙여 넣으십시오. `dialectric`처럼 철자가 틀리면 "Repository not found"로 실패합니다.
3. **플러그인 추가.** 마켓플레이스를 추가한 것만으로는 아직 아무것도 설치되지 않습니다. Customize › Plugins에서 Discover를 열고 `dia`(Dialectic Skills)를 선택한 뒤 Add를 누릅니다.
4. **확인.** 메시지 입력창에 `/dia`를 입력합니다. `dia:dia-adjudicate`부터 `dia:dia-warrant`까지 열세 개 항목(스킬 열두 개와 `dia:dia-menu`)이 나타나야 합니다. 업데이트는 마켓플레이스를 통해 받습니다(Check for updates 또는 Sync automatically).

2·3단계 대신 플러그인을 업로드할 수도 있습니다. Customize › Plugins › Add › Upload plugin에서 최신 릴리스의 [`dialectic-skills.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills.zip)을 올립니다. Customize › Skills가 아니라 Customize › Plugins를 사용해야 합니다. Skills 화면은 플러그인 매니페스트가 들어 있는 zip을 거부합니다. 업로드한 플러그인은 스스로 업데이트되지 않으므로, 새 릴리스가 나올 때마다 다시 업로드해야 합니다.

**Claude 데스크톱:** 같은 Customize › Plugins 화면이지만 그 컴퓨터에만 설치됩니다. 저장소 소유자가 확인한 바로는, Claude 데스크톱에서 추가한 플러그인은 모바일 앱에 나타나지 않았고, claude.ai에서 추가한 플러그인은 Claude 데스크톱에 나타나지 않았습니다. 둘 다 쓴다면 양쪽에 각각 설치하세요.

### Claude 모바일 (iOS, Android)

따로 설치할 필요가 없습니다. claude.ai(웹)에서 추가한 플러그인은 계정에 저장되어 모바일 앱에 자동으로 나타납니다. Claude 데스크톱에서 추가한 것은 나타나지 않습니다. 모바일의 `/` 메뉴에는 플러그인 스킬이 표시되지 않습니다. 가장 짧은 방법은 메시지를 `dia`로 시작하는 것입니다(호출 방법 참고). 이름을 끝까지 입력해도 됩니다. 예: `/dia-brainstorm`, 또는 `dia-brainstorm`으로 시작하는 메시지. 말로 요청해도 됩니다.

### Claude Code

```
/plugin marketplace add ajitta/dialectic-skills
/plugin install dia@dialectic-skills
```

- 업데이트: `/plugin marketplace update dialectic-skills`를 실행한 뒤 플러그인을 업데이트합니다(또는 해당 마켓플레이스의 자동 업데이트를 켭니다).
- 제거: `/plugin uninstall dia@dialectic-skills`.
- claude.ai에서 추가한 플러그인은 같은 계정으로 로그인하면 Claude Code에도 동기화됩니다. 명령줄에서 다시 설치하지 마십시오.
- 카탈로그를 통해 설치하려면: `/plugin marketplace add ajitta/claude-plugins`를 실행한 뒤 `/plugin install dia@ajitta`를 실행합니다. 코드는 같고 설치 이름만 다릅니다.

### Codex CLI와 IDE

```
codex plugin marketplace add ajitta/dialectic-skills
codex plugin add dia@dialectic-skills
```

- 업데이트: `codex plugin marketplace upgrade`로 마켓플레이스를 갱신하고, `codex plugin list`로 설치된 버전을 확인합니다.
- 플러그인 없이 쓰려면: `skills/dia-<x>/` 폴더를 `~/.agents/skills/`에 복사합니다. 이렇게 복사한 스킬의 이름은 `$dia:dia-<x>`가 아니라 `$dia-<x>`입니다.

### ChatGPT 데스크톱(Codex 포함)과 모바일

방법은 두 가지입니다. 웹과 모바일에는 첫 번째를, 데스크톱 앱에는 두 번째를 쓰세요. 저장소 소유자는 둘 다 씁니다.

1. **웹에서 zip 업로드(웹과 모바일):** 최신 릴리스에서 [`dialectic-skills-openai.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills-openai.zip)을 내려받아 chatgpt.com의 플러그인 zip 업로드로 올립니다. 플러그인이 계정에 저장되므로 ChatGPT 웹과 모바일에 나타납니다. 이 zip에는 ChatGPT용 목록 정보(설명, 시작 프롬프트, 로고)가 들어 있습니다. 업로드한 플러그인은 스스로 업데이트되지 않으므로, 새 릴리스가 나올 때마다 다시 올려야 합니다.
2. **데스크톱 앱에서 마켓플레이스 추가(이 컴퓨터에서만):** Codex는 ChatGPT 데스크톱 앱에 포함되어 있습니다. GitHub 저장소(`ajitta/dialectic-skills`), Git URL(`https://github.com/ajitta/dialectic-skills.git`), 로컬 폴더(이 저장소를 클론한 폴더) 중 하나로 마켓플레이스를 추가하고, 그 플러그인 목록에서 `dia`를 선택해 설치합니다. 데스크톱 앱의 로컬 Codex 폴더에 설치될 뿐 계정에 저장되지 않으므로, 모바일과 웹에는 나타나지 않습니다. 업데이트는 마켓플레이스를 통해 받습니다.

Business와 Enterprise 워크스페이스에서는 관리자가 워크스페이스 전체에 플러그인을 추가할 수도 있습니다(zip 업로드 또는 GitHub 마켓플레이스 가져오기).

### Windows

위의 모든 경로는 Windows에서도 작동합니다. 스킬에는 스크립트가 없으므로 Python이나 셸 설정이 필요하지 않습니다.

## 호출 방법

방법은 네 가지이며, 모든 환경에서 적어도 한 가지는 지원합니다.

1. **메뉴: 메시지를 `dia`로 시작하기.** `dia`만 입력하면 번호가 붙은 스킬 목록이 나옵니다. `dia 4 <your text>`나 `dia red <your text>`는 그 스킬(여기서는 `dia-reductio`)을 시작합니다. 앞 글자가 두 스킬에 해당하면(`con`) 어느 쪽인지 묻습니다. `dia <your text>`는 알맞은 스킬을 골라 대개 먼저 한 줄로 이름을 밝히고 실행합니다. 두 스킬이 비슷하게 맞으면 묻습니다. 일반 요청으로는 `dia-confirm`(1), `dia-ratchet`(10), `dia-adjudicate`(11)를 절대 시작하지 않으므로, 번호나 이름을 쓰십시오. 예: `dia 10 --max 2 <draft>`. 휴대폰에서 가장 빠른 방법입니다. 세 글자에 하이픈도 없습니다.
2. **말로 요청하기.** 방법을 직접 요청합니다: "…에 귀류법을 적용해 주세요", "…을 내재적 비판해 주세요", "소크라테스식 대화로 부탁합니다…", "이 근거가 결론을 얼마나 뒷받침하나요?", "내 규칙의 반례를 찾아 주세요…", "이 계획에 반대 입장을 맡아 주세요…", "에이전트에게 줄 이 프롬프트를 검토해 주세요…". 모든 환경에서 작동하며, 모바일에서는 이 방법이 가장 안전한 기본값입니다. `dia-reductio`, `dia-negative`, `dia-elenchus`, `dia-brainstorm`, `dia-warrant`, `dia-conjecture`, `dia-counterplan`, `dia-instruct`에 쓸 수 있습니다.
3. **메시지에 이름 적기.** 메시지를 스킬 이름으로 시작합니다: `dia-confirm …`, `dia-refine …`, `dia-ratchet …`, `dia-adjudicate …`. 1.2.0부터는 Codex에서 `$` 없이, ChatGPT에서 `@` 없이(모바일 앱에서 소유자 확인) 이렇게 시작할 수 있습니다. `dia-refine`, `dia-ratchet`, `dia-adjudicate`는 이 방식이나 명시적 선택으로 시작하도록 설계되었습니다. `dia-ratchet`과 `dia-adjudicate`는 일반 요청으로는 절대 시작되지 않으며, Claude Code에서는 "이 초안 고쳐 주세요" 같은 일반 요청으로 `dia-refine`이 로드되는 경우가 드뭅니다.
4. **명시적 선택.** 환경마다 표기법이 다릅니다.

| 환경 | 문법 | 예시 |
|---|---|---|
| claude.ai, Claude 데스크톱, Claude Code | `/dia:dia-<x>` | `/dia:dia-reductio` |
| Claude 모바일 | `/dia-<x>` 또는 `/dia:dia-<x>`를 끝까지 입력(`/` 메뉴에는 표시되지 않음) | `/dia-brainstorm`, `/dia:dia-brainstorm` |
| Codex (플러그인) | `$dia:dia-<x>` 뒤에 공백 | `$dia:dia-confirm 백업 스크립트 작성해줘` |
| Codex (복사한 폴더) | `$dia-<x>` | `$dia-refine` |
| ChatGPT | `@` 입력 후 스킬 선택 | `@dia-negative` |

1.2.0부터 Codex와 ChatGPT에서도 Claude처럼 모든 스킬이 모델에 보입니다. `dia-reductio`, `dia-negative`, `dia-elenchus`, `dia-brainstorm`, `dia-warrant`, `dia-conjecture`, `dia-counterplan`, `dia-refine`, `dia-instruct`은 요청 내용이 맞으면 저절로 시작될 수 있고, `dia-confirm`, `dia-ratchet`, `dia-adjudicate`는 메시지를 이름으로 시작하거나 직접 선택(`$dia:dia-<x>`, `@`)할 때만 시작하도록 되어 있습니다. 다만 Codex에서는 "먼저 내 목표를 정리하고 결정할 것들을 알려줘"처럼 `dia-confirm`의 절차를 그대로 말로 요청하면 이 스킬이 로드되기도 합니다.

### 옵션

옵션은 플래그로 쓰거나 일반 문장으로 쓸 수 있으며, 언어는 상관없습니다.

- `--target=user|claude|text|all` (`dia-reductio`, `dia-negative`, `dia-warrant`): 검토 대상을 정합니다. `user`는 사용자가 제시한 주장, `claude`는 어시스턴트 자신의 이전 답변(어떤 어시스턴트든 해당), `text`는 붙여 넣은 텍스트, `all`은 이 중 존재하는 모든 것입니다. 플래그가 없으면 스킬이 대상을 추론하고 첫 줄에 밝힙니다.
- `--target=user|claude|text` (`dia-counterplan`): 누구의 계획을 검토할지 정합니다. `claude`는 어시스턴트 자신의 이전 추천을 직접 가리킬 때만 씁니다.
- `--mode=audit|ask` (`dia-warrant`): `audit`(기본값)은 점검 전체를 한 번에 보여 주고, `ask`는 사용자가 각 부분을 직접 채우도록 한 번에 한 질문씩 묻습니다.
- `--max N` (`dia-ratchet`): 라운드 상한이며, 기본값은 3입니다.
- 모드와 깊이 (`dia-brainstorm`): `develop`(기본값) 또는 `stress`("허점을 찔러 주세요"), 그리고 `quick`, `standard`(기본값), `deep`.
- 기준 (`dia-refine`, `dia-ratchet`): 이름 뒤에 오는 모든 내용이 기준이 됩니다. 예: `dia-refine — 숫자 확인해줘` 또는 `dia-refine 어조 위주로`.

## 스킬 안내와 예시

이 스킬들을 쓰는 데 철학 지식은 전혀 필요 없습니다. 각 스킬은 사람들이 오래전부터 써 온 생각하는 방법 하나를, 어시스턴트가 한 단계씩 따라가는 절차로 옮겨 놓은 것입니다. 아래에서는 스킬마다 쉬운 말로 된 설명, 직접 해 볼 프롬프트, 그리고 실제 세션을 줄여서 보여 드립니다.

세션은 이 플러그인을 설치한 Claude Code(Sonnet)에서 실행했고, 대화 예시에 나오는 사용자 답변은 미리 써 둔 대본이 아니라 시뮬레이션한 사용자가 그때그때 답한 것입니다. 아래 대화는 영어로 실행한 것을 번역해 실었습니다. 실행할 때마다 표현은 조금씩 달라집니다. 모든 프롬프트는 어떤 언어로 써도 작동하며, 어시스턴트는 사용자가 쓴 언어로 답합니다.

**하고 싶은 일로 스킬 고르기**

| 이런 걸 하고 싶다면… | 쓸 스킬 |
|---|---|
| 일을 시작하기 전에 어시스턴트가 과제를 제대로 이해했는지 확인하기 | `dia-confirm` |
| 어떤 단어나 생각으로 내가 정말 무엇을 뜻하는지 알아내기 | `dia-elenchus` |
| 막연한 아이디어를 선택지와 계획으로 바꾸기 | `dia-brainstorm` |
| 어떤 주장이 앞뒤가 맞는지 확인하기 | `dia-reductio` |
| 구호, 정책, 약속이 스스로 한 말을 지키는지 보기 | `dia-negative` |
| 결론을 받치는 이유가 실제로 얼마나 튼튼한지 보기 | `dia-warrant` |
| 내가 믿는 "언제나", "절대" 규칙을 반례로 시험하기 | `dia-conjecture` |
| 결정하기 전에 다른 계획을 가장 강하게 옹호하는 주장 들어 보기 | `dia-counterplan` |
| 답변이나 초안의 실수를 한 번 바로잡기 | `dia-refine` |
| 라운드를 거듭하며 꼼꼼하게 사실 확인하기 | `dia-ratchet` |
| 한 글에 대한 여러 리뷰 가운데 어떤 지적이 맞는지 가리기 | `dia-adjudicate` |
| 모델이 뜻한 대로 따르도록 프롬프트, 스킬, 에이전트 파일을 쓰거나 점검하기 | `dia-instruct` |
| 어떤 스킬을 쓸지 모르겠을 때, 또는 휴대폰으로 입력할 때 | `dia` (`dia-menu`) |

### dia-confirm: 일을 시작하기 전에 과제 합의하기

**쉽게 말하면.** 좋은 시공업자는 공사를 시작하기 전에 일을 함께 짚어 봅니다. 이런 걸 만들겠다, 이런 걸 가정하고 있다, 이건 고객님만 정할 수 있다고요. `dia-confirm`은 어시스턴트가 바로 그렇게 하도록 만들고, 짐작으로 진행하는 대신 사용자가 승인할 때까지 기다리게 합니다.

**이럴 때 쓰세요.** 요청은 짧은데 결과가 사용자만 아는 내용에 달려 있을 때입니다. 축사, 계획, 스크립트, 중요한 사람에게 보내는 이메일 같은 경우입니다. 답이 하나로 뻔한 간단한 질문이라면 **쓰지 않아도 됩니다**.

**해 보기:**

```
dia-confirm 동생 결혼식에서 할 짧은 축사를 써 주세요.
```

**세션은 이렇게 진행됩니다** (줄임):

> **어시스턴트:**
> **목표와 성공 조건:** 동생분에 관한 짧은 결혼식 축사로, 바로 소리 내어 읽을 수 있고, 1–2분 정도 분량에, 따뜻한 분위기로, 건배사를 포함합니다.
> **근거와 가정:** 동생분이나 두 분에 대해 알 수 있는 정보가 없습니다. 동생분이 신랑이고, 가벼운 유머가 섞인 따뜻한 어조이며, 영어로 쓴다고 가정했습니다.
> **사용자가 내려야 할 결정:** 1. 이름, 2. 함께한 추억 같은 실제 이야기 한두 가지, 3. 어조, 4. 피해야 할 내용. 이 정보가 없으면 빈칸을 남긴 일반적인 축사를 쓸 수밖에 없습니다.
> **확인:** 답변과 함께 "진행"이라고 보내 주시거나, 일반 템플릿으로 써 달라고 말씀해 주세요.
>
> **나:** 동생 이름은 민호이고, 사라와 결혼해요. 저는 베스트맨을 맡았어요. 민호가 저보다 어린데도 저한테 자전거 타는 법을 가르쳐 줬어요. 따뜻하게, 가벼운 농담 하나 넣어서, 3분 정도로요. 진행
>
> **어시스턴트:** 약 400단어 분량의 축사입니다… *(자전거 이야기를 중심으로 한 축사가 이어집니다)* …참고: 이야기의 작은 세부는 제가 지어냈습니다. 실제와 다른 부분은 고쳐 주세요.

**팁**

- 신경 쓰이는 질문에만 답하고 "진행"을 덧붙이면 됩니다. 수정 사항과 "진행"을 함께 보내면 수정된 과제를 승인한 것으로 봅니다.
- "좋아 보여요", 아무 답 없음, 엄지 이모지는 승인으로 치지 않습니다. 어시스턴트는 계속 기다립니다.
- 적용 범위는 그 과제 하나와 직접 이어지는 후속 작업입니다. 새 과제에서도 같은 확인을 받고 싶다면 다시 `dia-confirm`으로 시작하세요.

### dia-elenchus: 내가 정말 무엇을 뜻하는지 알아내기

**쉽게 말하면.** 플라톤의 대화편에서 소크라테스가 쓰는 방법입니다. 사용자가 어떤 것이 무엇이라고 생각하는지 말합니다("좋은 교사란…"). 어시스턴트는 반박하거나 자기 의견을 내놓지 않습니다. 대신 구체적인 사례를 하나씩 묻는데, 그 사례들은 사용자의 대답이 스스로 내린 정의와 조금씩 어긋나도록 골라져 있습니다. 그러면 사용자는 자기 말로 정의를 고칩니다. 결국 막다른 곳에 이르는 경우가 많은데, 이 상태를 그리스어로 **아포리아**라고 합니다. 여기서 막히는 것은 실패가 아니라 하나의 결과입니다. 이제 어느 부분을 모르는지 정확히 알게 되었으니, 잘못된 가정 위에 무언가를 쌓아 올리지 않게 됩니다.

**이럴 때 쓰세요.** 뜻이 뻔해 보이지만 실제 결정을 좌우하는 단어에 기대고 있을 때입니다. 좋은 교사, 공정한 분배, 성공한 프로젝트, 건강한 관계 같은 것들입니다. 조언을 얻는 용도로는 **맞지 않습니다**. 대화하는 동안에는 조언을 전혀 하지 않습니다.

**해 보기:**

```
소크라테스식 대화를 부탁합니다. 저는 좋은 교사란 학생들이 시험에서 높은 점수를 받게 하는 교사라고 생각합니다.
```

**세션은 이렇게 진행됩니다** (실제 실행, 줄임):

> **어시스턴트:** 저는 무엇이 좋은 교사를 만드는지 모르니, 말씀하신 정의를 시험해 보겠습니다. 어떤 교사가 시험 전날 학생들에게 시험 문제와 답을 나눠 주어서 모두 높은 점수를 받았다고 해 봅시다. 그 사람은 좋은 교사입니까?
>
> **나:** 아니요, 그건 사실상 부정행위죠. 좋은 교사란 학생들이 *실제로 내용을 배워서* 높은 점수를 받게 하는 교사일지도 모르겠네요.
>
> **어시스턴트:** 표현이 "시험에서 높은 점수"에서 "실제로 내용을 배워서 받은 높은 점수"로 바뀌었습니다. 이번에는 학생들이 정말로 배웠는데 시험이 잘못 만들어져서 점수가 낮게 나온 교사를 생각해 봅시다. 그 사람은 좋은 교사입니까?
>
> **나:** 네, 시험이 잘못된 건 시험 탓이니까요. 그러면 좋은 교사를 만드는 건 사실 점수가 아니네요.
>
> **어시스턴트:** … 모든 학생이 모든 것을 배웠지만, 전부 책과 개인 과외 교사로 혼자 배운 반을 생각해 봅시다. 담당 교사는 아무것도 기여하지 않았습니다. 그 사람은 좋은 교사입니까?
>
> **나:** 아니요. 그러면 좋은 교사란 자기 가르침이 실제로 학생들의 배움을 돕는 교사네요.
>
> *…사례가 세 개 더 이어집니다. 학생들이 수업을 빼먹는 교사, 똑같이 명료하게 가르치지만 반이 다른 두 교사, 온갖 방법을 써 봤지만 아무것도 통하지 않은 교사…*
>
> **어시스턴트:** 앞에서 학생들이 수업을 빼먹는 교사도 여전히 좋은 교사라고 하셨습니다. 그 학생들은 "무리 없이 참여할 수 있는" 상태였습니까?
>
> **나:** 참여할 수 있었는데 안 하기로 한 거죠. 그러니 제 새 생각대로라면 그 교사는 좋은 교사가 아니에요. 아까 한 말과 모순되네요. 막혔어요. 그럼 저는 어디에 서 있는 거죠?
>
> **어시스턴트:** 아포리아에 이르셨습니다. 이건 실패가 아니라 하나의 결과입니다. 좋은 교사를 학생들이 결국 배운 것으로 정의할지, 교사가 하는 일로 정의할지가 아직 열려 있습니다… *(이어서 기록이 나옵니다. 정의가 어떻게 바뀌었는지, 동의한 전제들, 이제 모른다는 것을 알게 된 것, 가져갈 질문 하나. 결과: 아포리아)*

**팁**

- 짧고 솔직한 대답이 가장 좋습니다. "잘 모르겠어요"도 훌륭한 대답입니다.
- 어시스턴트가 표현이 "바뀌었다"고 짚는 것은 말이 어떻게 달라졌는지 보여 줄 뿐입니다. 무엇을 남길지는 사용자가 정합니다.
- 언제든 "그만"이라고 하면 기록을 받습니다. 그다음 제안을 원하면 요청하세요. 어시스턴트는 소크라테스식 부분이 끝났다고 밝히고, 자기 아이디어에는 자기 것이라고 표시합니다.

### dia-brainstorm: 막연한 아이디어를 키운 뒤 결정하기

**쉽게 말하면.** 선택지를 건네기 전에 좋은 질문부터 던지는 코치입니다. 먼저 한 번에 하나씩 질문해서 사용자가 원하는 것과 아는 것을 분명히 합니다(소크라테스식 질문). 그다음 사용자가 선택지를 내놓고, 어시스턴트가 몇 가지를 보태고, 사용자가 무엇이 중요한지 고르면, 결론과 바로 실행에 옮길 수 있는 짧은 요약서로 마무리합니다. `dia-elenchus`와 달리, 질문을 마친 뒤에는 제안도 합니다.

**이럴 때 쓰세요.** 목표는 있는데 아직 계획이 없을 때입니다. 부업, 진로 변경, 작은 프로젝트, 여행 같은 경우입니다. 실제로 무언가를 만드는 용도로는 **맞지 않습니다**. 코드를 쓰거나 행동에 옮기는 일은 하지 않습니다.

**해 보기:**

```
저와 소크라테스식 브레인스토밍을 해 주세요. 짧게 진행해 주세요: 주말에 부수입을 좀 벌고 싶습니다.
```

**세션은 이렇게 진행됩니다** (실제 실행, 줄임):

> **어시스턴트:** 짧게 진행하는 모드이고, 질문은 4개 정도입니다. 지금 하시는 일과 별개로 주말에 부수입을 좀 벌고 싶다는 생각이시죠. 맞습니까, 아니면 제가 의도하지 않은 걸 가정했나요?
>
> **나:** 맞아요. 주말마다 8시간 정도, 한 달에 대략 $300, 시작 비용은 $200 이하로요.
>
> **어시스턴트:** 주말 8시간이면 한 달에 약 32시간이니, $300는 시간당 약 $9입니다. 이미 할 줄 아는 것 중에 누군가 실제로 돈을 낼 만한 것이 무엇입니까?
>
> **나:** 사진을 잘 찍고 괜찮은 카메라도 있어요. 동네 작은 가게들 사진을 찍어 주면 어떨까 싶어요.
>
> **어시스턴트:** 칭찬을 들었다는 건 좋은 신호지만 아직 돈을 낸 사람은 없으니, 가장 큰 미지수는 가게가 정말… 앞으로 몇 주말 동안 가게들을 찾아간다고 해 봅시다. 무엇을 보면 이게 안 된다고 판단하시겠습니까?
>
> **나:** 세 주말 동안 가게 10곳 정도에 제안했는데 저렴한 시범 촬영조차 승낙하는 곳이 하나도 없으면, 안 되는 걸로 보겠어요.
>
> *…사용자가 선택지를 더 내놓고(주말 장터에서 사진 인화본 판매, 스톡 사진, 프로필 사진, '반려동물 사진 찍는 아침'), 어시스턴트가 자기 선택지를 보태고(결혼식 보조 촬영, 초보자 사진 산책 모임, 아무것도 하지 않기), 사용자가 기준 세 가지를 고릅니다. 시작 비용이 낮을 것, 무급 보정 작업이 많지 않으면서 약 $300를 벌 것, 일이 즐거울 것…*
>
> **어시스턴트:** **결론: 열려 있음.** 제가 시험해 본 부분에서는 아이디어가 버텼지만, 핵심 가정, 즉 누군가 이 사진에 돈을 낼 것이라는 가정은 아직 시험되지 않았습니다… **다음 단계:** 이번 주에 동네 커뮤니티 두 곳에 공원 촬영 3–4자리를 올리고, 예약 수, 받은 금액, 고객 한 명당 보정 시간(분)을 기록하세요.

**팁**

- 얼마나 세게 밀어붙일지 말해 주세요. "짧게", "깊이 있게", 또는 더 혹독한 검증을 원하면 "허점을 찔러 주세요"라고 하면 됩니다.
- 언제든 "마무리"라고 하면 바로 결론과 요약서로 넘어갑니다.
- 결론이 "열려 있음"이면 핵심 가정을 아직 현실에서 시험해 봐야 한다는 뜻이고, 그게 어떤 가정인지는 요약서에 적혀 있습니다.

### dia-reductio: 주장이 앞뒤가 맞는지 확인하기

**쉽게 말하면.** 귀류법, 다른 말로 모순에 의한 증명입니다. 주장을 말 그대로 받아들여 한 단계씩 따라가 보고, 동시에 참일 수 없는 두 문장에 이르는지 봅니다. 그렇다면 출발점의 무언가는 포기해야 합니다. 어시스턴트는 사용한 전제를 모두 나열하고, 그중 자기가 보탠 것을 표시하며, 무엇을 포기할지는 사용자에게 맡깁니다.

**이럴 때 쓰세요.** "언제나", "절대", "모든 사람" 같은 말이 들어간 자신만만한 규칙을 들었을 때, 또는 내 입장을 변호하기 전에 먼저 시험해 보고 싶을 때입니다. 어떤 생각이 전체적으로 현명한지 판단하는 용도로는 **맞지 않습니다**. 이 스킬은 일관성만 시험합니다.

**해 보기:**

```
이 주장에 귀류법을 적용해 주세요: 고객은 언제나 옳다.
```

**결과는 이렇습니다** (실제 실행, 줄임):

> **시험한 해석:** "옳다"는 참이라는 뜻이므로, 고객이 하는 말은 무엇이든 맞다.
> **전제:** P1 [A] "옳다"는 "참이다"라는 뜻이다. P2 [A] 같은 코트를 두고 고객 C1은 이곳에서 샀다고 하고 고객 C2는 이곳에서 사지 않았다고 한다. P3 [L] not-p가 참이면 p는 참이 아니다.
> **도출:** 1. 모든 고객의 주장은 참이다(주장 자체). … 4. p는 참이다. … 6. p는 참이 아니다.
> **모순:** 4행과 6행. **강도:** 추가한 전제 P1과 P2에 기대고 있으며, 이 둘은 논리가 아니라 평범한 사실입니다.
> **선택지:** "언제나"를 포기한다. "옳다"에 다른 뜻을 준다. 고객끼리 의견이 엇갈리는 일은 없다고 본다. 또는 주장을 고친다: "고객의 선의의 불만은 공정하게 들을 가치가 있고, 업체가 할 수 있는 범위에서 해결책을 받을 가치가 있다."
> **권고:** 고친 주장. 이 구호가 원래 하려던 일을 지켜 주기 때문입니다. 결정은 사용자의 몫입니다.

표시의 뜻은 이렇습니다. **[T]** 주장이 직접 말한 것, **[L]** 논리 법칙, **[A]** 어시스턴트가 보탠 것. [A] 전제가 있어야 성립하는 모순은 그 전제만큼만 강하며, 어시스턴트는 그 점을 밝힙니다.

**팁**

- 어시스턴트 자신의 직전 답변을 시험하려면 "직전 답변을 귀류법으로 검토해 주세요"라고 쓰거나 `--target=claude`를 붙이세요.
- [A] 전제가 틀렸다고 생각하면 그렇게 말해 주세요. 어시스턴트가 그 전제를 빼고 논증을 다시 실행합니다. 선택지 중 하나를 고를 때도 같은 방식으로 하면 됩니다.

### dia-negative: 주장을 그 자신의 기준으로 평가하기

**쉽게 말하면.** 주장을 내 가치관으로 판단하는 대신, 그 주장이 스스로 한 말로 판단합니다. 주장이 약속하는 것("누구나 언제든 문제를 제기할 수 있다")을 붙잡고, 그 약속이 지켜지지 않는 실제 사례를 찾습니다. 그다음 그 주장이 실제로 어떤 일을 하는지, 확인해 볼 수 있는 추측의 형태로 묻습니다. 이름은 철학자 아도르노의 '부정의 변증법'에서 왔습니다. 이 스킬은 그의 생각을 더 좁고 실용적으로 다듬은 '내부 비판'을 사용합니다.

**이럴 때 쓰세요.** 구호, 정책, 사명 선언문, 계획이 그럴듯하게 들리는데 무엇이 빠져 있는지 보고 싶을 때입니다. 코드나 명령어, 설정이 무엇을 하는지 설명하는 용도나 일반적인 검토용으로는 **맞지 않습니다**.

**해 보기:**

```
이 주장에 대해 내재적 비판을 해 주세요: "우리 회사는 오픈 도어 정책을 운영하므로, 회사의 누구나 언제든지 경영진에게 문제를 제기할 수 있습니다."
```

**결과는 이렇습니다** (실제 실행, 줄임):

> **주장 자신의 기준:** "누구나"(예외 없음), "언제든지"(시간 제한 없음), "경영진에게 문제를 제기할 수 있다"(경영진에게 닿는다), 그리고 "~하므로"(정책만으로 충분하다).
> **F1. 경영진에 관한 문제에서는 "누구나"가 성립하지 않습니다.** 문제의 대상이 내 관리자라면, 열린 문은 바로 내가 불만을 제기하려는 그 사람에게 열려 있고, 정책은 다른 경로를 제시하지 않습니다. *빠져나가는 것:* 가장 제기되기 어려운 문제들.
> **F2. 실제 근무 시간 앞에서 "언제든지"가 성립하지 않습니다.** 야간 근무자나 원격 근무자는 새벽 3시에 관리자*에게* 직접 문제를 제기할 수 없습니다.
> **F3. "~하므로"가 지나칩니다.** 정책은 허락을 줄 뿐입니다. 사람들이 실제로 말할 수 있는지는 그 뒤에 무슨 일이 일어나는지, 예컨대 아무 반응이 없거나 보복을 당하는지에도 달려 있습니다.
> **실제로 하는 일(추론):** 침묵의 책임을 문을 열고 들어오지 않은 사람에게 돌립니다. *이것이 틀렸음을 보여 줄 증거:* 관리자에 대한 불만이 이 정책을 통해 제기되고 실제로 처리된 기록.
> **선택지:** 주장의 범위를 좁힌다. 관행을 바꾼다(두 번째 경로, 근무 시간 외 신고, 보복 금지 약속). 그대로 두되 한계를 공개적으로 밝힌다. 주장을 철회한다. 실제 사례 하나로 시험해 본다. **권고:** 관행을 바꾸기. 결정은 사용자의 몫입니다.

**팁**

- 조건부로 표시된 발견은 사용자의 상황에 관한 사실에 달려 있으니, 그 사실을 어시스턴트에게 알려 주세요. 어떤 기준이 사실 그 주장의 기준이 아니라고 말하면, 그 기준을 쓴 발견을 빼고 다시 실행합니다.
- 선택지 하나를 권고하지만, 대신 골라 주지는 않습니다.

### dia-warrant: 이유가 결론을 얼마나 뒷받침하는지 보기

**쉽게 말하면.** 일상의 논증은 대부분 무언가를 증명하지 않고, 결론을 그럴듯하게 만들 뿐입니다. 전문가가 그렇게 말했다, 그 사람에게는 통했다, 이게 저걸 일으킨다는 식입니다. `dia-warrant`는 철학자 스티븐 툴민의 방식에 따라 이런 논증을 부분별로 펼쳐 놓습니다. **주장**, 주장이 기대는 **자료**, 자료에서 주장으로 건너가게 해 주는 일반 규칙인 **논거**(사람들이 대개 말하지 않고 넘어가는 부분), 그 규칙의 **뒷받침**, 주장이 얼마나 확실한지 나타내는 **한정어**, 그리고 규칙이 통하지 않는 경우인 **반박 조건**입니다. 그다음 논증 연구자 더글러스 월턴이 정리한, 그런 종류의 논증에 던지는 표준 **비판적 질문**을 묻고, 질문마다 어느 부분을 시험하는지 표시한 뒤 가장 약한 고리를 짚습니다. 뒷받침이 가장 얇은 한 부분을 "가장 약한 고리: 논거"처럼 이름으로 말해 줍니다. 판단하는 것은 뒷받침의 정도이지, 주장이 참인지가 아닙니다.

**이럴 때 쓰세요.** "왜냐하면"이 얼마나 무게를 버틸 수 있는지 알고 싶을 때입니다. 전문가의 조언, 다른 사람의 경험과 비교하는 말, 앞으로 일어날 일에 대한 예측 같은 것들입니다. 주장에 "언제나", "모든", "절대"가 들어 있고 그 말을 엄격한 뜻으로 쓴다면 `dia-conjecture`, 주장이 스스로 모순되는지 알고 싶다면 `dia-reductio`, 결정하려는 계획이라면 `dia-counterplan`을 **대신 쓰세요**.

**해 보기:**

```
이 이유가 결론을 얼마나 뒷받침하나요? "제 친구는 퍼스널 트레이너인데 달리기가 무릎을 망친다고 하더라고요. 그러니 제가 달리기를 시작하면 무릎에 문제가 생길 거예요."
```

**결과는 이렇습니다** (실제 실행, 줄임):

> **대상:** user (추정). 말씀하신 그대로의 논증을 검토합니다.
> **주장 (C):** "제가 달리기를 시작하면 무릎에 문제가 생길 거예요." 명시되어 있고, 한정어는 없습니다("생길 거예요").
> **중간 주장 (C1):** "달리기가 무릎을 망친다." 친구의 견해로 명시되어 있습니다. 이 논증은 사슬 구조입니다: 자료 → C1 → C.
> **읽는 방식 고정:** "망친다"는 뜻이 모호합니다. "달리는 사람의 무릎에 오래가는 손상을 일으킨다"로 읽겠습니다.
> **자료 (명시됨):** "제 친구는 퍼스널 트레이너인데 달리기가 무릎을 망친다고 하더라고요."
> **Wa (재구성):** 퍼스널 트레이너가 달리기가 무릎에 미치는 영향에 대해 하는 말은 대체로 믿을 만하다. 자료에서 C1로 가는 단계입니다. **Wb (재구성):** 달리기가 대체로 무릎을 망친다면, 달리기를 시작한 사람은 대체로 무릎에 문제가 생길 것이다. C1에서 C로 가는 단계입니다.
> **뒷받침:** 제시되지 않음. **반박 조건:** 제시되지 않음. **도식:** 첫 단계는 **전문가 의견**입니다. 둘째 단계는 **일반 규칙을 사례에 적용**하는 것이고, 일반 질문으로 시험했습니다.
> **비판적 질문** *(8개, 모두 열려 있음)*: 1. [자료] 그 친구는 이 주장이 속한 분야의 진짜 전문가입니까? 밝혀진 역할은 퍼스널 트레이너입니다. 그것이 관절 건강이나 부상까지 다루는지는 논증에 나오지 않습니다. **열려 있음.** … 3. [논거/뒷받침] 그 친구의 주장은 증거에 근거합니까? 논증은 아무 증거도 들지 않고 "그렇게 말하더라"뿐입니다. **열려 있음.** … 7. [반박] 예를 들어 달리는 양, 과거 이력, 그 밖의 요인 때문에 당신이 예외일 수 있습니까? **열려 있음.** … 어느 질문에도 제가 가진 사실로 답하지 않았습니다. 하나하나 당신이나 출처가 답해야 합니다.
> **한정어 점검:** C는 "생길 거예요"라고 합니다. Wa와 Wb가 허용하는 것은 "대체로", 즉 "아마"뿐입니다. 그러므로 주장은 **지나치게 강합니다**. 두 논거 모두 제가 재구성한 것이고, 지나친 강도는 "대체로"라는 기본값에서 나옵니다. "반드시"라는 뜻이었다면 말씀해 주세요. …
> **결과:** **가장 약한 고리: 논거 (Wa). "그 친구의 주장은 증거에 근거합니까?"가 열려 있기 때문입니다.** 모든 것이 "그렇게 말하더라"에 기대고 있어서 중요합니다. 그 친구의 주장에 밝혀진 근거가 없으면, 자료는 C를 거의 뒷받침하지 못합니다. 그 주장이 무엇에 기대는지, 예를 들어 연구, 고객들의 결과, 부상에 관한 교육을 알면 고리가 튼튼해집니다. … *(이어서 기록: 대상과 주장, 모드, 도식, 둘 다 재구성된 논거, 물은 질문 8개 중 답한 것 0개, 결과, 한정어 점검, 고리를 튼튼하게 할 것, 재구성된 논거에 대한 결정: 보류)*
> 이 점검은 달리기가 무릎 문제를 일으키는지 판정하지 않습니다. 제시된 이유가 그 주장을 얼마나 잘 뒷받침하는지만 평가합니다.
> 자기 논증을 단계별로 점검하고 싶으시면 ask 모드로 바꿀 수 있습니다.

"명시됨"은 논증이 직접 말한 것이고, "재구성"은 그 단계에 필요해서 어시스턴트가 보충한 것입니다. 여기서는 이유가 중간 주장(C1, "달리기가 무릎을 망친다")을 거쳐 가므로, 단계마다 논거(Wa, Wb)가 따로 붙고 결과도 약한 고리가 어느 단계에 있는지 밝힙니다. 시험하기 전에 모호한 단어 "망친다"를 한 가지 뜻으로 고정해 두기도 했습니다. 꺾쇠 표시는 각 질문이 어느 부분을 시험하는지 보여 줍니다: **[자료]**, **[논거/뒷받침]**, **[반박]**, **[결론]**. 결과는 자료, 논거, 뒷받침, 한정어, 반박 조건, 주장 중 한 부분을 짚습니다.

**팁**

- 열려 있는 질문에 다음 메시지로 답하세요("고객 중에 달리는 사람은 대부분 무릎이 아프다고 하더래요"). 어시스턴트가 그 질문을 사용자가 답한 것으로 표시하고 결과를 다시 따집니다.
- 재구성된 논거에 실제로 기대고 있지 않다면 그렇게 말하세요. 그 논거는 빠지고, 어시스턴트가 실제로 기대는 규칙이 무엇인지 묻습니다.
- 자기 논증을 점검하면, 점검 끝에 ask 모드(`--mode=ask`)를 제안합니다. 어시스턴트가 한 번에 한 부분씩 묻고 사용자가 채워 넣는 방식입니다. 처음부터 요청해도 되며, 아직 다듬는 중인 논증에 잘 맞습니다.
- "물어본 질문 중에서는 약한 고리를 찾지 못함"은 증명이 아니며, 약한 고리가 있다고 주장이 거짓이 되는 것도 아닙니다.

### dia-conjecture: "언제나" 규칙을 반례로 시험하기

**쉽게 말하면.** "언제나", "모든", "절대"가 들어간 규칙은 들어맞지 않는 사례 하나로 무너질 수 있습니다. 이 스킬은 철학자 임레 라카토슈가 『증명과 반박』에서 설명한 방법을 따릅니다. 먼저 그 규칙을 믿는 이유를 번호 붙은 단계로 나눕니다. 그다음 메시지마다 반례를 하나씩 가져와, 그 사례가 어떻게 규칙의 조건에 들어맞으면서도 규칙을 깨는지 한 줄씩 보여 주고, 그 사례가 무엇에 기대는지도 밝힙니다(예시용으로 지어낸 숫자로 한 계산인 경우가 많습니다). 각 사례가 반례로 인정되는지는 사용자가 정합니다. 인정되더라도 규칙을 버릴 필요는 없습니다. 어시스턴트가 깨진 단계를 규칙 안에 조건으로 넣는 것 같은 수선 방법들을 내놓고 하나를 권하지만, 고르는 것은 사용자입니다. 그러면 규칙이 언제 성립하는지 정확히 말하게 됩니다.

**이럴 때 쓰세요.** 기대고 있는 경험칙을 엄격한 뜻으로 말할 때입니다. "대용량으로 사면 언제나 돈이 절약된다", "빠른 계산대 줄이 언제나 더 빠르다", "비싼 와인이 언제나 더 맛있다" 같은 것들입니다. "대개"라는 뜻이라면 `dia-warrant`, 계획이나 정책, 결정이라면 `dia-counterplan`(허점을 찔러 보려면 `dia-brainstorm`), 진짜 문제가 단어의 뜻이라면 `dia-elenchus`를 **대신 쓰세요**.

**해 보기:**

```
내 규칙의 반례를 찾아 주세요: 대용량으로 사면 언제나 돈이 절약된다.
```

**세션은 이렇게 진행됩니다** (실제 실행, 줄임):

> **어시스턴트:** 직접 내세우신 주장입니다. 제 말로 옮기면 C는 이렇습니다: 대용량으로 사는(한 번에 평소보다 많이 사는) 모든 구매는 돈을 아껴 준다. 여기서 "돈을 아낀다"는 대용량으로 사지 않았을 때보다 전체로 덜 쓴다는 뜻입니다. 왜 이 규칙을 믿으십니까? 정리된 논증이 없다면 번호 붙은 단계로 재구성해 드릴 수 있지만, 그러면 제가 직접 쓴 증명을 제가 공격하게 됩니다. 어느 쪽을 원하십니까?
>
> **나:** 네, 이유를 말할 수 있어요. 큰 포장이 개당 가격이 더 싸고, 어차피 살 물건이니까, 결국 덜 쓰게 되죠. 원하시면 단계로 정리해 주세요. 어느 단계에 동의하는지 말씀드릴게요.
>
> **어시스턴트:** 논증을 번호 붙은 단계로 정리했습니다. L1과 L2는 당신의 말입니다. L3부터 L5는 논증에 필요해서 제가 썼습니다. 1. [T] "큰 포장이 개당 가격이 더 싸다" 2. [T] "어차피 살 물건이다" 3. [A] 큰 포장에 든 것을 전부 쓴다. 상하거나, 기한이 지나거나, 잃어버리거나, 버리는 것이 없고, 많이 있다고 더 빨리 쓰지도 않는다. … 4. [A] 대용량 구매에 따르는 추가 비용은 없거나, 개당 절약분에 비해 작다. 회비, 보관 공간, 미리 내는 돈, 운반이 여기에 들어간다. … 5. [A] 개당 가격이 싼 것은 대용량 포장 자체 때문이지, 작은 포장의 할인 행사 때문이 아니다. … L3이 가장 의심스럽습니다… L3부터 L5는 제가 쓰고 제가 공격하는 것이므로, 여기서 저는 양쪽을 모두 맡고 있습니다. 이것이 당신의 논증입니까? 틀린 줄은 고치고, 어느 줄을 받아들이는지 알려 주세요.
>
> **나:** 네, 그게 제 논증이에요. 1, 2, 4, 5는 동의하고, 3은 제가 정말 다 쓰는 물건만 말한 거라서, 다 쓰기 전에 상하는 건 절약으로 치지 않는 것 같아요.
>
> **어시스턴트:** 규칙을 바꾸신 것이니, 예전 문구와 새 문구를 적겠습니다. **예전 C:** 모든 대용량 구매는 돈을 아껴 준다. **새 C′:** 실제로 다 쓸 물건의 대용량 구매는 모두 돈을 아껴 준다. **C′가 더 이상 포괄하지 않는 것:** 다 쓰기 전에 상하거나, 기한이 지나거나, 눅눅해지거나, 잃어버리는 모든 것. … 사례를 내놓기 전에 묻겠습니다. 무엇을 이 규칙에 대한 반대 증거로 받아들이시겠습니까? …
>
> *…사용자는 물건을 전부 다 썼는데도 작은 포장들보다 전체로 더 많이 낸 경우, 예를 들어 회비나 그곳까지 가는 기름값이 개당 절약분보다 큰 경우라고 답합니다…*
>
> **어시스턴트:** 사례 1 (둘 다: C′와 L4에 대한 반례): 한 번뿐인 창고형 매장 나들이. 키친타월 40롤 묶음 하나를 사려고 연회비 $60를 내고 창고형 매장에 가입한다고 해 봅시다. 이 묶음은 근처 가게보다 롤당 $0.25 싸고, 40롤을 다 씁니다. **A, 다 쓸 물건의 대용량 구매인가?** 예. 40롤 묶음이고 한 롤도 남김없이 씁니다. **B가 깨지는가, 돈을 아끼는가?** 예, 깨집니다. 롤당 절약분은 40 × $0.25 = $10인데, 가입하는 데 $60를 냈습니다. … **L4도 깨집니다.** … 이 사례는 제가 지어낸 숫자로 한 계산에 기대므로, 증거 등급은 실제 영수증이 아니라 논리입니다. 이 사례가 당신의 규칙에 대한 반례로 인정됩니까?
>
> **나:** 네, 그건 인정해요. … 대용량은 회비 같은 추가 비용이 제가 아끼는 돈보다 작을 때만 돈을 아껴 준다고 해야겠네요.
>
> **어시스턴트:** 고치신 내용은 대용량이 추가 비용이 아끼는 돈보다 작을 때만 돈을 아껴 준다는 것입니다. 맞는 말이지만 수선으로는 통하지 않습니다. "대용량은 돈을 아낄 때 돈을 아낀다"는 말이 되어, 어떤 구매도 반례가 될 수 없습니다. … 1. **이 구매에 따르는 추가 비용이 없을 것.** C′는 이렇게 됩니다: 다 쓸 물건의 대용량 구매 가운데, 이 구매 하나 때문에 생기는 회비, 일부러 가는 걸음, 보관 비용이 없는 것은 모두 돈을 아껴 준다. … 2. **회비와 일부러 가는 걸음만.** … 3. **C′를 포기하기.** … 1번을 권합니다. L4가 숨기고 있던 비용을 모두 짚어 내므로, 예외를 하나씩 덧붙이게 되지 않습니다. 어느 것을 고르시겠습니까?

> **나:** 1번으로 할게요. 회비만이 아니라 보관이랑 일부러 가는 걸음도 포함하고, 그것들도 똑같이 절약분을 갉아먹을 수 있으니까, 하나씩 땜질하기보다 추가 비용을 처음부터 다 적어 두는 게 좋겠어요.
>
> **어시스턴트:** 고르신 대로의 현재 주장 C′: … 사례 2 (둘 다: C′와 L1에 대한 반례): 개당 가격이 더 비싼 대용량 포장. 한 가게에서 어떤 브랜드 건전지를 12개들이 $9(개당 $0.75), 48개들이 $42(개당 $0.875)에 판다고 해 봅시다. 건전지가 48개 필요하고 하나도 남김없이 씁니다. … **B가 깨지는가, 돈을 아끼는가?** 예, 깨집니다. 48개들이는 $42이고, 12개들이 네 개는 4 × $9 = $36입니다. $6를 더 씁니다. **L1도 깨집니다.** … 이 사례가 당신의 규칙에 대한 반례로 인정됩니까?
>
> **나:** 네, 그것도 인정해요. … 개당 가격을 먼저 확인해야겠네요. 제 규칙은 큰 포장이 정말 개당 더 쌀 때만 통하니까요.
>
> **어시스턴트:** 개당 가격을 먼저 확인하자는 것은 수선이 맞고, 지난번과 달리 사기 전에 확인할 수 있는 조건이 있습니다. 세 가지 형태가 있습니다: … 1번을 권합니다… 한 가지 주의할 점: 이만큼 넣고 나면 규칙은 거의 계산만으로 참이 됩니다. … 남는 것은 발견이라기보다 점검표에 가깝습니다. 어느 것을 고르시겠습니까?

**팁**

- 사례가 규칙에 들어맞지 않는다고 생각하면, 그 검토 과정의 어느 줄이 틀렸는지 말하세요. 그냥 "아니요"라고만 하면 그 사례는 "다툼 있음"으로 남습니다. 철회되지도 않고 반례로 인정되지도 않습니다.
- 수선 방법은 매번 사용자가 고릅니다. 이미 자기 말로 말한 것이어도 마찬가지입니다. 위 실행에서 사용자는 고칠 방법을 두 번 직접 말했고, 어시스턴트는 두 번 다 번호 붙은 선택지를 내놓고 하나를 권한 뒤 고르라고 했습니다. "대용량은 돈을 아낄 때 돈을 아낀다"는 말이 되어 버리는 수정은 수선으로 받아들여지지 않습니다. 어떤 구매도 그 규칙의 반례가 될 수 없기 때문입니다.
- 사례마다 무엇에 기대는지 적혀 있습니다. "지어낸 숫자로 한 계산"은 숫자는 지어낸 것이고 계산만 확인했다는 뜻입니다. 실제 가격이 그런지는 사용자가 판단합니다.
- 위 실행의 "정말 다 쓰는 물건만 말한 거"처럼 규칙의 단어를 좁히면 정의를 바꾸는 것입니다. 어시스턴트는 예전 문구와 새 문구를 적고, 규칙이 이제 무엇을 포괄하지 못하는지 밝힙니다. 사례를 막으려고 "그건 진짜 대용량 구매가 아니다"라고 하는 것도 마찬가지입니다.
- 세 라운드가 지나면 멈출지 묻고, "마무리"라고 하면 언제든 멈춥니다. 가장 좋은 결과는 "시험한 사례들에 대해서는 버팀"이며, "증명됨"은 결코 아닙니다. "열려 있음"은 다툼 있는 사례가 있거나, 인정된 반례가 있는데 아직 수선 방법을 고르지 않았다는 뜻입니다.

### dia-counterplan: 다른 계획을 옹호하는 주장 들어 보기

**쉽게 말하면.** 큰 결정을 앞두고는 정반대의 가정 위에 세운 다른 계획을 누군가 옹호하는 말을 들어 보는 것이 도움이 됩니다. 이것이 경영학 연구에서 나온 계획 방법인 변증법적 탐구입니다(리처드 메이슨, 1969). 어시스턴트는 사용자의 계획이 기대는 가정들을 나열하고, 틀렸다면 결정이 바뀔 가정만 남겨, 가정마다 그럴듯한 반대 가정을 세운 뒤, 같은 사실 위에 가장 강한 경쟁 계획을 짭니다. 반대 가정은 어시스턴트가 고른 것이고, 거기 붙은 이유("…라고 가정하면")는 사용자의 상황에 대한 사실이 아니라 가정일 뿐입니다. 그다음 사용자가 이제 어느 가정을 믿는지 말하고, 그 조합이 결과가 됩니다. 어시스턴트는 어느 단계에서도 판정을 내리지 않으며, 양쪽을 모두 자기가 썼다는 사실을 솔직히 밝힙니다.

**이럴 때 쓰세요.** 어떤 계획에 막 뛰어들려 할 때입니다. 이사, 이직 제안, 큰 구매, 팀의 다음 단계 같은 경우입니다. 내 아이디어에 대해 한 번에 한 질문씩 질문을 받거나 허점을 찔러 보고 싶다면 `dia-brainstorm`, 계획이 스스로 한 약속을 지키는지 보려면 `dia-negative`, 하나의 논증이 내세운 이유가 얼마나 튼튼한지 보려면 `dia-warrant`를 **대신 쓰세요**. 어떤 주장 하나가 참인지가 궁금하다면 그냥 물어보면 됩니다.

**해 보기:**

```
이 계획에 반대 입장을 맡아 주세요: 아이들(6살, 3살)이 내년 9월에 학교에 들어가기 전에, 도심의 방 두 개짜리 아파트에서 교외의 더 큰 집으로 이사하려고 합니다. 매달 내는 대출 상환금은 지금 월세와 비슷하고, 아이들이 각자 방을 갖고 마당도 생기며, 그 동네 학교는 평이 좋습니다. 걸리는 점은 제 출퇴근 시간이 편도 20분에서 1시간 정도로 늘어난다는 것입니다.
```

- "어느 계획이 이기나요?"라고 물어도 탐구 중이든 끝난 뒤든 판정은 하지 않습니다. 같은 어시스턴트가 양쪽을 썼기 때문입니다. 대신 가장 판단하기 어려운 쌍을 가를 관찰이 무엇인지 알려 줍니다.

### dia-refine: 답변이나 초안을 한 번 꼼꼼히 검토하기

**쉽게 말하면.** 꼼꼼한 편집자가 한 번 훑어보는 것입니다. 어시스턴트는 잘못된 점을 나열하고, 하나하나 확인한 뒤, 확인된 오류만 고칩니다. 의심은 되지만 확인하지 못한 오류는 예상되는 수정안과 함께 따로 적어 두므로, 아무것도 몰래 바뀌지 않습니다.

**이럴 때 쓰세요.** 초안이나 어시스턴트의 직전 답변이 있고, 사실 오류와 논리의 빈틈, 빠진 부분을 한 번 바로잡고 싶을 때입니다. 메시지를 `dia-refine`으로 시작하고, 특별히 볼 부분이 있으면 덧붙이세요.

**해 보기:**

```
dia-refine 사실관계를 확인해 주세요: 만리장성은 달에서 맨눈으로 보이는 유일한 인공 구조물이며, 전부 명나라 때 지어졌다.
```

**결과는 이렇습니다** (웹 검색을 쓴 실제 실행, 줄임):

> **① 확인된 오류:** "달에서 보인다"는 거짓입니다(검색으로 확인). 약 384,000 km 떨어진 곳에서는 어떤 인공 구조물도 하나만 따로 보이지 않으며, 우주비행사들은 우주에서 맨눈으로 장성을 볼 수 없다고 말해 왔습니다. "전부 명나라 때 지어졌다"도 거짓입니다. 기원전 220년 무렵 진나라 때 성벽들이 이어졌고, 다른 왕조들도 구간을 덧붙였습니다.
> **② 누락된 요구 사항:** 없음.
> **③ 유지한 올바른 내용:** 오늘날 볼 수 있는 석조 성벽의 대부분은 명나라가 지었습니다.
> **④ 남은 불확실성:** 진나라와 한나라 시기의 정확한 연대는 자료마다 다르며, 2차 자료만 확인했습니다.
> **수정본:** 만리장성은 달에서 맨눈으로 보이지 않으며, 그렇게 보이는 인공 구조물은 하나도 없습니다. 또한 전부 명나라 때 지어진 것도 아닙니다… *(출처 목록)*

**팁**

- 검색 도구가 없어도, 어시스턴트가 직접 다시 따져 볼 수 있는 논리와 계산은 고칠 수 있고, 확인하지 못한 사실은 ④에 적습니다.
- "이 작업을 dia-refine 방식으로 해 주세요"라고 하면, 답변을 쓰고 한 번 검토한 뒤 최종본만 보여 줍니다.

### dia-ratchet: 라운드를 거듭하며 확인하고 고치기

**쉽게 말하면.** `dia-refine`과 비슷하지만 여러 라운드에 걸쳐 진행되고, 모든 수정에 외부 근거가 필요합니다. 검색, 도구 실행, 또는 사용자가 준 자료입니다. 확인을 통과한 사실은 고정되어서 이후 라운드에서 되돌릴 수 없습니다. 더 고칠 것이 없거나, 더는 검증할 수 없거나, 라운드 상한에 이르면 반복은 저절로 멈춥니다.

**이럴 때 쓰세요.** 속도보다 정확성이 중요할 때입니다. 예를 들어 곧 공개할 글의 사실과 날짜를 확인할 때입니다. 메시지를 `dia-ratchet`으로 시작하세요. 일반 요청으로는 절대 시작되지 않습니다.

**해 보기:**

```
dia-ratchet --max 2 이 문단의 날짜와 사실을 확인해 주세요: "최초의 아이폰은 2008년에 출시되었고, 같은 날 앱 500개와 함께 앱스토어가 문을 열었다."
```

**결과는 이렇습니다** (웹 검색을 쓴 실제 실행, 줄임):

> **변경 사항:** "2008년에 출시되었고" → "2007년"(2007년 6월 29일 출시). "같은 날 앱스토어가 문을 열었다" → "약 1년 뒤인 2008년 7월에".
> **라운드 요약:** 1라운드: 주장 3개를 웹 검색으로 확인했고, 2개는 틀린 것으로 확인, 1개는 맞았습니다. 고정한 항목: 아이폰 출시일, 앱스토어 개장일, 개장 당시 앱 약 500개. 남은 결함이 없어서 멈췄으므로 2라운드는 필요하지 않았습니다.
> **검증하지 못한 항목:** 개장 당시의 정확한 앱 수(자료에 따라 500개에서 552개)와, 앱스토어가 2008년 7월 10일에 열렸는지 11일에 열렸는지.
> **수정한 문단:** "최초의 아이폰은 2007년에 출시되었고, 약 1년 뒤인 2008년 7월에 앱 500개와 함께 앱스토어가 문을 열었다."

**팁**

- `--max N`으로 라운드 상한을 정합니다(기본값 3).
- 검색이나 도구가 없는 채팅에서는 1라운드 후에 멈추고, 짐작하는 대신 검증하지 못한 항목을 나열합니다.
- 1.5.0 이전 이름은 `dia-iterate`였습니다. 옛 이름으로는 더 이상 시작되지 않습니다.

### dia-adjudicate: 리뷰의 어떤 지적이 맞는지 가리기

**쉽게 말하면.** 리뷰를 판정하는 심판입니다. 글 하나와 그 글에 대한 비판이나 리뷰를 하나 이상 주면 됩니다. 사람이 쓴 것이든 다른 어시스턴트가 쓴 것이든 상관없습니다. 글의 주장과 리뷰의 모든 지적을 출처와 대조해 어떤 지적이 맞고 어떤 지적이 틀렸거나 과장됐는지 판정하고, 사람이 다시 확인해야 할 판정 몇 개를 마지막에 모아 줍니다. 글을 고쳐 쓰지 않고, 자기 리뷰를 덧붙이지도 않습니다.

**이럴 때 쓰세요.** 같은 글에 대한 리뷰들이 서로 다르게 말할 때, 또는 자신 있게 쓰인 리뷰를 따르기 전에 확인하고 싶을 때입니다. 메시지를 `dia-adjudicate`로 시작하고 글과 리뷰를 함께 주세요. 일반 요청으로는 절대 시작되지 않습니다.

**해 보기:**

```
dia-adjudicate
글: "무어는 1965년 논문에서 트랜지스터 수가 18개월마다 두 배가 된다고 예측했으므로, 10년이면 칩에 약 16배가 들어간다."
리뷰 A: "두 군데가 틀렸다. 1965년 논문은 매년이라고 했고, 2년마다 두 배면 10년에 32배다."
리뷰 B: "18개월은 무어 본인이 1975년에 제시한 수치이고, 2년마다 두 배면 10년에 64배다."
```

**결과는 이렇습니다** (같은 사실로 이 스킬의 초안을 웹 검색과 함께 돌린 설계 실험을 바탕으로 만든 예시이며, 이 프롬프트를 실제로 실행한 기록은 아닙니다. [docs/research/dia-adjudicate.md](docs/research/dia-adjudicate.md) 참고):

> **글의 주장:** "1965년 논문의 18개월"은 성립하지 않습니다. 1965년 논문은 약 1년마다라고 했고, 18개월은 인텔의 데이비드 하우스가 성능에 대해 한 말입니다. "약 16배"도 성립하지 않습니다. 2^5 = 32입니다(재계산).
> **리뷰 항목:** A는 타당합니다. B는 두 지적 모두 틀렸습니다. 1975년의 수정은 2년마다였고, 2년마다 두 배면 64배가 아니라 32배입니다.
> **사람이 확인할 것:** B를 뒤집은 판정 두 개와, 각 판정이 기댄 출처 문장.

**팁**

- 리뷰는 받은 그대로 주면 됩니다. 순서를 섞어 R1, R2…로 다시 붙이고, 누가 썼는지가 아니라 내용으로 판정합니다.
- 어시스턴트가 별도의 에이전트를 띄울 수 있거나 두 번째 채팅을 열 수 있다면, 같은 입력으로 두 번 돌리고 판정이 갈린 곳만 다시 확인하세요.
- 검색 도구가 없으면 숫자와 논리는 다시 계산하지만, 사실에 관한 지적은 뒤집지 않고 "확인 불가"로 남깁니다.

### dia-instruct: 모델이 따를 글 쓰기

**쉽게 말하면.** AI에게 주는 지시문을 점검하는 문체 검사입니다. 스킬 파일, 에이전트용 프롬프트, 프로젝트의 에이전트 지침 파일, 규칙 파일이 대상입니다. 글을 네 가지 규칙에 비춰 봅니다. 문단마다 원하는 결과를 말하고 그 조건과 대안을 같은 문장에 담아, 어떤 조건도 따로 떨어진 줄에 남지 않게 합니다. 한계를 정하는 단어("건드리다", "바꾸다" 같은)는 뜻한 만큼만 좁아야 합니다. 지시는 더 적게 쓰고, 하나마다 이유를 붙입니다. 한 대상에는 이름 하나만 씁니다. 검토만 요청하면 규칙을 어긴 곳을 심각한 순서로 나열하고, 사용자가 고를 때까지 아무것도 바꾸지 않습니다.

**이럴 때 쓰세요.** 스킬, 에이전트나 서브에이전트용 프롬프트, 에이전트 지침 파일, 규칙 파일을 쓰거나 고칠 때, 또는 어시스턴트가 써 둔 조건을 자꾸 무시할 때입니다. 말로 요청하거나 이름으로 선택하세요.

**해 보기:**

```
코딩 에이전트에게 줄 이 지시문을 검토해 주세요:
새 플래그에 맞게 문서를 업데이트하라.
작업에 필요한 파일만 건드려라.
- 테스트가 실패하면 멈춰라.
```

**결과는 이렇습니다** (보고서 형식을 보여 주는 예시이며, 실제로 실행한 기록은 아닙니다):

> **"테스트가 실패하면 멈춰라"**: 조건이 따로 떨어진 글머리 기호에 있어, 그 조건이 막아야 할 업데이트와 떨어져 있습니다(규칙 1).
> **"건드려라"**는 편집뿐 아니라 읽기로도 읽힐 수 있습니다. 파일 이름을 적거나 "편집하라"고 쓰세요(규칙 2).
> **이유 없음:** 어느 줄도 이유를 말하지 않아, 에이전트는 어떤 문서가 중요한지 알 수 없습니다(규칙 3).
> 사용자가 지적 사항을 고를 때까지 아무것도 바꾸지 않습니다.

**팁**

- 건네받은 글은 그 자체가 프롬프트라도 따를 지시가 아니라 점검할 재료로 다룹니다.
- "이 규칙은 근거가 얼마나 강한가요?"라고 물으면 각 규칙의 근거를 보여 줍니다. 그 파일은 그때만 읽습니다.
- 어시스턴트가 별도 에이전트를 띄울 수 있으면, 계속 쓸 글의 변경은 그 변경을 쓰지 않은 에이전트가 검토합니다. 그렇지 않으면 독립적이지 않은 점검이라고 밝힙니다.

### dia-menu: 짧은 한 단어로 모든 스킬 부르기

**쉽게 말하면.** 그 자체로 하나의 방법은 아니고, 더 빨리 들어가는 길일 뿐입니다. 메시지를 `dia`로 시작하세요. `dia`만 쓰면 스킬 열두 개를 번호와 함께 보여 줍니다. 뒤에 번호나 이름의 앞 몇 글자를 붙이면 그 스킬이 시작되고, 원하는 일을 그냥 쓰면 알맞은 스킬을 골라 대개 먼저 한 줄로 어떤 스킬인지 알려 줍니다. 앞 글자가 두 스킬에 해당하거나 두 스킬이 요청에 비슷하게 맞으면, 짐작하지 않고 묻습니다.

**이럴 때 쓰세요.** 휴대폰으로 입력할 때, 또는 어떤 스킬이 필요한지 잘 모를 때입니다. `dia-confirm`(1), `dia-ratchet`(10), `dia-adjudicate`(11)는 번호나 이름으로만 시작되며, `dia`가 짐작해서 시작하는 일은 없습니다.

**해 보기:**

```
dia
dia 4 모든 소수는 홀수라고 가정하고 어디서 무너지는지 보여 주세요.
dia 온보딩 이메일을 추가한 뒤 이탈률이 떨어졌으니, 이메일이 이탈을 줄인 거예요. 제 이유가 이 결론을 얼마나 뒷받침하나요?
```

**결과는 이렇습니다** (Claude Code에서 실제 실행, 줄임; `dia con` 외에는 영어 실행을 번역):

> `dia` → 번호가 붙은 목록: "1. **dia-confirm**: 작업을 시작하기 전에 목표, 가정, 아직 열려 있는 결정을 다시 정리합니다(이름이나 번호로만). 2. **dia-brainstorm**: … 10. **dia-iterate**: 외부 확인을 거쳐야 하는 검토 라운드를 반복합니다(이름이나 번호로만)", 이어서 고르는 방법을 안내합니다.
> `dia 4 …` → `dia-reductio`가 바로 시작됩니다: "**대상:** 사용자(추정). **논제 T:** ‘모든 소수는 홀수다’. **방향:** 반박. …"
> `dia 온보딩 이메일을 …` → `dia-warrant`가 시작됩니다: "**구조** – **주장:** ‘이메일이 이탈을 줄였다’(명시됨). … **자료:** ‘온보딩 이메일을 추가한 뒤 이탈률이 떨어졌다’(명시됨). …"
> `dia con …` (`dia-confirm`과 `dia-conjecture`에 모두 해당, 한국어로 실행한 원문 그대로) → "‘con’으로 시작하는 skill이 둘이라 하나를 고를 수 없습니다. 번호로 골라 주세요." 그리고 두 스킬을 함께 보여 줍니다.
> *(1.4.0으로 기록한 실행이며, 당시 10번은 `dia-iterate`였습니다. 1.5.0부터 목록은 열한 줄이고 10번은 `dia-ratchet`, 11번은 `dia-adjudicate`입니다. 1.6.0부터는 열두 줄이며 12번은 `dia-instruct`입니다.)*

**팁**

- 번호는 바뀌지 않습니다: 1 confirm, 2 brainstorm, 3 elenchus, 4 reductio, 5 negative, 6 warrant, 7 conjecture, 8 counterplan, 9 refine, 10 ratchet, 11 adjudicate, 12 instruct.
- 옵션은 그대로 전달됩니다: `dia 10 --max 2 <draft>`는 `dia-ratchet --max 2 <draft>`와 같습니다.
- `dia`는 단독으로 첫 단어여야 합니다. `dia-refine …`을 비롯한 전체 이름은 여전히 곧바로 해당 스킬로 갑니다.
- 앞 글자는 세 글자 이상이어야 하고(`re`가 아니라 `red`), 문장의 일부임이 분명한 단어(`dia red flags in my plan?`)는 선택이 아니라 요청으로 읽습니다.
- 어시스턴트가 두 번째 스킬을 열 수 없는 환경에서는 `dia`가 메뉴는 그대로 보여 주고, 보낼 전체 형식(예: `dia-reductio …`)을 알려 줍니다. 이 경우는 시험하지 않았습니다.

## 여러 스킬 함께 쓰기

- **한 요청에 `dia-elenchus`와 `dia-brainstorm`을 함께 쓰는 경우:** 정의를 다루는 대화가 먼저 진행되며, 첫 메시지에서 이를 알립니다. 사용자가 선택지를 요청하거나 대화가 끝나면 브레인스토밍이 시작됩니다. 두 과정이 뒤섞이는 일은 없습니다.
- **한 요청에 `dia-refine`과 `dia-ratchet`을 함께 쓰는 경우:** 별개의 두 과정으로 실행되며 출력도 따로 나옵니다. refine 과정에서 어시스턴트가 직접 한 재도출은 ratchet 라운드의 검증으로 인정되지 않습니다.
- **한 요청에 `dia-reductio`와 `dia-negative`를 함께 쓰는 경우:** 둘 다 실행되고 두 답변 모두 완전하게 제시되므로 출력이 길어집니다(테스트에서 약 9,000자). 휴대폰에서는 하나씩 요청하십시오.
- **`dia-warrant`, `dia-conjecture`, `dia-counterplan`은 받은 요청부터 확인합니다.** 요청이 다른 스킬에 속하면 한 줄로 그렇게 말하고 그 스킬을 알려 줍니다. `dia-conjecture`는 "대개"라는 뜻의 규칙을 `dia-warrant`로, 계획을 `dia-counterplan`이나 `dia-brainstorm`으로 보냅니다. `dia-warrant`는 엄격한 "언제나" 주장을 `dia-conjecture`로, 계획의 가정을 `dia-counterplan`으로 보냅니다. `dia-counterplan`은 계획에 대해 질문을 받고 싶은 요청을 `dia-brainstorm`으로 보냅니다. 알려 준 스킬로 다시 요청하십시오.
- **`dia-elenchus` 이후:** 그다음에 조언을 요청하면, 어시스턴트는 소크라테스식 부분이 끝났다고 밝히고 각 제안이 자신의 것임을 표시합니다. 선택지와 계획까지 다루는 온전한 세션을 원하면 `dia-brainstorm`을 지정하십시오. 그러면 그 기록을 이어받아 진행합니다.

## 문제 해결

- **마켓플레이스를 추가할 때 `Repository not found`가 나타납니다.** 철자를 확인합니다: `ajitta/dialectic-skills`(dialectric이 아니라 dialectic). 저장소는 공개되어 있으며 GitHub 로그인이 필요하지 않습니다.
- **Claude 모바일의 `/`에 dia 스킬이 없습니다.** 정상입니다. 모바일 메뉴에는 플러그인 스킬이 표시되지 않습니다. 메시지를 `dia`로 시작하거나, 이름을 끝까지 입력하거나(예: `/dia-brainstorm`), 말로 요청하거나, 메시지를 스킬 이름으로 시작합니다.
- **어떤 기기에서는 dia가 되는데 다른 기기에서는 안 됩니다.** 데스크톱에서 설치한 것은 그 컴퓨터에만 있고, 웹에서 설치한 것은 계정에 저장되어 모바일 앱까지 갑니다. 웹과 모바일용으로 웹에서 한 번, 쓰는 데스크톱 앱마다 한 번씩 설치하세요(설치 참고).
- **모든 스킬이 두 번씩 나타납니다.** 플러그인이 두 경로로 설치된 것입니다(예: `dia@dialectic-skills`와 `dia@ajitta`, 또는 업로드와 마켓플레이스). 하나를 제거합니다.
- **claude.ai에 Skills 섹션이 없거나 비활성화되어 있습니다.** Settings › Capabilities › Code execution and file creation을 켭니다.
- **`dia-intent`를 찾을 수 없습니다.** 1.1.0에서 `dia-confirm`으로 이름이 바뀌었습니다.
- **`dia-iterate`를 찾을 수 없습니다.** 1.5.0에서 `dia-ratchet`으로 이름이 바뀌었습니다.
- **`dia-ratchet`이나 `dia-adjudicate`가 시작되지 않습니다.** 메시지의 첫 단어가 스킬 이름이거나 명시적으로 선택했을 때(`/dia:dia-ratchet`, `$dia:dia-ratchet`, `@dia-ratchet`, `dia 10`, `dia ratchet`; `dia-adjudicate`도 같은 형식과 `dia 11`)에만 시작됩니다. `dia <request>`만으로는 절대 선택되지 않습니다.
- **Codex에서 `$dia:dia-confirm:`이 인식되지 않습니다.** 스킬 이름 뒤에 콜론이 아니라 공백을 넣습니다.
- **claude.ai에서 업로드가 거부됩니다.** Customize › Skills가 아니라 Customize › Plugins › Upload plugin을 사용합니다.
- **claude.ai에서 Check for updates 후에도 예전 버전이 남아 있습니다.** Customize › Plugins에서 `dia`를 제거한 뒤 `dialectic-skills` 마켓플레이스에서 다시 설치합니다. 이후 릴리스를 자동으로 받으려면 Sync automatically를 켭니다.

어떤 경로를 어떻게 검증했는지는 [docs/probes.md](docs/probes.md)에 기록되어 있습니다.

## 개발

```bash
python tools/package.py            # validate, write plugins/dia/ and the zip
python tools/package.py --check    # validate; fail if the committed output lags the source
python -m unittest discover -s tests -v
claude plugin validate --strict plugins/dia
```

생성된 출력물이 아니라 `skills/`를 수정합니다. 스킬 파일을 변경할 때마다 `plugin-manifest.json`의 `version`(및 해당 스킬의 `metadata.version`)을 새로 올려야 합니다. Claude Code는 버전이 바뀔 때만 설치된 플러그인을 업데이트하며, 그렇지 않으면 검사가 실패합니다. 배포 패키지에서 한글은 `skills/<skill>/references/ko/` 아래에서만 허용됩니다. 이 README를 변경하면 같은 커밋에서 번역본도 갱신해야 하며, 테스트가 번역본이 같은 구조를 유지하는지 확인합니다.
