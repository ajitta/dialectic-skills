# Dialectic Skills (`dia`)

[English](README.md) | **한국어** | [日本語](README.ja.md) | [简体中文](README.zh-CN.md)

웹사이트: [ajitta.github.io/dialectic-skills](https://ajitta.github.io/dialectic-skills/)

추론과 검토를 위한 스킬 열세 개를 하나의 플러그인에 담았습니다. Agent Skills를 불러오는 모든 어시스턴트, 즉 Claude(웹, 데스크톱, 모바일, Claude Code), Codex, ChatGPT에서 수정 없이 실행되도록 작성했습니다. 패키지는 지침(Markdown, YAML, JSON)으로만 이루어져 있으므로 도구가 없는 채팅에서도 모든 스킬이 작동합니다. 스킬 파일은 영어로 작성되어 있으며, 각 스킬은 사용자가 쓴 메시지의 언어로 답합니다. 스킬은 메시지가 `dia`나 스킬의 전체 이름으로 시작하거나 스킬을 명시적으로 선택할 때만 시작되며, 일반 문장으로 한 요청으로는 어떤 스킬도 시작되지 않습니다. 휴대폰에서는 `dia`만 입력하면 됩니다. 라우터 스킬(`dia-router`)이 스킬 목록을 보여 주고, `dia` 뒤에 스킬의 이름을 붙이면 그 스킬이 시작되며, `dia` 뒤에 요청을 쓰면 알맞은 스킬을 고릅니다.

| 스킬 | 하는 일 | 시작 방식 |
|---|---|---|
| `dia-skopos` | 작업을 시작하기 전에: 요청하신 것을 어떻게 읽었는지와 그 일이 어떤 결과를 위한 것이라고 보는지를 보여 주고, 사용자만 정할 수 있는 것만 나열한 뒤, 요청한 것을 만들지 아니면 그 결과를 위해 일할지 묻습니다. 그런 다음 사용자의 답을 기다립니다. | `dia-skopos …` 또는 `dia skopos …`; 일반 `dia <request>`로는 선택되지 않음 |
| `dia-elenchus` | 플라톤의 엘렝코스(논박술): "X란 무엇인가?"를 묻고, 한 번에 한 질문씩 전제에 합의하며, 모순을 드러냅니다. 수정할 때마다 그것이 사용자의 새로운 생각이 됩니다. 대개 아포리아로 끝나며, 조언은 하지 않습니다. | `dia-elenchus …`, `dia elenchus …`, 또는 `dia <request>` |
| `dia-quaestio` | 현대적인 소크라테스식 질문을 한 번에 하나씩 던진 뒤, 사용자의 선택지와 표시를 붙인 최대 세 개의 제안, 기준에 따른 수렴, 결론, 요약서를 제시합니다. 구현은 하지 않습니다. | `dia-quaestio …`, `dia quaestio …`, 또는 `dia <request>` |
| `dia-reductio` | 귀류법: 어떤 입장이 기대는 모든 것을 나열하고 말하지 않은 전제를 표시한 뒤, 엄격한 모순(어떤 진술과 그 정확한 부정)을 찾고, 빠져나갈 길을 하나하나 시험해 자기라면 어느 길을 택할지 밝힙니다. | `dia-reductio …`, `dia reductio …`, 또는 `dia <request>` |
| `dia-negative` | 내부 비판(아도르노의 내재적 비판보다 좁은 의미)을 한 번에 수행합니다: 대상 자신의 기준, 사례와 "빠져나가는 것"을 갖춘 엄격한 간극, 반증 조건을 붙인 실제 작동 목적, 억지 종합 없는 선택지. | `dia-negative …`, `dia negative …`, 또는 `dia <request>` |
| `dia-warrant` | 툴민의 논거(warrant): 이유에서 결론으로 가는 각 단계가 기대는, 대개 말하지 않은 규칙과 그런 단계가 받을 수 있는 질문을 짚고, 질문에는 기억이 아니라 증거로 답한 뒤, 결론에 얼마나 기댈 수 있는지 말합니다. 약한 뒷받침과 거짓을 구분합니다. | `dia-warrant …`, `dia warrant …`, 또는 `dia <request>` |
| `dia-conjecture` | 라카토슈의 증명과 반박을 "모든 / 언제나 / 절대" 주장에 적용합니다: 논증을 번호 붙은 단계로 놓고, 반례를 검토 과정과 함께 내놓으며(사용자의 자료부터), 빠진 조건을 주장 안에 넣는 수선을 한 뒤, "모든"이 버티는지와 그 주장에 기대던 것이 어떻게 되는지 말합니다. | `dia-conjecture …`, `dia conjecture …`, 또는 `dia <request>` |
| `dia-counterplan` | 메이슨의 변증법적 탐구를 계획이나 결정에 적용합니다: 핵심 가정, 가정마다 그럴듯한 반대 가정과 어느 쪽이 참인지 보여 줄 것, 같은 사실 위에 세운 대안 계획을 제시한 뒤, 지금이라면 어느 길을 택할지와 무엇이 그 판단을 바꿀지 말합니다. 양쪽을 모두 자기가 썼다고 밝힙니다. | `dia-counterplan …`, `dia counterplan …`, 또는 `dia <request>` |
| `dia-emend` | 직전 답변이나 초안을 한 차례 검토합니다: 사실 오류, 논리적 비약, 누락된 요구 사항, 반복. 확인된 결함만 고칩니다. | `dia-emend …`, `dia emend …`, 또는 `dia <request>` |
| `dia-ratchet` | 검토 라운드를 반복하되, 외부 근거(검색, 도구 실행, 사용자가 준 자료)만 인정하고 어시스턴트 자신의 재도출은 인정하지 않습니다. 확인을 통과한 항목은 고정합니다. 퇴행, 결함 0건, 검증 수단 소진, 고정점 도달, `--max N`(기본값 3) 중 하나에 이르면 멈춥니다. | `dia-ratchet …` 또는 `dia ratchet …`; 일반 `dia <request>`로는 선택되지 않음 |
| `dia-adjudicate` | 사람이나 다른 어시스턴트가 어떤 글에 대해 쓴 보고서(비판, 리뷰, 검증 보고서)를 판정합니다. 글의 주장과 보고서의 모든 지적을 출처와 대조해 항목마다 판정을 내리고, 그 판정들이 글의 결론에서 무엇을 남기는지와 어느 보고서도 제기하지 않은 것을 말한 뒤, 자기 판정이 틀렸을 수 있는 곳을 나열합니다. | `dia-adjudicate …` 또는 `dia adjudicate …`; 일반 `dia <request>`로는 선택되지 않음 |
| `dia-regula` | 모델이 읽고 따를 글(스킬 파일, 에이전트 프롬프트, 에이전트 지침 파일)을 네 가지 규칙으로 점검하거나 씁니다: 조건과 대안을 품은 하나의 식인 문단, 뜻한 만큼만 좁은 범위 단어, 저마다 이유가 붙은 더 적은 지시, 한 대상에 한 이름. 검토만 요청하면 위반 사항을 나열하고, 사용자가 고를 때까지 아무것도 바꾸지 않습니다. | `dia-regula …`, `dia regula …`, 또는 `dia <request>` |
| `dia-techne` | 그 분야 최고 실무자처럼 요청을 그 요청이 위한 결과까지 가져갑니다. 요청한 것을 거기에 이르는 다른 방법들과 비교하고, 결과에 필요한 것을 만들고, 어시스턴트가 아닌 것으로 확인받습니다. 되돌릴 수 없는 단계 앞에서는 멈춥니다. | `dia-techne …` 또는 `dia techne …`; 일반 `dia <request>`로는 선택되지 않음 |
| `dia-router` | 방법이 아니라 짧은 진입점입니다. `dia`는 메뉴를 보여 주고, `dia reductio …`는 이름으로 스킬을 시작하며, `dia <request>`는 알맞은 스킬을 골라 어떤 스킬인지 밝힙니다. 일반 요청으로는 `dia-skopos`, `dia-ratchet`, `dia-adjudicate`, `dia-techne`를 시작하지 않습니다. | 첫 단어를 `dia`로 |

## 빠른 시작

Claude Code:

```
/plugin marketplace add ajitta/dialectic-skills
/plugin install dia@dialectic-skills
```

Codex CLI:

```
codex plugin marketplace add ajitta/dialectic-skills
codex plugin add dia@dialectic-skills
```

claude.ai(웹): Customize › Plugins › Add › Add marketplace에 `ajitta/dialectic-skills`를 입력한 뒤, Discover › `dia` › Add를 선택합니다. 웹과 모바일 앱에서 쓸 수 있습니다. 자세한 단계는 아래에 있습니다.

그런 다음 이렇게 입력해 봅니다: `dia reductio 재택근무는 언제나 생산성을 높인다.`

## 설치

**어디서 설치하느냐에 따라 dia가 보이는 곳이 달라집니다.** 웹(claude.ai, chatgpt.com)에서 설치하면 계정에 저장되어 웹과 모바일 앱에 나타납니다. 데스크톱 앱(Claude 데스크톱, ChatGPT 데스크톱 앱의 Codex)에서 설치하면 그 컴퓨터에만 남습니다. 모든 곳에서 쓰려면 웹에서 한 번, 그리고 쓰는 데스크톱 앱마다 한 번씩 설치하세요. 저장소 소유자도 이렇게 쓰고 있습니다.

### claude.ai 웹과 Claude 데스크톱

1. Settings › Capabilities에서 **Code execution and file creation**을 켭니다. dia 스킬은 코드를 실행하지 않지만, 스킬 기능 자체에 이 설정이 필요합니다.
2. **마켓플레이스 추가.** Customize › Plugins › Add › Add marketplace를 열고 다음을 입력합니다.

   ```
   ajitta/dialectic-skills
   ```

   Git URL `https://github.com/ajitta/dialectic-skills.git`을 넣어도 되고, Claude 데스크톱에서는 로컬 폴더(이 저장소를 클론한 폴더)도 지정할 수 있습니다. 직접 타이핑하지 말고 복사해서 붙여 넣으십시오. `dialectric`처럼 철자가 틀리면 "Repository not found"로 실패합니다.
3. **플러그인 추가.** 마켓플레이스를 추가한 것만으로는 아직 아무것도 설치되지 않습니다. Customize › Plugins에서 Discover를 열고 `dia`(Dialectic Skills)를 선택한 뒤 Add를 누릅니다.
4. **확인.** 메시지 입력창에 `/dia`를 입력합니다. `dia:dia-adjudicate`부터 `dia:dia-warrant`까지 열네 개 항목(스킬 열세 개와 `dia:dia-router`)이 나타나야 합니다. 업데이트는 마켓플레이스를 통해 받습니다(Check for updates 또는 Sync automatically).

2·3단계 대신 플러그인을 업로드할 수도 있습니다. Customize › Plugins › Add › Upload plugin에서 최신 릴리스의 [`dialectic-skills.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills.zip)을 올립니다. Customize › Skills가 아니라 Customize › Plugins를 사용해야 합니다. Skills 화면은 플러그인 매니페스트가 들어 있는 zip을 거부합니다. 업로드한 플러그인은 스스로 업데이트되지 않으므로, 새 릴리스가 나올 때마다 다시 업로드해야 합니다.

**Claude 데스크톱:** 같은 Customize › Plugins 화면이지만 그 컴퓨터에만 설치됩니다. 저장소 소유자가 확인한 바로는, Claude 데스크톱에서 추가한 플러그인은 모바일 앱에 나타나지 않았고, claude.ai에서 추가한 플러그인은 Claude 데스크톱에 나타나지 않았습니다. 둘 다 쓴다면 양쪽에 각각 설치하세요.

### Claude 모바일 (iOS, Android)

따로 설치할 필요가 없습니다. claude.ai(웹)에서 추가한 플러그인은 계정에 저장되어 모바일 앱에 자동으로 나타납니다. Claude 데스크톱에서 추가한 것은 나타나지 않습니다. 모바일의 `/` 메뉴에는 플러그인 스킬이 표시되지 않습니다. 가장 짧은 방법은 메시지를 `dia`로 시작하는 것입니다(호출 방법 참고). 이름을 끝까지 입력해도 됩니다. 예: `/dia-quaestio`, 또는 `dia-quaestio`로 시작하는 메시지.

### Claude Code

```
/plugin marketplace add ajitta/dialectic-skills
/plugin install dia@dialectic-skills
```

- 업데이트: `/plugin marketplace update dialectic-skills`를 실행한 뒤 플러그인을 업데이트합니다(또는 해당 마켓플레이스의 자동 업데이트를 켭니다).
- 제거: `/plugin uninstall dia@dialectic-skills`.
- claude.ai에서 추가한 플러그인은 같은 계정으로 로그인하면 Claude Code에도 동기화됩니다. 명령줄에서 다시 설치하지 마십시오.
- 카탈로그를 통해 설치하려면: `/plugin marketplace add ajitta/claude-plugins`를 실행한 뒤 `/plugin install dia@ajitta`를 실행합니다. 코드는 같고 설치 이름만 다릅니다.

### Codex CLI와 IDE

```
codex plugin marketplace add ajitta/dialectic-skills
codex plugin add dia@dialectic-skills
```

- 업데이트: `codex plugin marketplace upgrade`로 마켓플레이스를 갱신하고, `codex plugin list`로 설치된 버전을 확인합니다.
- 플러그인 없이 쓰려면: `skills/dia-<x>/` 폴더를 `~/.agents/skills/`에 복사합니다. 이렇게 복사한 스킬의 이름은 `$dia:dia-<x>`가 아니라 `$dia-<x>`입니다.

### ChatGPT 데스크톱(Codex 포함)과 모바일

방법은 두 가지입니다. 웹과 모바일에는 첫 번째를, 데스크톱 앱에는 두 번째를 쓰세요. 저장소 소유자는 둘 다 씁니다.

1. **웹에서 zip 업로드(웹과 모바일):** 최신 릴리스에서 [`dialectic-skills-openai.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills-openai.zip)을 내려받아 chatgpt.com의 플러그인 zip 업로드로 올립니다. 플러그인이 계정에 저장되므로 ChatGPT 웹과 모바일에 나타납니다. 이 zip에는 ChatGPT용 목록 정보(설명, 시작 프롬프트, 로고)가 들어 있습니다. 업로드한 플러그인은 스스로 업데이트되지 않으므로, 새 릴리스가 나올 때마다 다시 올려야 합니다.
2. **데스크톱 앱에서 마켓플레이스 추가(이 컴퓨터에서만):** Codex는 ChatGPT 데스크톱 앱에 포함되어 있습니다. GitHub 저장소(`ajitta/dialectic-skills`), Git URL(`https://github.com/ajitta/dialectic-skills.git`), 로컬 폴더(이 저장소를 클론한 폴더) 중 하나로 마켓플레이스를 추가하고, 그 플러그인 목록에서 `dia`를 선택해 설치합니다. 데스크톱 앱의 로컬 Codex 폴더에 설치될 뿐 계정에 저장되지 않으므로, 모바일과 웹에는 나타나지 않습니다. 업데이트는 마켓플레이스를 통해 받습니다.

Business와 Enterprise 워크스페이스에서는 관리자가 워크스페이스 전체에 플러그인을 추가할 수도 있습니다(zip 업로드 또는 GitHub 마켓플레이스 가져오기).

### Windows

위의 모든 경로는 Windows에서도 작동합니다. 스킬에는 스크립트가 없으므로 Python이나 셸 설정이 필요하지 않습니다.

## 호출 방법

방법은 세 가지이며, 모든 환경에서 적어도 한 가지는 지원합니다. 이 중 어느 방법으로도 시작하지 않은 메시지는 스킬의 방법을 말로 요청하더라도("…에 귀류법을 적용해 주세요") 어떤 dia 스킬도 시작하지 않습니다. 1.x에서는 스킬 아홉 개가 이런 요청으로도 시작되었습니다.

1. **라우터: 메시지를 `dia`로 시작하기.** `dia`만 입력하면(또는 `dia help`, `dia menu`, `dia ?`) 스킬 목록이 나옵니다. `dia reductio <your text>`(`dia dia-reductio …`도 가능)는 그 스킬(여기서는 `dia-reductio`)을 시작합니다. `dia <your text>`는 설명이 알맞은 스킬을 골라 한 줄로 밝힌 뒤 실행합니다. 두 스킬이 비슷하게 맞으면 묻고, 맞는 스킬이 없으면 dia 스킬 없이 답합니다. 일반 요청으로는 `dia-skopos`, `dia-ratchet`, `dia-adjudicate`, `dia-techne`를 시작하지 않고, 보낼 형식(예: `dia ratchet --max 2 <draft>`)을 알려 줍니다. 휴대폰에서 가장 빠른 방법입니다. 세 글자에 하이픈도 없습니다.
2. **메시지에 이름 적기.** 메시지를 스킬의 전체 이름으로 시작합니다: `dia-skopos …`, `dia-emend …`, `dia-ratchet …`, `dia-adjudicate …`, `dia-techne …` 등 열세 개 모두 같습니다. 1.2.0부터는 Codex에서 `$` 없이, ChatGPT에서 `@` 없이(모바일 앱에서 소유자 확인) 이렇게 시작할 수 있습니다.
3. **명시적 선택.** 환경마다 표기법이 다릅니다.

| 환경 | 문법 | 예시 |
|---|---|---|
| claude.ai, Claude 데스크톱, Claude Code | `/dia:dia-<x>` | `/dia:dia-reductio` |
| Claude 모바일 | `/dia-<x>` 또는 `/dia:dia-<x>`를 끝까지 입력(`/` 메뉴에는 표시되지 않음) | `/dia-quaestio`, `/dia:dia-quaestio` |
| Codex (플러그인) | `$dia:dia-<x>` 뒤에 공백 | `$dia:dia-skopos 백업 스크립트 작성해줘` |
| Codex (복사한 폴더) | `$dia-<x>` | `$dia-emend` |
| ChatGPT | `@` 입력 후 스킬 선택 | `@dia-negative` |

`dia` 뒤에서는 스킬의 전체 이름(`dia-`는 있어도 없어도 됨)만 스킬을 고르며, 줄인 이름으로는 고르지 않습니다. 문장의 일부로 읽히는 이름(`dia negative feedback on my draft?`)은 요청으로 읽으며, `dia`가 그 요청에 알맞은 스킬을 고릅니다.

### 옵션

옵션은 스킬 이름이나 `dia` 선택어 뒤에 플래그로 쓰거나 일반 문장으로 쓸 수 있으며, 언어는 상관없습니다.

- `--target=user|claude|text|all` (`dia-negative`): 검토 대상을 정합니다. `user`는 사용자가 제시한 주장, `claude`는 어시스턴트 자신의 이전 답변(어떤 어시스턴트든 해당), `text`는 붙여 넣은 텍스트, `all`은 이 중 존재하는 모든 것입니다. 플래그가 없으면 스킬이 대상을 추론하고 첫 줄에 밝힙니다.
- 플래그 없음 (`dia-reductio`, `dia-warrant`, `dia-conjecture`, `dia-counterplan`): 각 스킬이 무엇을 대상으로 삼았는지 첫 줄에 밝힙니다. 어시스턴트 자신의 이전 답변을 검토받으려면 말로 요청하세요(`dia reductio 직전 답변을 검토해 주세요`).
- 질문받기 (`dia-warrant`): 질문해 달라고 요청하면, 사용자가 각 부분을 직접 채우도록 한 번에 한 질문씩 묻고, 어시스턴트는 마지막에 판단합니다.
- `--max N` (`dia-ratchet`): 라운드 상한이며, 기본값은 3입니다.
- 모드와 깊이 (`dia-quaestio`): `develop`(기본값) 또는 `stress`("허점을 찔러 주세요"), 그리고 `quick`, `standard`(기본값), `deep`.
- 기준 (`dia-emend`, `dia-ratchet`): 이름 뒤에 오는 모든 내용이 기준이 됩니다. 예: `dia-emend — 숫자 확인해줘` 또는 `dia-emend 어조 위주로`.

### 한 대화 동안 지킬 규칙 하나

dia 스킬은 작업 하나에 불러 쓰는 방법이며, 대화 전체에 걸친 규칙을 정해 주는 스킬은 없습니다. 그런 규칙이 필요하면 대화를 시작할 때 아래와 같은 문장을 붙여 넣으세요. 이 문장은 확인을 부탁한 답이 어시스턴트의 기억에 기댄 것일 때 그렇다고 밝히게 합니다.

```
이 대화 동안: 내가 뭔가를 확인하거나 검토해 달라고 할 때만, 네 답이 기억에 기댄 것이면 그렇게 말하고 기억을 '확인됨'이라고 하지 마. 확인하지 않은 것도 말해줘. 지나가며 묻는 흔한 사실에는 이런 말을 붙이지 마.
```

이 규칙은 그 대화에서만 유지되므로, 새 대화에서는 다시 붙여 넣어야 합니다.

## 스킬 안내와 예시

이 스킬들을 쓰는 데 철학 지식은 전혀 필요 없습니다. 각 스킬은 사람들이 오래전부터 써 온 생각하는 방법 하나를, 어시스턴트가 한 단계씩 따라가는 절차로 옮겨 놓은 것입니다. 아래에서는 스킬마다 쉬운 말로 된 설명, 직접 해 볼 프롬프트, 그리고 실제 세션을 줄여서 보여 드립니다.

세션은 이 플러그인을 설치한 Claude Code에서 실행했고, 대화 예시에 나오는 사용자 답변은 미리 써 둔 대본이 아니라 시뮬레이션한 사용자가 그때그때 답한 것입니다. 각 세션 아래의 메모에 기록한 버전과 모델이 적혀 있습니다. 한국어로 실행했다고 밝힌 세션 말고는, 아래 대화는 영어로 실행한 것을 번역해 실었습니다. 실행할 때마다 표현은 조금씩 달라집니다. 모든 프롬프트는 어떤 언어로 써도 작동하며, 어시스턴트는 사용자가 쓴 언어로 답합니다.

**하고 싶은 일로 스킬 고르기**

| 이런 걸 하고 싶다면… | 쓸 스킬 |
|---|---|
| 일을 시작하기 전에 어시스턴트가 과제를 제대로 이해했는지 확인하기 | `dia-skopos` |
| 어떤 단어나 생각으로 내가 정말 무엇을 뜻하는지 알아내기 | `dia-elenchus` |
| 막연한 아이디어를 선택지와 계획으로 바꾸기 | `dia-quaestio` |
| 어떤 주장이 앞뒤가 맞는지 확인하기 | `dia-reductio` |
| 구호, 정책, 약속이 스스로 한 말을 지키는지 보기 | `dia-negative` |
| 결론을 받치는 이유가 실제로 얼마나 튼튼한지 보기 | `dia-warrant` |
| "언제나", "절대" 규칙을 반례로 시험하기 | `dia-conjecture` |
| 결정하기 전에 다른 계획을 가장 강하게 옹호하는 주장 들어 보기 | `dia-counterplan` |

| 모델이 뜻한 대로 따르도록 프롬프트, 스킬, 에이전트 파일을 쓰거나 점검하기 | `dia-regula` |
| 그 분야 최고 실무자처럼 일을 하고, 어시스턴트가 아닌 것으로 결과를 확인하기 | `dia-techne` |
| 어떤 스킬을 쓸지 모르겠을 때, 또는 휴대폰으로 입력할 때 | `dia` (`dia-router`) |

### dia-skopos: 일을 시작하기 전에 과제 합의하기

**쉽게 말하면.** 좋은 시공업자는 공사를 시작하기 전에 일을 함께 짚어 봅니다. 이렇게 이해했다, 이게 무엇을 위한 일이라고 본다, 이건 고객님만 정할 수 있다고요. `dia-skopos`는 어시스턴트가 바로 그렇게 하게 한 뒤, 한 가지를 묻게 합니다. 요청하신 것을 만들까요, 아니면 원하시는 결과를 위해 일할까요? 그리고 짐작으로 진행하는 대신 사용자의 답을 기다립니다.

**이럴 때 쓰세요.** 요청은 짧은데 원하는 것이 그 말보다 클 때입니다. 축사, 계획, 테스트, 중요한 사람에게 보내는 이메일 같은 경우입니다. 답이 하나로 뻔한 간단한 질문이라면 **쓰지 않아도 됩니다**.

**해 보기:**

```
dia-skopos 동생 결혼식에서 할 짧은 축사를 써 주세요.
```

**세션은 이렇게 진행됩니다** (줄임):

> **어시스턴트:**
> **만들려는 것:** 2~3분 정도에 직접 하실 수 있는 축사입니다. … 따뜻함과 가벼운 유머를 섞고, 자기소개로 시작해 동생분에 대한 개인적인 이야기 하나를 들려주고, 배우자를 맞이한 뒤 건배로 끝냅니다. 제 해석은 "짧은"을 말로 3분 미만으로 보고 어조를 섞는다는 점을 덧붙입니다. 맡으신 역할이 없다면 공식 역할(베스트맨, 주례)은 뺍니다. …
> **결과(제 해석):** 동생분과 배우자가 사용자께 정말로 이해받고 축하받는다고 느끼고, 하객들이 두 사람에게 마음을 열며, 사용자는 두려움 대신 자신감을 갖고 일어서는 것입니다. 이것을 가장 크게 제한하는 것은 사용자만 가진 재료입니다. 실제 이름, 진짜 이야기, 그리고 여러 사람 앞에서 말하는 것이 얼마나 편한지입니다.
> **사용자만 정하실 수 있는 것**(제 기본값과 함께): 이름, 이야기 한두 가지, 어조, 역할과 분량 제한, 피할 것.
> **선택.** **"요청대로":** 지금 가진 것으로 최대한 다듬은 짧은 결혼식 축사. 보내거나 쓰는 것은 없습니다. **결과를 위해(제안):** "동생 결혼식에서 동생과 배우자가 정말로 축하받는다고 느끼고, 제가 자신 있게 할 수 있는 축사를 하도록 도와주세요." 이 경우 글로 쓴 축사는 거기에 이르는 여러 방법 중 하나가 됩니다. …
> 제 문장이 맞지 않으면 원하시는 결과를 직접 말씀해 주세요. "진행"이라고만 하시면 제 문장대로 하고, "요청대로"라고 하시면 축사만 씁니다.
>
> **나:** dia-techne 진행해 주세요. 동생 이름은 민호이고, 사라와 결혼해요. 저는 베스트맨을 맡았어요. 민호가 저보다 어린데도 저한테 자전거 타는 법을 가르쳐 줬어요. 따뜻하게, 가벼운 농담 하나 넣어서, 3분 정도로요. 제가 원하는 건 하객들이 한 번 웃고 민호가 뭉클해하는 거예요.
>
> **어시스턴트:** **제가 목표로 삼은 결과(사용자의 것):** 하객들이 한 번 웃고 민호가 뭉클해하는 것. 아래의 모든 것을 그 두 순간으로 판단했습니다. … 전체 원고와 요점만 적은 큐 카드로 말하는 방식을 비교했습니다. 큐 카드가 더 자연스럽게 들릴 수 있지만, 민호를 뭉클하게 할 문장은 표현이 정확해야만 통하고 긴장하면 흐려지기 쉽습니다. 그래서 전체 원고를 썼습니다. … **웃음:** 동생이 형을 가르친다는 것이 요청하신 대로 유일한 농담입니다. … **뭉클한 순간:** "내가 잡고 있어"가 마지막에 돌아와, 이번에는 민호에게 되돌려 주는 말이 됩니다. … 하객들이 한 번 웃고 민호가 뭉클해할지는 결혼식 날이 되어야 알 수 있습니다. 그 전에는 위의 소리 내어 읽어 보는 시험이 가장 좋은 확인입니다.
> *(4.2.0, Claude Opus 5.5에서 기록했습니다.)*

**팁**

- **원하는 것을 자기 말로 한 문장으로 말하세요**("제가 원하는 건 …"). 그러면 일은 그 문장을 위해 이루어지고, 이것이 결과를 좌우하는 가장 큰 단일 요인입니다. 저희가 돌려 본 실행에서 같은 요청도 사용자가 이 문장을 덧붙이면 확연히 더 나은 결과에 이르렀습니다. 그냥 "진행"이라고만 하면 어시스턴트의 추측을 받아들이게 되는데, 요청이 정확할수록 그 추측은 원하는 것보다 좁은 경우가 많습니다.
- "요청대로"라고 하면 요청에서 이름 붙인 것만 하되, 그것을 가장 잘 만드는 실무자가 만들듯 만듭니다. 수정 사항과 "진행"을 함께 보내면 수정된 요청을 승인한 것으로 봅니다.
- "좋아 보여요", 질문, 아무 답 없음은 승인으로 치지 않습니다. 어시스턴트는 계속 기다리며 과제는 조금도 하지 않습니다.
- 승인하면 `dia-techne`가 설치된 곳에서는 일이 그쪽으로 넘어갑니다. 확실히 하려면 답을 `dia-techne`로 시작하세요. 검토 범위는 그 과제 하나입니다. 새 과제에서도 같은 확인을 받고 싶다면 다시 `dia-skopos`로 시작하세요.

### dia-elenchus: 내가 정말 무엇을 뜻하는지 알아내기

**쉽게 말하면.** 플라톤의 대화편에서 소크라테스가 쓰는 방법입니다. 사용자가 어떤 것이 무엇이라고 생각하는지 말합니다("좋은 교사란…"). 어시스턴트는 반박하거나 자기 의견을 내놓지 않습니다. 대신 구체적인 사례를 하나씩 묻는데, 그 사례들은 사용자의 대답이 스스로 내린 정의와 조금씩 어긋나도록 골라져 있습니다. 그러면 사용자는 자기 말로 정의를 고칩니다. 결국 막다른 곳에 이르는 경우가 많은데, 이 상태를 그리스어로 **아포리아**라고 합니다. 여기서 막히는 것은 실패가 아니라 하나의 결과입니다. 이제 어느 부분을 모르는지 정확히 알게 되었으니, 잘못된 가정 위에 무언가를 쌓아 올리지 않게 됩니다.

**이럴 때 쓰세요.** 뜻이 뻔해 보이지만 실제 결정을 좌우하는 단어에 기대고 있을 때입니다. 좋은 교사, 공정한 분배, 성공한 프로젝트, 건강한 관계 같은 것들입니다. 조언을 얻는 용도로는 **맞지 않습니다**. 대화하는 동안에는 조언을 전혀 하지 않습니다.

**해 보기:**

```
dia elenchus 저는 좋은 교사란 학생들이 시험에서 높은 점수를 받게 하는 교사라고 생각합니다.
```

**세션은 이렇게 진행됩니다** (실제 실행, 줄임):

> **어시스턴트:** 우리가 살펴볼 것은 **좋은 교사**입니다. 말씀하신 대로라면, 좋은 교사란 학생들이 시험에서 높은 점수를 받게 하는 교사입니다. 어떤 교사가 학년이 시작되기 전부터 이미 최상위 점수를 받던 학생들의 반을 맡았다고 해 봅시다. 그 교사는 거의 아무것도 하지 않고, 학생들은 학년 말에도 똑같이 높은 점수를 받습니다. 그 사람은 좋은 교사입니까?
>
> **나:** 음, 그렇진 않네요. 어차피 높은 점수를 받았을 테니까요. 점수가 그 교사 덕분에 올라가는지가 더 중요한 걸까요?
>
> **어시스턴트:** ① 좋은 교사란 학생들이 시험에서 높은 점수를 받게 하는 교사다(정의) ② 거의 아무것도 하지 않는 교사는, 학생들이 어차피 높은 점수를 받았을 경우 좋은 교사가 아니다(동의함). 그러니 ①과 ②는 함께 성립할 수 없습니다. 사용자는 ①을 바꾸는 쪽을 택했습니다. 바뀐 점: "시험에서 높은 점수" → "점수가 그 교사 덕분에 올라간다". … 어떤 교사가 시험 형식과 답을 찾는 요령을 반복해서 훈련시켜 점수를 올렸다고 해 봅시다. 시험이 끝나고 한 달 뒤, 학생들은 거의 아무것도 기억하지 못합니다 … 그 사람은 좋은 교사입니까?
>
> *…잘못 만들어진 시험, 겁을 주며 가르치는 교사, "점수는 거의 안 올랐지만 아이가 수학을 좋아하게 됐다"는 사용자 딸의 수학 선생님, 어차피 잘했을 반…*
>
> **나:** 대충 말해 보면, 좋은 교사란 그 교사가 없었을 때보다 학생들이 진짜로 무언가를 배우고 계속 배우고 싶어 하게 만드는 교사예요. 그런데 과외를 받는 아이들은 그걸 도대체 어떻게 가려낼 수 있을지 솔직히 모르겠어요. 거기서 막힌 것 같아요.
>
> *…이 정의는 한 번의 시험은 통과하지만, 서른 명 중 세 명에게만 닿는 교사에서 무너집니다. "학생 대부분"으로 고친 정의는, 교사가 달리 기댈 사람이 없는 세 명에게만 닿는 반에서 무너집니다…*
>
> **나:** 아니요, 그건 틀렸어요. 그 교사는 좋은 교사예요. 그 세 명이야말로 교사가 필요했던 아이들이잖아요. 그러니 "학생 대부분"도 안 맞아요. 오히려 실제로 그 교사에게 기댄 아이들 쪽에 가깝고, 그래서 또 막혔어요.
>
> **어시스턴트:** … 우리는 좋은 교사가 무엇인지 모른다는 것을 알게 된 것 같습니다. 이건 실패가 아니라 하나의 결과입니다. 이제 어느 부분을 아직 말할 수 없는지 아시니, "시험에서 높은 점수"가 문제를 해결한 것처럼 그 위에 무언가를 쌓지는 않으실 겁니다. … **결과: 아포리아. 이제 좋은 교사에 대해 붙들고 있는 정의는 하나도 없으며, 가져갈 질문은 어떤 학생들에게 생긴 차이가 중요한지, 그리고 왜 그런지입니다.** *(이어서 기록이 나옵니다. 정의 여덟 개와 각각이 무너진 과정, 동의한 전제 열 개, 생겨난 생각들, 이제 모른다는 것을 알게 된 것, 다음 정의가 해내야 할 일(예: "⑩ 나머지 학생들은 다른 도움을 받았을 때, 달리 기댈 사람이 없는 세 명에게 닿는 교사를 포함할 것"), 검토하지 않은 것, 확인할 것, 가져갈 질문)*
> *(5.1.0에서 Claude Opus 5.5, effort medium으로 기록했습니다. 사용자는 시뮬레이션했습니다.)*

**팁**

- 짧고 솔직한 대답이 가장 좋습니다. "잘 모르겠어요"도 훌륭한 대답입니다.
- 먼저 당신 자신의 상황에서 사례를 묻습니다(당신의 팀, 지난달, 관련된 사람들). 실제 사례에서 가장 많은 것이 드러나며, 당신의 사례로 더 시험할 것이 없을 때 지어낸 사례로 넘어갑니다.
- 어시스턴트가 표현이 "바뀌었다"고 짚는 것은 말이 어떻게 달라졌는지 보여 줄 뿐입니다. 무엇을 남길지는 사용자가 정합니다.
- 언제든 "그만"이라고 하면 기록을 받습니다. 그다음 제안을 원하면 요청하세요. 어시스턴트는 소크라테스식 부분이 끝났다고 밝히고, 자기 아이디어에는 자기 것이라고 표시합니다.

### dia-quaestio: 막연한 아이디어를 키운 뒤 결정하기

**쉽게 말하면.** 선택지를 건네기 전에 좋은 질문부터 던지는 코치입니다. 먼저 한 번에 하나씩 질문해서 사용자가 원하는 것과 아는 것을 분명히 합니다(소크라테스식 질문). 그다음 사용자가 선택지를 내놓고, 어시스턴트가 몇 가지를 보태고, 사용자가 무엇이 중요한지 고르면, 결론과 바로 실행에 옮길 수 있는 짧은 요약서로 마무리합니다. `dia-elenchus`와 달리, 질문을 마친 뒤에는 제안도 합니다.

**이럴 때 쓰세요.** 목표는 있는데 아직 계획이 없을 때입니다. 부업, 진로 변경, 작은 프로젝트, 여행 같은 경우입니다. 실제로 무언가를 만드는 용도로는 **맞지 않습니다**. 코드를 쓰거나 행동에 옮기는 일은 하지 않습니다.

**해 보기:**

```
dia quaestio 짧게 진행해 주세요: 주말에 부수입을 좀 벌고 싶습니다.
```

**세션은 이렇게 진행됩니다** (실제 실행, 줄임):

> **어시스턴트:** 질문 4개 정도로 짧게 진행하겠습니다. … 제가 이해한 생각은 이렇습니다. 지금 하시는 일과 별개로, 주말을 이용해 부수입을 벌고 싶으시다는 것입니다. … 얼마를 벌고 싶은지, 어떤 일을 할지, 그 돈을 어디에 쓸지는 말씀하지 않으셔서 열어 두었습니다. 맞습니까, 아니면 제가 의도하지 않은 걸 가정했나요?
>
> **나:** 네, 맞아요. 평일에는 사무실에서 풀타임으로 일해요. 이 돈은 내년 여름 여행 경비예요. 저축에 손대지 않으려고요.
>
> *…한 달에 약 $300, 주말마다 약 8시간, 주로 토요일…*
>
> **어시스턴트:** 거의 다 왔습니다. 질문 두 개만 더 하겠습니다. 이미 할 줄 아는 것 중에, 누군가 돈을 낸 적이 있거나 자주 도와 달라고 부탁하는 것은 무엇입니까?
>
> **나:** 돈을 받아 본 적은 없지만, 사진을 잘 찍고 괜찮은 카메라와 렌즈 두 개가 있어요. 친구들이 제 사진을 늘 칭찬해요.
>
> *…사용자가 자기 선택지(동네 가게 사진, 주말 장터에서 인화본 판매, 공원에서 반려동물 초상 사진), 가장 싼 안, 가장 과감한 안, 아무것도 하지 않는 안, 그리고 두 가지 제한(모르는 사람에게 대면으로 팔지 않기, 저녁 내내 보정하지 않기)을 내놓고, 어시스턴트가 자기 안 세 가지를 보태고(행사 사진가의 보조 촬영, 스톡 사진 라이선스, 토요일 아르바이트), 사용자가 기준 세 가지를 고릅니다. 시작 비용 $200 미만, 무급 보정 작업이 많지 않으면서 약 $300, 일이 즐거울 것…*
>
> **어시스턴트:** **결론: 열려 있음.** 상위 두 안, 곧 동네 가게 사진과 보조 촬영 중 무엇을 먼저 해 볼지 정할 준비가 되셨습니다. 그 전에 한 가지를 확인하세요. 빵집이나 꽃집이 정말 사진에 돈을 낼까요? … **위험한 가정:** 빵집과 꽃집이 사진을 원하고, 사진을 마음에 들어 하는 데서 그치지 않고 돈을 낸다. … **이번 세션에서 시험하지 않은 것:** 반례로 아이디어를 몰아붙이지도, 무엇을 보면 그만두겠는지 묻지도 않았습니다. … **다음 단계:** 계획하신 대로 다음 토요일에 빵집이나 꽃집에 사진 몇 장을 무료로 드리세요. 건네면서, 이런 사진에 매달 돈을 낼 생각이 있는지, 대략 얼마인지 물어보세요.
> *(5.1.0에서 Claude Opus 5.5, effort medium으로 기록했습니다. 사용자는 시뮬레이션했습니다.)*

**팁**

- 얼마나 세게 밀어붙일지 말해 주세요. "짧게", "깊이 있게", 또는 더 혹독한 검증을 원하면 "허점을 찔러 주세요"라고 하면 됩니다.
- 언제든 "마무리"라고 하면 바로 결론과 요약서로 넘어갑니다.
- 결론이 "열려 있음"이면 핵심 가정을 아직 현실에서 시험해 봐야 한다는 뜻이고, 그게 어떤 가정인지는 요약서에 적혀 있습니다.

### dia-reductio: 주장이 앞뒤가 맞는지 확인하기

**쉽게 말하면.** 귀류법, 다른 말로 모순에 의한 증명입니다. 어떤 입장(주장, 계획, 규칙 묶음, 논증)을 말 그대로 받아들여, 그 입장이 기대야 하는 것을 모두 나열하고, 그것들이 한꺼번에 참일 수 있는지 봅니다. 어시스턴트는 자기가 보태야 했던 전제마다 표시합니다. 입장에 꼭 필요한데 아무도 말하지 않은 전제가, 이 스킬이 찾아내는 것 가운데 가장 쓸모 있는 경우가 많기 때문입니다. 모순은 엄격할 때만 인정합니다. 어떤 진술과 그 정확한 부정이 논리, 정의, 계산으로 도출되어야 하며, 도구가 있으면 도구로 돌려 봅니다. 그런 다음 어시스턴트는 자기 판단을 내놓습니다. 빠져나갈 길(약속 하나를 포기하거나, 입장을 꼭 필요한 만큼만 좁히는 것)을 하나하나 같은 방식으로 시험하고, 각 길이 그 입장이 이루려던 것에 무엇을 치르게 하는지 말한 뒤, 자기라면 어느 길을 택할지 밝힙니다. 고친 문구처럼 그 결과물 자체가 필요하면 그것을 써 줍니다.

**이럴 때 쓰세요.** 숫자가 들어간 규칙, 약속, 계획에 기대려는 참인데, 그 전부가 한꺼번에 참일 수 있는지 알고 싶을 때입니다. 공지, 정책, "언제나", "절대", "모든 사람" 같은 말이 들어간 자신만만한 규칙, 또는 변호하기 전의 내 입장 같은 것들입니다. 이유가 그럴듯한 결론을 얼마나 강하게 뒷받침하는지 판단하는 용도로는 **맞지 않습니다**. 그건 `dia-warrant`의 일입니다.

**해 보기:**

```
dia reductio 12월 컵대회 단톡방 공지 올리기 전에 한번 봐주세요. 리그 때처럼 11월 연습 다 나온 애들은 모든 경기 최소 절반 이상 뛰게 해준다는 내용인데, 16명에 8명 출전, 전후반 20분씩이라 딱 맞아서 문제없을 것 같거든요. 부모님들이 출전시간에 민감해서 이대로 올려도 되는지, 아니면 뭐라고 고쳐야 하는지 알려주세요.
```

**세션은 이렇게 진행됩니다** (한국어로 한 실제 실행, 줄임):

> **어시스턴트:** **검토 대상:** 사용자님이 설명해 주신 공지 내용입니다. 공지 원문은 아직 보지 못했습니다. 원문을 붙여 주시면 문구 단위로 다시 보겠습니다.
> **이대로 올리시는 건 권하지 않습니다.** "딱 맞는다"는 건 여유 시간이 0분이라는 뜻입니다. 그래서 약속이 깨질 수 있는 경우가 세 가지 있습니다. 1. 한 경기에서라도 경기장 위 인원이 8명 아래로 줄면 약속을 지킬 수 없습니다. 퇴장, 교체 불가 부상, 경기 단축이 여기에 해당합니다. 2. 골키퍼 한 명이 40분 내내 뛰면 나머지 아이들 몫이 20분이 안 됩니다. 3. 컵대회에 경기당 엔트리 제한이 있으면 엔트리에 못 든 아이는 그 경기를 아예 못 뜁니다. 어떤 경우든 **예외 조항은 꼭 넣으셔야 합니다.** …
> **공지가 전제로 깔고 있는 것:** … 출전 가능 시간: 8자리 × 40분 = **320분** (계산). 약속한 시간: 16명 × 20분 = **320분** (계산). 제가 보탠 전제 ①: 16명 전원이 11월 연습에 다 나왔다. "딱 맞는다"는 말이 이걸 가정하는 것 같습니다. **확인이 필요합니다.** 제가 보탠 전제 ②: 경기 중에 경기장 인원이 줄 수 있다. …
> **모순이 생기는 과정:** 1. 대상 16명이 각각 20분 이상 뛰어야 하니 최소 320분이 필요합니다. (약속 + 전제 ①) 2. 한 경기에서 한 명이 퇴장당해 7명으로 10분을 뛰면, 실제 출전 시간은 310분입니다. (전제 ② + 계산) 3. 320분 이상이 필요한데 310분뿐이라 약속을 지킬 수 없습니다. … 이 모순은 전제 ①과 ②가 둘 다 맞을 때만 성립합니다. … 계산은 손으로 확인했고, 도구는 쓰지 않았습니다.
> **지금 바로 넣으셔도 되는 문구:** "단, 퇴장·부상·경기 단축 등 불가피한 상황이나 대회 규정(엔트리·교체)상 어려운 경우는 예외로 하며, 이때는 다음 경기에서 최대한 보완하겠습니다." …
> **답을 주시면 나머지를 정리해 드릴게요:** 1. **11월 연습에 다 나온 아이가 실제로 몇 명인가요?** 16명이면 위 문제가 그대로 적용됩니다. 15명 이하면 여유가 생겨서 "최소 절반" 표현을 살릴 수 있습니다. 2. **컵대회 엔트리 제한과 교체 규정은 어떻게 되나요?** … 엔트리 제한이 16명보다 적으면 "모든 경기"라는 표현을 고쳐야 합니다. 3. **골키퍼는 하프타임에 교체하실 건가요?** … 4. **"이상"은 일부 아이를 더 뛰게 할 여지를 두려고 쓰신 건가요?** … 5. **대상이 아닌 아이는 어떻게 하실 계획인가요?** …
>
> **나:** 유소년 코치 8년 하면서 출전시간 약속 못 지킨 적 한 번도 없어요, 그건 제가 제일 잘 알아요. 11월 연습은 3일부터 21일까지 화·목·토 9번 했고, 9번 다 나온 애가 14명이에요. 컵대회는 경기마다 명단에 13명까지만 올릴 수 있고, 교체는 경기당 5명까지에 한 번 나간 선수는 다시 못 들어와요. 골키퍼 교체랑 "이상"을 쓴 이유, 연습 빠진 애들 계획은 모르겠어요.
>
> **어시스턴트:** **말씀해 주신 대회 규정을 기준으로 하면, 지금 공지대로는 한 경기도 약속을 지킬 수 없습니다.** 이건 상황이 나빠야 생기는 문제가 아니라, 숫자만으로 정해지는 결과입니다. … 대상은 14명입니다. 경기 명단은 최대 13명입니다. 그래서 매 경기 대상 아이 중 최소 1명은 명단에 못 들고, 출전 시간이 0분이 됩니다.
> 코치님이 8년 동안 출전 약속을 한 번도 어기지 않으셨다는 건 저도 의심하지 않습니다. 다만 그 기록이 이 숫자를 바꾸지는 못합니다. 리그 때는 아마 명단 제한이 없어서 문제가 드러나지 않았을 것 같은데, 이건 제 추측입니다.
> … 교체 5번에 재입장이 안 되면, 한 경기에서 20분 이상 뛸 수 있는 사람은 **최대 13명**입니다. 3명은 40분을 다 뜁니다. 나머지 5자리는 하프타임에 정확히 한 번씩 교체해서 10명이 20분씩 뜁니다. 이건 가능한 경우를 전부 계산해서 확인한 결과입니다. 숫자는 주신 규정 그대로 넣었습니다. … 13명을 모두 20분씩 채우려면 **교체 5번을 전부 하프타임에 써야 합니다.** …
> **고치는 방법:** **A. 약속을 "명단에 든 경기"로 좁히기 (제가 권하는 방법)** … **B. 대회 전체 출전 시간 기준으로 바꾸기** … 1경기만 하고 끝나면 불가능합니다. 토너먼트에서 첫 경기에 탈락하면 지킬 수 없습니다. …
> *…이어서 A의 문안, 그리고 코치만 정할 수 있는 것: 연습에 빠진 아이 2명, 명단에서 빠지는 순서, 하프타임 교체가 5번 안에 들어가는지…*
>
> **나:** 그래도 경기 날엔 보통 두세 명은 빠지잖아요, 그럼 다 뛸 수 있는 거 아니에요? 그리고 컵대회는 12월 12일 토요일에 조별리그 2경기 하고, 조 1위만 13일 일요일 4강에 가요. 하프타임 교체가 5명 안에 들어가는지, 연습 빠진 두 명이랑 명단 빠지는 순서는 모르겠어요.
>
> **어시스턴트:** **"보통 두세 명 빠진다"는 것만 믿고 "모든 경기" 약속을 거는 건 안 됩니다.** 대상 14명 중 1명이라도 그날 안 오면, 경기마다 남은 아이 모두 절반 이상 뛰게 할 수 있습니다. 하지만 14명이 다 오는 날에는 처음부터 지킬 수 없는 약속이 됩니다. 빠지는 2~3명이 연습에 빠졌던 2명이면, 대상 14명은 그대로 다 옵니다. 출전시간에 민감한 부모님들께 하는 약속이 아이들 결석에 달려 있으면 안 됩니다.
> 대신 주신 일정을 보면 **토요일 두 경기를 합쳐서 약속하는 방법**이 있습니다. 이 방법은 대상 14명이 모두 와도 지킬 수 있습니다. … **1경기**: A·B·C 40분, D~M 10명 20분씩. N은 명단에서 빠집니다. **2경기**: N·A·B 40분, D~M 10명 20분씩. C는 명단에서 빠집니다. **결과**: 14명 모두 두 경기 합쳐 40분 이상 뜁니다. 경기 시간 80분의 절반입니다. 이 배정은 직접 계산해서 확인했습니다. 하프타임 교체가 5번 안에 들어간다고 보고, 가장 빡빡한 경우로 잡았습니다. …
> **공지 문안:** "11월 연습(9회)에 모두 참석한 선수는 12일(토) 조별리그 2경기 합산 출전시간이 절반(40분) 이상이 되도록 하겠습니다. 대회 규정상 경기당 명단은 13명, 교체는 5명까지라 경기에 따라 명단에서 빠지는 선수가 있을 수 있습니다. 이 경우 다른 경기에서 더 뛰게 하겠습니다. 13일(일) 4강에 진출하면, 명단에 든 선수는 절반 이상 출전합니다. 단, 부상·퇴장·경기 단축 등 불가피한 경우는 예외로 하겠습니다."
> **정하실 것:** 정하신 것과 상관없이 위 문안은 그대로 쓰실 수 있습니다. 공지에 내용을 더 넣을지만 달라집니다. …
>
> **나:** 아, 연습 빠졌던 두 명이 경기 날에도 잘 빠지니까 결석으로는 해결이 안 되는 거네요, 알겠어요. 말씀하신 문안대로 올릴게요. 고마워요, 이제 됐어요.
> *(스킬의 5.0.0 문구로 Claude Opus 5.5, effort medium에서 기록했습니다. 사용자는 시뮬레이션했습니다.)*

첫 답에서 어시스턴트는 바로 정할 수 있는 것(공지에 예외 조항이 필요하다)을 말하고, 필요한 것을 한 번에 모두 물었으며, 질문마다 그 답이 무엇을 정하는지 붙였습니다. 코치가 8년 동안 약속을 한 번도 어기지 않았다는 말은 아무것도 움직이지 못했고, 어시스턴트는 그 이유를 말했습니다. 결론을 정한 것은 코치가 알려 준 사실(대상 14명, 명단 13명)이었습니다.

**팁**

- 답할 수 있는 것은 답하고, 나머지는 "모르겠어요"라고 하세요. 어시스턴트는 있는 것으로 판단하고, 무엇이 아직 열려 있는지 말합니다.
- 어시스턴트가 몰랐던 사실, 사용자가 받아들이지 않는 전제, 어시스턴트가 잘못 읽은 용어는 그것이 미치는 만큼 정확히 결과를 움직입니다. 경력, 권위, 되풀이는 아무것도 움직이지 못합니다.
- 전제를 빼거나 어떤 단어를 다른 뜻으로 썼다고 하면 입장이 바뀐 것입니다. 처음 말한 입장은 읽은 그대로는 무너진 것이고, 새 입장을 다시 시험합니다.
- 모든 사실에는 어떻게 아는지가 붙습니다. 도구로 돌렸는지, 사용자가 알려 줬는지, 출처 하나인지, 어시스턴트의 기억인지이며, 기억은 결코 '확인됨'이라고 하지 않습니다. 시험하지 않은 빠져나갈 길은 시험하지 않았다고 밝힙니다.
- 어시스턴트 자신의 직전 답변을 시험하려면 `dia reductio 직전 답변을 검토해 주세요`라고 쓰세요. 그 답변을 쓴 장본인이 검토한다는 점을 밝힙니다.

### dia-negative: 주장을 그 자신의 기준으로 평가하기

**쉽게 말하면.** 주장을 내 가치관으로 판단하는 대신, 그 주장이 스스로 한 말로 판단합니다. 주장이 약속하는 것("누구나 언제든 문제를 제기할 수 있다")을 붙잡고, 그 약속이 지켜지지 않는 실제 사례를 찾습니다. 그다음 그 주장이 실제로 어떤 일을 하는지, 확인해 볼 수 있는 추측의 형태로 묻습니다. 이름은 철학자 아도르노의 '부정의 변증법'에서 왔습니다. 이 스킬은 그의 생각을 더 좁고 실용적으로 다듬은 '내부 비판'을 사용합니다.

**이럴 때 쓰세요.** 구호, 정책, 사명 선언문, 계획이 그럴듯하게 들리는데 무엇이 빠져 있는지 보고 싶을 때입니다. 코드나 명령어, 설정이 무엇을 하는지 설명하는 용도나 일반적인 검토용으로는 **맞지 않습니다**.

**해 보기:**

```
dia negative "우리 회사는 오픈 도어 정책을 운영하므로, 회사의 누구나 언제든지 경영진에게 문제를 제기할 수 있습니다."
```

**결과는 이렇습니다** (실제 실행, 줄임):

> **대상:** 인용된 문장, `text`로 읽음(다른 사람의 정책 문구). 사용자 자신의 주장이라면 그렇다고 말씀해 주세요. `user`로 다시 실행하겠습니다.
> **주장:** … **시험한 읽기:** "할 수 있다"는 "실제로 할 수 있다", 곧 그 사람에게 열려 있는 경로가 있다는 뜻입니다. 문장 자체의 "~하므로"가 이 읽기를 가리킵니다. …
> **결과: 열려 있음.** 확정된 지적 1개, 조건부 지적 1개. 확정: 주장은 누구나 **언제든지** 문제를 제기할 수 있다고 하지만, 오픈 도어 정책은 관리자가 실제로 자리에 있을 때만 길을 열어 줍니다.
> **주장 자신의 기준:** "회사의 누구나"(모든 사람, 예외 없음), "언제든지"(모든 순간), "우리 회사는 오픈 도어 정책을 운영하**므로**…"(정책만으로 둘 다 이루어진다).
> **F1(확정): 정책은 "언제든지"를 지켜 낼 수 없습니다.** 연락이 닿는 관리자가 없는 시간: 야간 근무, 모두 회의 중, 휴가나 출장. … 정책이 있는데도 연락이 닿는 관리자가 없는 시간이 하나라도 있을 수 있으면 "~하므로"는 깨집니다. *빠져나가는 것:* 어떤 문제는 문 뒤에 아무도 없을 때 생기며, 그것이 급한 문제일 수 있습니다.
> **F2(조건부): "누구나"와 문.** 원격 근무자나 외부 근무 직원, 또는 다른 교대조 사람들: 주장이 말하는 유일한 경로는 문입니다 … 회사에 그런 직원이 있는지, 그리고 "오픈 도어"가 이메일, 채팅, 전화도 포함하는지*에 달려 있습니다.*
> **이 문장이 실제로 하는 일(추론):** "해도 된다"를 "할 수 있다"로 바꿉니다. … 책임도 직원에게 돌립니다. 제기되지 않은 문제가 있으면, 이 문장은 제기할 수 있었다고 암시합니다. *이것을 반증할 증거:* 이름이 정해진 대리인, 정해진 시간, 상위 보고 경로, 또는 누군가 확인하는 서면 창구.
> **선택지:** A. 주장의 범위를 좁힌다. B. 그대로 두되 빠지는 것을 밝힌다. C. 관행을 바꾼다(누군가 자리에 있는지에 달려 있지 않은 경로). D. F2를 더 살핀다. **권고: C**, F1에 근거. … 결정은 사용자의 몫입니다.
> *(5.1.0에서 Claude Opus 5.5, effort medium으로 기록했습니다.)*

**팁**

- 조건부로 표시된 발견은 사용자의 상황에 관한 사실에 달려 있으니, 그 사실을 어시스턴트에게 알려 주세요. 어떤 기준이 사실 그 주장의 기준이 아니라고 말하면, 그 기준을 쓴 발견을 빼고 다시 실행합니다.
- 선택지 하나를 권고하지만, 대신 골라 주지는 않습니다.

### dia-warrant: 이유가 결론을 얼마나 뒷받침하는지 보기

**쉽게 말하면.** 일상의 논증은 대부분 무언가를 증명하지 않고, 결론을 그럴듯하게 만들 뿐입니다. 시험 결과가 좋았다, 전문가가 그렇게 말했다, 다른 사람에게는 통했다는 식입니다. 이유가 혼자서 결론에 닿지는 않습니다. 대개 말하지 않은 규칙 하나가 이유를 결론까지 데려가고("필름이 한 라인에서 한 일은 모든 라인에서도 할 것이다"), 그런 규칙에는 모두 통하지 않는 경우가 있습니다. 철학자 스티븐 툴민은 이 규칙을 **논거**(warrant)라고 불렀습니다. `dia-warrant`는 이유에서 결론으로 가는 단계들을 펼쳐 놓고, 각 단계가 기대는 규칙을 밝히며(사용자가 말하지 않은 곳에서는 자기가 읽은 것이라고 표시합니다), 그런 종류의 단계가 받을 수 있는 질문을 묻습니다. 그 밖에 무엇이 바뀌었는지, 잰 값이 정말 그 대상을 따라가는지, 전문가의 지식이 바로 이 단계에 관한 것인지, 비슷한 사례가 중요한 점에서 정말 비슷한지 같은 질문입니다. 질문은 증거로만 닫힙니다. 논증 자신의 말, 사용자의 파일(도구가 있으면 도구로 읽고 계산합니다), 사용자의 답, 또는 어시스턴트가 밝히는 출처이며, 어시스턴트의 기억으로는 닫히지 않습니다. 그런 다음 판단합니다. 이유가 무엇을 뒷받침하고 무엇을 뒷받침하지 못하는지, 어느 단계가 가장 약한지, 지금 상태로 그 결론대로 움직이겠는지를 말합니다. 약한 뒷받침과 "거짓"은 구분합니다. 움직이는 데 필요한 것이 있으면 만들어 줍니다. 보낼 회신, 도달해야 할 수치, 열린 것을 가를 확인 같은 것입니다.

**이럴 때 쓰세요.** "왜냐하면"이 얼마나 무게를 버틸 수 있는지 알고 싶을 때입니다. 시험 결과, 전문가의 조언, 다른 사람의 경험과 비교하는 말, 앞으로 일어날 일에 대한 예측 같은 것들입니다. 주장에 "언제나", "모든", "절대"가 들어 있고 그 말을 엄격한 뜻으로 쓴다면 `dia-conjecture`, 주장이 스스로 모순되는지 알고 싶다면 `dia-reductio`, 결정하려는 계획이라면 `dia-counterplan`을 **대신 쓰세요**.

### dia-counterplan: 다른 계획을 옹호하는 주장 들어 보기

**쉽게 말하면.** 큰 결정을 앞두고는 정반대의 가정 위에 세운 다른 계획을 옹호하는 말을 들어 보는 것이 도움이 됩니다. 이것이 경영학 연구에서 나온 계획 방법인 변증법적 탐구입니다(리처드 메이슨, 1969). 어시스턴트는 사용자의 계획이 성립하려면 참이어야 하는 것들을 나열하고(대부분 말하지 않은 것들입니다), 그중 결정이 걸린 몇 개만 남깁니다. 반대가 참이라면 다른 길이 맞겠는가를 묻는 것입니다. 남긴 가정마다 충분히 참일 수 있는 구체적인 반대 가정을 세우고, 쌍마다 어느 쪽이 참인지 보여 줄 가장 싼 관찰을 짚습니다. 그런 다음 사용자의 데이터와 답으로 정해지는 것은 정하고(반대 가정 아래에서 계획 자신의 수치를 다시 계산해 봅니다), 남은 반대 가정들이 요구하는 길을 계획과 같은 수준으로 자세히 세운 뒤, 지금이라면 어느 길을 택할지와 무엇이 그 판단을 바꿀지 말합니다. 계획이 버티는 것도 계획이 뒤집히는 것만큼 좋은 결과입니다. 양쪽을 모두 자기가 썼다는 사실을 솔직히 밝히므로, 이것은 계획에 대한 독립적인 시험이 아닙니다.

**이럴 때 쓰세요.** 어떤 계획에 막 뛰어들려 할 때입니다. 가격 변경, 이사, 이직 제안, 큰 구매, 팀의 다음 단계 같은 경우입니다. 내 아이디어에 대해 한 번에 한 질문씩 질문을 받거나 허점을 찔러 보고 싶다면 `dia-quaestio`, 계획이 스스로 한 약속을 지키는지 보려면 `dia-negative`, 하나의 논증이 내세운 이유가 얼마나 튼튼한지 보려면 `dia-warrant`를 **대신 쓰세요**. 어떤 주장 하나가 참인지가 궁금하다면 그냥 물어보면 됩니다.

> **나:** 알겠어요, 빵이 문제였네요. 동네 제빵학원 수강생 중에 12월부터 평일 새벽 5시에서 8시까지 일할 수 있다는 사람이 있어요, 시급 1만 3천 원이요. 그리고 평일 영업일은 한 달에 21일 정도고, 현수막이랑 메뉴판 새로 하는 데 28만 원 들어요.

> **어시스턴트:** **새벽 제빵 인력을 쓰는 쪽이 계산상 충분히 남아요. 다만 현수막은 빵이 실제로 7시 반에 나오는 걸 확인한 뒤에 거세요.** 이번에 바뀐 안을 같은 방식으로 다시 봤어요(숫자는 파이썬으로 계산). 인건비는 하루 3만 9천 원(3시간 × 13,000원), 한 달 81.9만 원(21일)이에요. … 하루 영수증 **약 8건**이 돌아오면 본전이에요. 빠진 31건의 4분의 1 정도예요. … 빠진 빵 손님 절반이 돌아온다고 가정하면 하루 +3.5만 원, 한 달 +74만 원 정도가 남아요. 절반은 가정한 숫자예요. …

질문을 하나도 하기 전에 판매 파일만으로 첫 번째 가정이 정해졌습니다. 할인은 남아 있던 손님을 겨냥하고 있었습니다. 원인은 사용자가 알려 준 사실로 정해졌고, 어시스턴트는 그 사실이 미치는 만큼 판단을 바꿨습니다. 새벽 제빵 인력 안은 바뀐 계획이었으므로 다시 검토했고, 어시스턴트의 기억에 기댄 비용 수치는 확인이 필요하다고 표시했습니다.

**팁**

- 계획이 기대는 데이터를 주세요. 무엇을 묻기 전에 데이터로 정할 수 있는 것부터 정하고, 사용자만 아는 것은 한 번에 모두 묻되 질문마다 그 답이 무엇을 정하는지 붙입니다.
- "모르겠어요"도 좋은 답입니다. 어시스턴트는 있는 것으로 판단하고, 나머지를 무엇이 가를지 말합니다.
- 사용자의 사실이나 이유는 그것이 미치는 만큼, 어느 쪽으로든 쌍을 정합니다. 반대 가정을 거부하는 것은 그 안의 결함(사실을 잘못 적었거나, 다른 반대 가정과 함께 성립할 수 없음)을 짚을 때만 인정됩니다. 거부만 하거나, 되풀이하거나, 누군가의 지위를 내세우면 그 쌍은 열린 채로 남고, 무엇이 그것을 정할지가 함께 적힙니다.
- 위의 새벽 제빵 인력처럼 계획을 바꾸면 새 계획이 되어 다시 검토하며, 그 변경으로 무엇을 내주게 되는지도 말합니다.
- "내 계획이 무엇에 기대고 있나요?"만 물으면 핵심 가정만, 각각 그것을 가를 질문과 함께 받습니다.
- 양쪽 이야기를 들었다는 것이 계획을 시험했다는 증거는 아닙니다. 답은 검토하지 않은 것, 예를 들어 이 둘 말고 다른 길이나 공유한 사실이 정확한지를 밝힙니다.

### dia-emend: 답변이나 초안을 한 번 꼼꼼히 검토하기

**쉽게 말하면.** 꼼꼼한 편집자가 한 번 훑어보는 것입니다. 어시스턴트는 잘못된 점을 나열하고, 하나하나 확인한 뒤, 확인된 오류만 고칩니다. 의심은 되지만 확인하지 못한 오류는 예상되는 수정안과 함께 따로 적어 두므로, 아무것도 몰래 바뀌지 않습니다.

**이럴 때 쓰세요.** 초안이나 어시스턴트의 직전 답변이 있고, 사실 오류와 논리의 빈틈, 빠진 부분을 한 번 바로잡고 싶을 때입니다. 메시지를 `dia-emend`(또는 `dia emend`)로 시작하고, 특별히 볼 부분이 있으면 덧붙이세요.

**해 보기:**

```
dia-emend 사실관계를 확인해 주세요: 만리장성은 달에서 맨눈으로 보이는 유일한 인공 구조물이며, 전부 명나라 때 지어졌다.
```

**결과는 이렇습니다** (웹 검색을 쓴 실제 실행, 줄임):

> **읽어 낸 요구 사항:** 검토 대상은 주신 문장입니다. "사실관계를 확인해 주세요"가 기준입니다. 문장을 어디에 쓰려는지는 말씀하지 않으셔서, 읽는 사람에게 만리장성에 관한 정확한 사실을 남기려는 문장이라고 가정했습니다.
> **① 확인된 오류:** 1. "달에서 맨눈으로 보이는 유일한 인공 구조물"은 거짓입니다(검색). NASA는 이를 근거 없는 속설이라고 합니다 … 장성의 폭은 약 6 m에 불과하고, 달은 약 384,400 km 떨어져 있습니다. … 2. "전부 명나라 때 지어졌다"도 거짓입니다(검색). 성벽은 기원전 7세기 무렵부터 지어졌습니다. 기원전 220년 무렵 진시황이 북쪽에 있던 성벽들을 하나의 체계로 이었습니다. … 명나라는 장성의 많은 부분을 벽돌과 돌로 다시 쌓았습니다.
> **② 누락된 요구 사항:** 없음.
> **③ 유지한 올바른 내용:** 명나라가 장성의 큰 부분을 지은 것은 맞으며, 오늘날 남아 있는 부분의 대부분도 여기에 속합니다.
> **④ 남은 불확실성:** 한나라 성벽의 길이는 자료마다 달라서, 수정본에는 수치를 넣지 않았습니다. 달에서 보이는 인공 구조물이 하나라도 있는지는 확인하지 않았으므로, 수정본은 그에 대해 아무 주장도 하지 않습니다.
> **수정본:** 만리장성은 달에서 맨눈으로 보이지 않습니다. NASA는 그런 생각을 근거 없는 속설이라고 합니다 … 또한 전부 명나라 때 지어진 것도 아닙니다. … *(출처 목록)*
> *(5.1.0에서 Claude Opus 5.5, effort medium으로 기록했습니다.)*

**팁**

- 검색 도구가 없어도, 어시스턴트가 직접 다시 따져 볼 수 있는 논리와 계산은 고칠 수 있고, 확인하지 못한 사실은 ④에 적습니다.
- `dia-emend 이 작업을 dia-emend 방식으로 해 주세요: <task>`라고 하면, 답변을 쓰고 한 번 검토한 뒤 최종본만 보여 줍니다.

### dia-ratchet: 라운드를 거듭하며 확인하고 고치기

**쉽게 말하면.** `dia-emend`와 비슷하지만 여러 라운드에 걸쳐 진행되고, 모든 수정에 외부 근거가 필요합니다. 검색, 도구 실행, 또는 사용자가 준 자료입니다. 확인을 통과한 사실은 고정되어서 이후 라운드에서 되돌릴 수 없습니다. 더 고칠 것이 없거나, 더는 검증할 수 없거나, 라운드 상한에 이르면 반복은 저절로 멈춥니다.

**이럴 때 쓰세요.** 속도보다 정확성이 중요할 때입니다. 예를 들어 곧 공개할 글의 사실과 날짜를 확인할 때입니다. 메시지를 `dia-ratchet`(또는 `dia ratchet`)으로 시작하세요. `dia <request>`로는 선택되지 않습니다.

**해 보기:**

```
dia-ratchet --max 2 이 문단의 날짜와 사실을 확인해 주세요: "최초의 아이폰은 2008년에 출시되었고, 같은 날 앱 500개와 함께 앱스토어가 문을 열었다."
```

**결과는 이렇습니다** (웹 검색을 쓴 실제 실행, 줄임):

> Apple의 보도자료와 대조해 문단을 확인했고, 오류 세 개를 찾았습니다. 세 개 모두 고쳤습니다.
> **수정한 문단:** "최초의 아이폰은 2007년에 출시되었고, 앱스토어는 2008년 7월 10일에 앱 500개 이상과 함께 문을 열었다."

> **세부 사항 하나:** … 2008년 7월 10일은 iTunes 7.7에서 스토어가 열린 날입니다. 아이폰에서는 iPhone 3G가 출시된 7월 11일부터 들어갈 수 있었습니다 … *(출처 목록)*

### dia-adjudicate: 리뷰의 어떤 지적이 맞는지 가리기

**쉽게 말하면.** 리뷰를 판정하는 심판입니다. 글 하나(제안서, 문서, 주장, 수치)와 그 글에 대한 리뷰를 하나 이상 주면 됩니다. 사람이 쓴 것이든 다른 어시스턴트가 쓴 것이든 상관없습니다. 리뷰를 꼼꼼히 읽기 전에, 글 자체가 주장하는 것 가운데 확인할 수 있는 것을 먼저 나열해 리뷰가 범위를 정하지 않게 합니다. 그다음 리뷰의 지적마다 한 번씩 출처와 대조해 판정합니다. 맞음, 일부만 맞음, 과장, 틀림, 확인 불가 중 하나입니다. 어떤 말을 리뷰 몇 개가 했는지, 누가 썼는지는 전혀 셈에 들어가지 않습니다. 서로 엇갈리는 리뷰가 각자의 기준으로는 모두 맞을 수 있고, 그럴 때는 어느 기준으로 맞는지 말합니다. 리뷰를 뒤집을 때는 출처 자신의 말이나 보여 준 재계산으로만 뒤집습니다. 그런 다음 판단을 내놓습니다. 글의 결론에서 무엇이 남는지, 어느 리뷰가 어느 점에서 맞았는지, 어느 리뷰도 제기하지 않은 것은 무엇인지, 고친 글이 무엇을 충족해야 하는지입니다. 움직이는 데 필요한 문구가 있으면 써 주되, 그것이 자기 문구이고 판정을 거치지 않았다고 밝힙니다. 마지막에는 자기 판정이 가장 틀렸을 법한 곳을 말합니다.

**이럴 때 쓰세요.** 같은 글에 대한 리뷰들이 서로 다르게 말할 때, 또는 자신 있게 쓰인 리뷰를 따르기 전에 확인하고 싶을 때입니다. 메시지를 `dia-adjudicate`(또는 `dia adjudicate`)로 시작하고 글과 리뷰를 함께 주세요. `dia <request>`로는 선택되지 않습니다.

- 글, 리뷰, 그리고 리뷰가 가리키는 출처(여기서는 택배사 견적서)를 주세요. 판정하기 전에 읽고, 글 자체의 주장도 확인하므로 어느 리뷰도 제기하지 않은 것을 찾아낼 수 있습니다.
- 두 리뷰가 같은 말을 한다고 해서 하나일 때보다 더 강한 증거가 되지 않으며, 리뷰어의 지위도 셈에 들어가지 않습니다. 내용으로 판정합니다.
- 사용자만 아는 것에 답하세요. 질문마다 그 답이 무엇을 정하는지 붙어 있습니다. 덧붙인 자료는 사용자가 준 것으로 표시하고, 그 자료가 걸린 판정을 다시 내립니다.
- 이의를 제기한 판정은 짚을 수 있는 결함(출처를 잘못 읽음, 계산이 틀림, 조건을 놓침, 몰랐던 사실)이 있을 때만 철회합니다. 리뷰어들의 의견 일치, 그들의 지위, 되풀이는 아무것도 움직이지 못합니다.
- 어시스턴트가 별도 에이전트를 띄울 수 있고 출처를 읽은 방식에 기대어 리뷰를 뒤집는다면, 같은 입력을 한 번 더 판정하게 해 둘을 비교합니다. 한 번 돌렸는지 두 번 돌렸는지도 밝힙니다. 띄울 수 없다면 두 번째 채팅에서 다시 돌리고, 갈린 판정만 다시 확인하면 됩니다.
- 검색 도구가 없어도 수치는 다시 계산하지만, 확인할 수 없는 지적은 "틀림"이 아니라 "확인 불가"로 남깁니다.

### dia-regula: 모델이 따를 글 쓰기

**쉽게 말하면.** AI에게 주는 지시문을 점검하는 문체 검사입니다. 스킬 파일, 에이전트용 프롬프트, 프로젝트의 에이전트 지침 파일, 규칙 파일이 대상입니다. 글을 네 가지 규칙에 비춰 봅니다. 문단마다 원하는 결과를 말하고 그 조건과 대안을 같은 문장에 담아, 어떤 조건도 따로 떨어진 줄에 남지 않게 합니다. 한계를 정하는 단어("건드리다", "바꾸다" 같은)는 뜻한 만큼만 좁아야 합니다. 지시는 더 적게 쓰고, 하나마다 이유를 붙입니다. 한 대상에는 이름 하나만 씁니다. 검토만 요청하면 규칙을 어긴 곳을 심각한 순서로 나열하고, 사용자가 고를 때까지 아무것도 바꾸지 않습니다.

**이럴 때 쓰세요.** 스킬, 에이전트나 서브에이전트용 프롬프트, 에이전트 지침 파일, 규칙 파일을 쓰거나 고칠 때, 또는 어시스턴트가 써 둔 조건을 자꾸 무시할 때입니다. 메시지를 `dia-regula`나 `dia regula`로 시작하거나, `dia <request>`가 고르게 하세요.

**해 보기:**

```
dia regula 코딩 에이전트에게 줄 이 지시문을 검토해 주세요:
새 플래그에 맞게 문서를 업데이트하라.
작업에 필요한 파일만 건드려라.
- 테스트가 실패하면 멈춰라.
```

**결과는 이렇습니다** (실제 실행, 줄임):

> 문제 네 개를 찾았고, 가장 심각한 것부터 적었습니다. 검토만 요청하셨으므로 아무것도 다시 쓰지 않았습니다. 고치기를 원하는 지적을 고르시면 수정하겠습니다.
> 1. **편집 범위가 에이전트 자신의 판단에 달려 있습니다** (규칙 2). 2줄: `작업에 필요한 파일만 건드려라.` 작업에 무엇이 "필요한지"는 에이전트가 정하므로, 이 문장은 에이전트가 자기 권한을 스스로 넓힐 수 있게 합니다. … 정확한 경로(예: `docs/cli.md`)를 적으면 에이전트가 늘릴 여지가 없어집니다.
> 2. **테스트 조건이 따로 떨어진 글머리 기호에 있어, 그 조건이 통제하는 동작과 떨어져 있습니다** (규칙 1). 3줄: `- 테스트가 실패하면 멈춰라.` 테스트를 언제 돌릴지, 어떤 테스트인지, "멈춰라"가 무슨 뜻인지(편집 전에 멈추기, 변경을 그대로 두기, 되돌리기), 테스트를 아예 돌릴 수 없으면 어떻게 할지가 열려 있습니다.
> 3. **어떤 지시에도 이유가 없습니다** (규칙 3). … 이유가 없으면 에이전트는 글에 적히지 않은 경우에 지시를 적용할 수 없습니다. 예를 들어, 원래부터 실패하던 테스트를 고쳐야 할까요?
> 4. **"새 플래그"는 에이전트가 찾지 못하는 것일 수 있습니다.** 저장소나 diff에서 어느 플래그가 새것인지 알 수 없으면, 에이전트는 추측하거나 지어낼 수 있습니다. 플래그 이름을 주고 어디에 정의되어 있는지 알려 주세요.
> 규칙 4 문제는 없습니다. 각 대상에 이름이 하나뿐입니다. **조언(결함 아님):** 글은 작업이 언제 끝나는지 말하지 않습니다 …
> *(5.1.0에서 Claude Opus 5.5, effort medium으로 기록했습니다.)*

**팁**

- 건네받은 글은 그 자체가 프롬프트라도 따를 지시가 아니라 점검할 재료로 다룹니다.
- "이 규칙은 근거가 얼마나 강한가요?"라고 물으면 각 규칙의 근거를 보여 줍니다. 그 파일은 그때만 읽습니다.
- 어시스턴트가 별도 에이전트를 띄울 수 있으면, 계속 쓸 글의 변경은 그 변경을 쓰지 않은 에이전트가 검토합니다. 그렇지 않을 때, 그리고 테스트 명령처럼 사실이나 명령만 더하는 편집은 어시스턴트가 직접 점검하고 독립적이지 않은 점검이라고 밝힙니다.

### dia-techne: 그 분야 최고 실무자처럼 일하기

**쉽게 말하면.** 요청은 그 요청이 이루려는 목적보다 좁은 경우가 많습니다. `dia-techne`는 먼저 요청이 무엇을 위한 것이라고 보는지 말하고, 요청한 것을 거기에 이르는 한 가지 방법으로 다룹니다. 그것을 적어도 하나의 다른 방법과 나란히 놓고, 그 결과 자체의 기준으로 비교한 뒤, 가장 나은 쪽을 택하고 비교에서 무엇이 드러났는지 알려 줍니다. 일은 그 분야 최고 실무자처럼 하고, 지금 만들 수 있는 것은 제안으로 남기지 않고 지금 만들며, 결과는 자기 아닌 것으로 확인받습니다. 만든 것을 실행해 보고, 수치를 다시 계산하고, 출처를 읽습니다. 사용자의 데이터나 사용자가 정한 한도는 바꾸지 않습니다. 사용자의 파일을 바꾸거나 지우기 전에 사본을 남기고, 사용자가 준 폴더 안에서 일하며, 사용자의 허락 없이는 아무것도 설치하지 않고, 보내기, 게시, 지출처럼 되돌릴 수 없는 일 앞에서는 멈춥니다.

**이럴 때 쓰세요.** 빠른 답보다 깊이 있는 버전이 필요할 만큼 중요한 일일 때입니다. 공개적으로 할 주장, 데이터에 기반한 결정, 어시스턴트가 아닌 다른 것으로 확인받고 싶은 수정 같은 경우입니다. 시간이 더 걸립니다. 메시지를 `dia-techne`로 시작하거나 `dia techne`를 쓰세요. `dia <request>`로는 선택되지 않습니다. 이름 붙인 것만 원하면 `--aim=request`를 붙이거나 "요청대로"라고 하세요.

**해 보기:**

```
dia-techne 우리 모바일 퍼즐 게임의 D30 리텐션이 12%야. 다음 주 투자자 발표에서 '업계 평균보다 높다'고 말해도 될까?
```

**결과는 이렇습니다** (웹 검색을 쓴 실제 실행, 줄임; 영어 실행을 번역):

> **제가 보는 목표 결과:** 투자자들이 리텐션이 진짜 강점이라고 확신하고 돌아가고, 실사에서 확인해도 그 주장이 유지되는 것. 다른 것이라면 고쳐 주세요.
> **권장:** 12%가 classic D30이라면 평균보다 훨씬 높고, "평균보다 높다"는 말은 너무 약합니다. … 두 가지 방법을 비교했습니다. "업계 평균보다 높다"(모호하고, 정의가 벤치마크와 다르면 무너짐)와 정의와 출처를 밝힌 구체적인 수치(구체적이고, 실사에서도 유지됨)입니다.
> **제안하는 슬라이드 문구(요청 범위 밖):** "D30 리텐션: 12%(classic day-30, [iOS/Android], 코호트 [2026년 월~월], n = [설치 수]). 일반적인 퍼즐 게임 D30(~5~7%)의 약 2배이며, 전체 장르 모바일 중앙값(<1%, GameAnalytics 2026)보다 훨씬 높습니다."
> **비교(비율은 모두 다시 계산):** 모든 모바일 장르 중앙값 0.69~0.79%, 따라서 12%는 약 15~17배, "보고서의 2차 요약에서 읽음"; 퍼즐 장르 약 5.35%, 약 2.2배, "2차 자료, 원 출처는 찾지 못함"; …
> **말하기 전에 확인할 것:** 정의(classic인지 rolling인지: "rolling 리텐션은 몇 배 높게 나올 수 있습니다. 벤치마크는 classic을 씁니다."), 코호트 구성, 표본 크기("설치 1,000건이면 12%의 95% 범위는 약 ±2%p입니다"), 코호트 간 일관성, 성숙한 코호트만 쓰기.
> **이 확인의 한계:** "GameAnalytics의 원 보고서나 장르별 보고서를 열지 못했습니다. 수치는 2차 요약에서 나온 것입니다." **사용자에게 남긴 일:** 정의, n, 코호트, 플랫폼 확인, 코호트 표를 앞에 보여 줄지 결정. *(출처 목록)*
> *(4.0.0, Claude Opus 5.5에서 기록했습니다.)*

**팁**

- **원하는 것을 말해 주면**("제가 원하는 건 실사 뒤에도 그 수치를 믿는 투자자예요") 그것을 위해 일합니다. 말하지 않으면 목적을 스스로 읽어 내고 그 사실을 먼저 밝혀, 사용자가 고칠 수 있게 합니다.
- 요청한 것 이상으로 만든 것은 그렇다고 표시하며, `--aim=request`를 쓰면 이름 붙인 것만 합니다.
- 사용자에게는 사용자만 할 수 있는 일만 남깁니다. 사용자가 내릴 결정, 사용자만 가진 사실, 현실 세계에서의 행동입니다. 확인하지 못한 것은 확인하는 방법을 알려 줍니다. 사용자가 설치를 허락하지 않으면 도구를 외부 라이브러리와 대조해 확인하지 않습니다.
- 다른 실행자를 지정하면("Codex에 줄 프롬프트만, 실행하지 마") 실행하는 대신 프롬프트를 씁니다. 도구가 없으면 아무것도 실행하거나 찾아볼 수 없으므로, 무엇이 기억에 기댄 것이고 무엇을 확인해야 하는지 말합니다.

### dia-router: 짧은 한 단어로 모든 스킬 부르기

**쉽게 말하면.** 그 자체로 하나의 방법은 아니고, 더 빨리 들어가는 길일 뿐입니다. 메시지를 `dia`로 시작하세요. `dia`만 쓰면 스킬 열세 개를 보여 줍니다. 뒤에 스킬의 이름을 붙이고 요청을 쓰면 그 스킬이 시작되고, 원하는 일을 그냥 쓰면 알맞은 스킬을 골라 먼저 한 줄로 어떤 스킬인지 알려 줍니다. 두 스킬이 요청에 비슷하게 맞으면 짐작하지 않고 묻고, 맞는 스킬이 없으면 스킬 없이 답합니다.

**이럴 때 쓰세요.** 휴대폰으로 입력할 때, 또는 어떤 스킬이 필요한지 잘 모를 때입니다. `dia-skopos`, `dia-ratchet`, `dia-adjudicate`, `dia-techne`는 이름으로만 시작되며, `dia`가 골라서 시작하는 일은 없습니다. 이런 요청에는 `dia`가 보낼 형식을 알려 줍니다.

**해 보기:**

```
dia
dia reductio 모든 소수는 홀수라고 가정하고 어디서 무너지는지 보여 주세요.
dia 온보딩 이메일을 추가한 뒤 이탈률이 떨어졌으니, 이메일이 이탈을 줄인 거예요. 제 이유가 이 결론을 얼마나 뒷받침하나요?
```

**결과는 이렇습니다** (Claude Code에서 실제 실행, 줄임; 영어 실행을 번역):

> `dia` → 메뉴, 곧 "dia-skopos | 작업 전에: 요청을 어떻게 읽었는지와 그 요청이 위한 결과를 보여 주고, 어느 쪽을 할지는 사용자가 고릅니다"부터 "dia-techne | 일회성 요청을 그 분야 최고 실무자처럼 깊게 만든 뒤 실행합니다"까지 스킬 열세 개를 담은 표, 이어서 "`dia <name> <request>`는 그 스킬을 실행합니다. 예: `dia reductio …`."
> `dia reductio …` → `dia-reductio`가 바로 시작됩니다: "**판단:** ‘모든 소수는 홀수다’는 거짓입니다. 이 주장의 정의 자체가 반례 **2**로 이를 반박합니다. … 4. 따라서 2는 홀수다. *(3, C1)* … 6. 따라서 2는 홀수가 아니다. *(5, C3)* 7. 4단계와 6단계는 ‘2는 홀수다’와 ‘2는 홀수가 아니다’를 말합니다. 이는 엄밀한 모순입니다. … **저라면 A를 택하겠습니다** [주장을 2를 제외한 모든 소수로 좁히기]. 가장 작은 변경이고, 위에서 증명되었습니다 …"
> `dia 온보딩 이메일을 …` → "→ dia-warrant: 이 요청은 제시한 이유가 결론을 얼마나 잘 뒷받침하는지 묻습니다." 이어서: "제시하신 이유는 이메일을 시작한 뒤 이탈률이 떨어졌다는 것을 보여 줍니다. 그래서 이메일은 그럴듯한 원인이 됩니다. 하지만 이메일이 하락을 일으켰다는 것까지는 아직 보여 주지 못합니다. … 논증은 한 단계뿐이고, 그것도 약한 종류입니다: ‘뒤에 일어났으니 그것 때문이다’. … 아마 이미 갖춰진 비교 대상이 있을 겁니다: 시작 직전에 가입한 고객들은 이메일을 한 번도 받지 못했습니다. …"
> *(5.1.0에서 Claude Opus 5.5, effort medium으로 기록했습니다.)*

**팁**

- 스킬의 전체 이름이 스킬을 고르며, `dia-`를 붙이든 안 붙이든 됩니다(`dia reductio …`, `dia dia-reductio …`). 줄인 이름으로는 고를 수 없습니다.
- 옵션은 그대로 전달됩니다: `dia ratchet --max 2 <draft>`는 `dia-ratchet --max 2 <draft>`와 같습니다.
- `dia`는 단독으로 첫 단어여야 합니다. `dia-emend …`를 비롯한 전체 이름은 곧바로 해당 스킬로 갑니다.
- 문장의 일부임이 분명한 이름(`dia negative feedback on my draft?`)은 선택이 아니며, 전체를 요청으로 읽습니다.
- 어시스턴트가 두 번째 스킬을 열 수 없는 환경에서는 `dia`가 메뉴는 그대로 보여 주고, 보낼 전체 형식(예: `dia-reductio …`)을 알려 줍니다. 이 경우는 시험하지 않았습니다.

## 여러 스킬 함께 쓰기

- **한 요청에 `dia-elenchus`와 `dia-quaestio`를 함께 쓰는 경우:** 정의를 다루는 대화가 먼저 진행되며, 첫 메시지에서 이를 알립니다. 사용자가 선택지를 요청하거나 대화가 끝나면 브레인스토밍이 시작됩니다. 두 과정이 뒤섞이는 일은 없습니다.
- **한 요청에 `dia-emend`와 `dia-ratchet`을 함께 쓰는 경우:** 별개의 두 과정으로 실행되며 출력도 따로 나옵니다. emend 과정에서 어시스턴트가 직접 한 재도출은 ratchet 라운드의 검증으로 인정되지 않습니다.
- **한 요청에 `dia-reductio`와 `dia-negative`를 함께 쓰는 경우:** 둘 다 실행되므로 출력이 길어집니다. 휴대폰에서는 하나씩 요청하십시오.
- **`dia-warrant`, `dia-conjecture`, `dia-counterplan`은 받은 요청부터 확인합니다.** 요청이 다른 방법의 일이면 한 줄로 그렇게 말합니다. `dia-warrant`에서는 엄격한 모순을 찾거나 모든 경우에 대한 주장의 반례를 찾는 요청, `dia-conjecture`에서는 "대개"나 "대부분"으로 말한 규칙, `dia-counterplan`에서는 행동 방향 없이 주장 하나가 참인지 묻는 요청이 그렇습니다. 그 줄에 쓸 스킬 이름이 없을 수도 있습니다. 맞는 스킬(위 표 참고)로 메시지를 시작해 다시 요청하십시오.
- **`dia-elenchus` 이후:** 그다음에 조언을 요청하면, 어시스턴트는 소크라테스식 부분이 끝났다고 밝히고 각 제안이 자신의 것임을 표시합니다. 선택지와 계획까지 다루는 온전한 세션을 원하면 메시지를 `dia-quaestio`로 시작하십시오. 그러면 그 기록을 이어받아 진행합니다.
- **여러 스킬을 검토단처럼 쓰기:** 하위 에이전트를 띄울 수 있는 어시스턴트로 한 텍스트에 여러 스킬을 돌릴 때는 하위 에이전트마다 스킬 하나를 맡깁니다. 계획이나 권고에는 `dia-counterplan`, 스스로 내건 규칙이나 기준에 비추어 볼 텍스트에는 `dia-negative`, 논증에는 `dia-warrant`, 텍스트가 앞뒤가 맞는지에는 `dia-reductio`를 씁니다. 스킬마다 중심 주장 하나를 검토하므로, 어느 주장을 볼지가 중요하면 지정하세요. 메시지는 스킬 이름과 텍스트로 시작하고 결과 전체를 질문 없이 한 번의 응답으로 달라고 하세요(그러면 `dia-counterplan`은 있는 것으로 판단합니다. 자료로 정해지지 않는 쌍은 무엇이 그것을 가를지와 함께 열어 두고, 대안 계획은 온전히 제시합니다). 출력 형식은 되도록 스킬에 맡기세요. 워크플로 스크립트나 다른 에이전트가 형식을 정하면, 이 네 스킬은 2.11.0부터 결과를 그 형식에 맞춰 넣습니다. 지적은 항목으로 내고 증명은 근거 칸에 넣으며, 형식에 자리가 없는 내용은 방법의 결과라고 표시한 마지막 항목에 담고(`dia-counterplan`은 쌍이 결함이 아니므로 출력 전체를 한 항목에 담습니다), 형식이 이 방법이 주지 않는 값(예: 심각도)을 강제하면 항목에 그렇다고 적습니다. 그러니 마지막 항목까지 모든 항목을 넘기세요. Claude Code 테스트에서 정해진 지적 형식을 주었을 때, 넘겨지는 항목에 방법의 결과가 남아 있던 경우는 2.10.0에서 4회 중 0회, 2.11.0에서 7회 중 7회였습니다(spec D68). 보고서는 `dia-adjudicate`에 두 번, 매번 두 번 중 하나라고 알린 별도 에이전트에서 넘기고(그래야 스스로 두 번째 실행을 시작하지 않습니다), 판정이 갈린 항목을 다시 확인하세요. 대안 계획의 쌍은 판정 대상이 아니라 결정하는 사람의 몫입니다. 테스트에서 `dia-adjudicate`는 검토한 텍스트에 있는, 다른 세션의 도구 설명에 대한 주장을 자기 세션에서 본 것으로 판정했습니다. 다른 세션, 버전, 실행 모드(예: `claude -p`)에 대한 주장의 판정은 직접 다시 확인하세요. 다른 어시스턴트(Codex, ChatGPT)에서 쓴 보고서도 같은 방식으로 붙여 넣으면 됩니다. Claude Code에서는 같은 마켓플레이스의 보조 플러그인 `dia-panel`이 이 검토단을 워크플로 하나로 돌립니다. `claude plugin install dia-panel@dialectic-skills`로 설치하고 `Run /dia-panel:review-panel on <파일>`처럼 요청하면, 스킬마다 에이전트를 따로 띄우고, `dia-adjudicate`를 보고서 순서를 바꿔 두 번 돌린 뒤, 판정이 갈린 항목을 직접 확인할 수 있게 정리합니다. 보고서가 이미 있으면 `Run /dia-panel:judge on <파일> with the reports <보고서 파일들>`처럼 요청하세요. `dia-adjudicate` 두 번 실행과 판정이 갈린 항목 정리만 합니다.
- **에이전트에게 dia 스킬을 쓰게 하기:** 하위 에이전트나 검토자에게 주는 프롬프트에 스킬 이름을 적고 한 번에 답하라고 요청합니다. 예: `Use the dia-negative skill (dia:dia-negative) on design.md and give the whole result in one response, with no questions.` "독립 검토자들에게 dia 스킬로 design.md를 검토시켜 줘"처럼 요청해도 됩니다. 앞에 `dia`를 붙이든 붙이지 않든, 어시스턴트가 검토자마다 스킬 하나를 맡겨 이름으로 시작하게 합니다. 도구 목록에 Skill 도구가 빠진 에이전트(Claude Code에서는 에이전트의 `tools`에 `Skill`을 넣거나, `skills`에 스킬을 적어 미리 불러오게 하십시오)나 플러그인이 설치되지 않은 곳에서 실행되는 에이전트는 스킬을 쓸 수 없습니다.

## 문제 해결

- **마켓플레이스를 추가할 때 `Repository not found`가 나타납니다.** 철자를 확인합니다: `ajitta/dialectic-skills`(dialectric이 아니라 dialectic). 저장소는 공개되어 있으며 GitHub 로그인이 필요하지 않습니다.
- **Claude 모바일의 `/`에 dia 스킬이 없습니다.** 정상입니다. 모바일 메뉴에는 플러그인 스킬이 표시되지 않습니다. 메시지를 `dia`나 스킬의 전체 이름으로 시작하거나, 선택 형식을 끝까지 입력합니다(예: `/dia-quaestio`).
- **스킬이 시작되지 않았습니다.** 2.0.0부터는 일반 문장으로 한 요청으로는 어떤 dia 스킬도 시작되지 않습니다. 메시지를 `dia`(`dia <request>`, 또는 스킬을 정해 `dia reductio …`처럼 `dia <name> <request>`)나 스킬의 전체 이름(`dia-reductio …`)으로 시작하십시오. 메시지를 스킬 이름으로 시작했는데도 스킬이 시작되지 않았다면, 어시스턴트가 그 이름을 문장의 일부로 읽었을 수 있습니다(한국어에서 이름 바로 뒤에 "폴더"가 오면 그 이름의 폴더로 읽혀 스킬이 시작되지 않습니다. 다른 명사가 올 때는 그렇지 않았습니다). 이름 뒤에서 줄을 바꾸거나 명시적 선택을 쓰십시오.
- **어떤 기기에서는 dia가 되는데 다른 기기에서는 안 됩니다.** 데스크톱에서 설치한 것은 그 컴퓨터에만 있고, 웹에서 설치한 것은 계정에 저장되어 모바일 앱까지 갑니다. 웹과 모바일용으로 웹에서 한 번, 쓰는 데스크톱 앱마다 한 번씩 설치하세요(설치 참고).
- **모든 스킬이 두 번씩 나타납니다.** 플러그인이 두 경로로 설치된 것입니다(예: `dia@dialectic-skills`와 `dia@ajitta`, 또는 업로드와 마켓플레이스). 하나를 제거합니다.
- **claude.ai에 Skills 섹션이 없거나 비활성화되어 있습니다.** Settings › Capabilities › Code execution and file creation을 켭니다.
- **`dia-ratchet`, `dia-adjudicate`, `dia-techne`가 시작되지 않습니다.** 메시지의 첫 단어가 스킬 이름이거나 명시적으로 선택했을 때(`/dia:dia-ratchet`, `$dia:dia-ratchet`, `@dia-ratchet`, `dia ratchet`; `dia-adjudicate`와 `dia-techne`도 같은 형식과 `dia adjudicate`, `dia techne`)에만 시작됩니다. `dia <request>`만으로는 절대 선택되지 않으며, 보낼 형식을 알려 줍니다.
- **Codex에서 `$dia:dia-skopos:`가 인식되지 않습니다.** 스킬 이름 뒤에 콜론이 아니라 공백을 넣습니다.
- **claude.ai에서 업로드가 거부됩니다.** Customize › Skills가 아니라 Customize › Plugins › Upload plugin을 사용합니다.
- **claude.ai에서 Check for updates 후에도 예전 버전이 남아 있습니다.** Customize › Plugins에서 `dia`를 제거한 뒤 `dialectic-skills` 마켓플레이스에서 다시 설치합니다. 이후 릴리스를 자동으로 받으려면 Sync automatically를 켭니다.

어떤 경로를 어떻게 검증했는지는 [docs/probes.md](docs/probes.md)에 기록되어 있습니다.

```
skills/dia-<x>/                 source: plain skills (SKILL.md, references/, agents/openai.yaml)

packaging/plugin-README.md      source for plugins/dia/README.md
packaging/openai/               OpenAI directory listing fields and images
plugin-release.json             content digest for the current version (not shipped)
.claude-plugin/marketplace.json marketplace "dialectic-skills" -> ./plugins/dia
plugins/dia/                    generated, shipped
releases/dialectic-skills.zip   generated, shipped (top-level folder dia/)
releases/dialectic-skills-openai.zip
                                generated, OpenAI directory upload
tools/package.py                validate and build (developer-only)
tests/                          developer-only
upstream/                       material the seven original skills were rebuilt from; never shipped
README.<lang>.md                translations of this file (not shipped)
docs/spec.md                    specification
docs/probes.md                  surface and routing probe results
docs/token-cost.md              measured token cost, always-on and per invocation (sections through plugin 2.3.0)
docs/skill-effect.md            each skill but dia-techne and dia-router against no skill, blind-judged (rounds through 2026-11-05)

```

## 개발

```bash
python tools/package.py            # validate, write plugins/dia/ and the zip
python tools/package.py --check    # validate; fail if the committed output lags the source
python -m unittest discover -s tests -v
claude plugin validate --strict plugins/dia
```

생성된 출력물이 아니라 `skills/`를 수정합니다. 스킬 파일을 변경할 때마다 `plugin-manifest.json`의 `version`(및 해당 스킬의 `metadata.version`)을 새로 올려야 합니다. Claude Code는 버전이 바뀔 때만 설치된 플러그인을 업데이트하며, 그렇지 않으면 검사가 실패합니다. 배포 패키지에서 한글은 `skills/<skill>/references/ko/` 아래에서만 허용됩니다. 이 README를 변경하면 같은 커밋에서 번역본도 갱신해야 하며, 테스트가 번역본이 같은 구조를 유지하는지 확인합니다.
