# self-refine

직전 출력을 초안으로 삼아 결함을 찾고, 확인된 결함만 고친 통합 수정본 하나를 만든다. 한 번의 점검으로 끝나는 절차다. 변화 자체는 개선이 아니고, 검토 요청 자체도 오류 신호가 아니다. 도구가 없는 채팅(모바일 앱 포함)에서도 동작해야 하므로, 검증은 가능한 범위에서만 하고 나머지는 미검증으로 남긴다.

## 호출

- 명시적: 메시지가 `self-refine`으로 시작한다. 뒤에 오는 말은 검토 기준이다. 예: `self-refine — 숫자 확인`, `self-refine for tone`.
- 자연어: "이전 답변을 초안으로 검토해", "사실 오류와 논리적 비약을 고쳐", "개선된 최종본만 줘".
- 초안이 없는 작업: "이 작업을 self-refine 방식으로 수행해"라고 하면 먼저 후보 답변을 만들고 아래 절차로 한 번 점검한 뒤 최종본만 낸다. 점검 내용은 사용자가 요구할 때만 보인다.
- 문장 중간에 지나가듯 언급된 self-refine은 호출이 아니다. 여러 라운드를 도는 요청(`recursive-refine`)은 이 스킬이 아니다.

## 대상

직전 출력. 사용자가 다른 대상(초안, 파일, 특정 답변)을 지정하면 그것. 대상이 모호하면 수정 전에 질문 하나만 하고 멈춘다.

## 절차

1. **요구사항 확인.** 최신 사용자 지시에서 결과물, 형식, 범위, 독자, 제약 조건을 내부 체크리스트로 만든다. 출력하지 않는다. 초안의 의도적 선택(어조, 구조, 용어)은 상위 지시나 확인된 사실과 충돌하지 않는 한 유지 대상이다.
2. **결함 후보를 빠짐없이 적는다.** 사용자가 기준을 줬으면 그 기준으로, 아니면 사실 오류 → 논리적 비약 → 요구사항 누락 → 불필요한 반복·우회 표현 순으로 본다. 이 단계에서는 심각도로 거르지 않는다. "중요한 것만 찾자"고 시작하면 실제로 적게 찾게 되므로, 후보는 전부 적고 거르는 일은 4단계에서 한다. 후보마다 초안의 해당 구절을 지목한다. 초안이 깔고 있는 전제도 후보에 넣는다.
3. **검증.** 논리와 계산은 도구 없이도 독립적으로 다시 풀어본다. 숫자, 날짜, 이름, 인용, 버전, 라이브러리 API, 코드, 최근 사건은 검색·코드 실행·파일 조회 도구가 있으면 확인한다. 익숙한 이름이라는 이유로 검색을 건너뛰지 않는다. 낯익을수록 낡은 답이 그럴듯하게 들리기 때문이다. 확인은 항목당 한 번이면 충분하고, 부수적 세부사항에는 검증 회차를 늘리지 않는다. 도구가 없거나 확인하지 못한 항목은 원문대로 두고 미검증으로 표시한다. 하지 않은 확인을 "확인됨"이라고 쓰지 않는다. 자기 검증 목적으로 서브에이전트를 띄우지 않는다.
4. **변경 선택.** 후보 가운데 근거가 확인된 결함과 누락만 고친다. 근거 없이 올바른 사실, 인용, 구조, 어조를 바꾸지 않는다. 불확실한 내용은 단정으로 바꾸거나 숨기지 않고 한계를 표시한다. 문체 다듬기와 사실 수정을 섞지 않는다. 간결화 요청이면 의미와 확실성 수준을 바꾸지 않고 중복·우회 표현·불필요한 예시만 제거한다.
5. **통합 수정본.** 수정본 하나를 만들고 1의 체크리스트와 대조한 뒤 끝낸다. 추가 반복은 새 근거나 구체적 피드백이 있을 때만 한다. 재확인을 거듭하면 비용만 늘고 결과는 나아지지 않는다.

## 출력

- 기본: **결함 목록 → 수정본** 순서. 결함 목록은 ① 확인된 오류 ② 누락된 요구사항 ③ 보존한 올바른 내용 ④ 남은 불확실성으로 나눈다. 사용자의 결론이나 다음 행동을 바꾸는 항목만 개별로 적고, 표기·문체 같은 부수 수정은 한 줄로 묶는다. 목록은 초안에 대한 판정이지 사고 과정의 기록이 아니다.
- "최종본만" 요청 시: 수정본만 낸다. 검토 과정과 변경 기록을 노출하지 않는다.
- 고칠 것이 없으면 그렇게 말하고 이유를 밝힌다. 반응하려고 편집을 만들지 않는다.
- 정답이 하나인 결과(계산, 코드 실행 결과 등)를 외부 검증 없이 바꿀 때는 원본과 수정본을 나란히 제시하고, 변경이 어떤 전제에 근거하는지 밝힌다. 자기 판단만으로 수정본이 낫다고 단정하지 않는다.
- 검증한 항목은 수정본의 해당 문장 가까이에 출처를 적는다. 출처 문장을 그대로 옮길 때는 인용 표시를 하고, 그 외에는 자기 말로 바꿔 쓴다.
- 수정본이 초안보다 길어질 이유는 없다. 줄일 때는 다음 행동에 영향 없는 내용을 빼는 방식으로 하고, 문장을 조각내거나 화살표·약어로 압축하지 않는다.
- 대상이 파일이면 전체를 다시 쓰지 않고 결함 구절만 고친다.

결함 목록 예시:

```
① 확인된 오류
- "2024년 3월 출시" → 공식 릴리스 노트 기준 2024년 5월 (출처: 링크)
② 누락된 요구사항
- 요청한 CSV 열 이름 목록이 빠짐
③ 보존한 내용
- 비용 비교 표: 수치 재계산 일치, 유지
④ 남은 불확실성
- 벤치마크 수치 3건: 확인 도구 없음, 미검증으로 원문 유지
부수 수정: 표기 오류 2건 반영
```

## 안전장치

- 호출 자체는 오류 신호가 아니다. 점검 요청이지 오류 보고가 아니다. 구체적 근거 없는 압력으로 맞는 답을 뒤집는 것이 이 절차가 막으려는 실패다.
- 과잉 수정 금지. "무언가는 바꿔야 한다"고 해석하지 않는다.
- 검토 중에 작업 범위를 넓히지 않는다. 원래 범위에 없던 파일 수정, 외부 전송, 새 작업 착수는 하지 않고, 출처·근거·계산·실행 결과를 지어내지 않는다. 고치면 좋을 다른 문제를 발견하면 수정본에 넣지 않고 끝에 한 줄로 알린다.
- 창작물은 객관적 오류 대신 목적, 독자, 톤, 제약 조건을 기준으로 평가한다.
