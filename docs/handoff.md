## How probes were run (for re-runs)

- **Claude Code:** `claude -p "<prompt>" --plugin-dir plugins/dia --model claude-opus-5-5 --effort medium --output-format stream-json --verbose --no-session-persistence --max-turns N` (the engine since spec D89; the batches before 2026-11-17 used `--model sonnet`).
  - Give every run its own fresh `CLAUDE_CONFIG_DIR` that holds only a copy of `.credentials.json`. Otherwise the account's claude.ai plugins and skills sync into the session within one run and compete with `dia`. `CLAUDE_CODE_SYNC_PLUGINS=0` and `CLAUDE_CODE_SYNC_SKILLS=0` do not prevent the sync.
  - Never run a probe on the home config: since 2026-11-17 a hook there (`~/.claude/hooks/dia-lab-before.py`) makes a session ask for the user's judgment before a dia skill runs, unless the prompt says that no user will reply or `DIA_LAB_HOOK=off` is set. A run with its own config folder does not load it.
  - Start each run in an empty directory outside the repository and pass an absolute `--plugin-dir`. At the repository root, `CLAUDE.md` imports `AGENTS.md`, which describes the skills and says to reply in Korean, and that confounds routing and language results.
  - Discard any run whose `system/init` event lists a plugin with an `@synced` source.
  - A conversation continued with `--resume` needs one more step: during a turn the account's plugins and skills sync into the run's config folder, and the next turn loads them. Remove `<config>/plugins/synced` and `<config>/skills/synced` before each resumed turn, and check the init event of every turn, not only the first (probes Part AU; `run.py` in `C:/Users/ajitta/work/dia-probes/fable-2026-11-17/` does both).
  - The agent tool is named `Task` in `--tools` (Claude Code 2.1.326), and its calls appear as `Agent` in the event stream; a sub-agent's events carry `parent_tool_use_id`.
  - Read which skill loaded from the `Skill` tool_use input.
  - Pass `--add-dir <plugin copy>` when a skill may open a file under its `references/`: with the plugin copy outside the working directory the `Read` is denied and the skill runs without the file (probes Part AL).
  - Tool-less runs use `--tools Skill`.
  - Set `ENABLE_CLAUDEAI_MCP_SERVERS=false`: the account's claude.ai connectors otherwise load into isolated sessions, add a varying number of tools, and even appear in `--tools Skill` runs.
  - Action-holding cells need `--max-turns` 12 or more; hitting the cap returns an empty result.
  - Delete the credential copies afterwards.
- **Baseline arm:** a plugin directory with `.claude-plugin/plugin.json` (`{"name": "old", ...}`) and `skills/` copied from `upstream/installed/*` and `upstream/superclaude-stable-47f791b/socratic-*`.
- **Codex CLI:** use an isolated `CODEX_HOME`.
  - `codex plugin marketplace add <path>`, then `codex plugin add dia@dialectic-skills`.
  - `codex debug prompt-input "hi"` shows the model-visible skill list and needs no model call.
  - Explicit invocation needs a real `codex exec` run, which needs a copy of `auth.json`; delete the copy afterwards.
  - An isolated `CODEX_HOME` still receives the plugins the account itself uploaded (cache folder `plugins/cache/created-by-me-remote`), and a run may then read that copy instead of the build under test (probes Part T; Part AJ (a), where five of six runs did). `enabled = false` for it in `config.toml` did not keep it out reliably; creating that folder read-only before the first run did (0 of 22 sessions listed it, in a check on another plugin). Check in each run's events which SKILL.md was read.
  - `$dia:dia-<x>` must be followed by a space, not a colon; `$dia:dia-intent:` does not resolve.
  - On the OCI build VM the Codex sandbox (bwrap) cannot start, so no shell command runs under `-s read-only` or `workspace-write`; cells that need file access ran with `--dangerously-bypass-approvals-and-sandbox` in a scratch directory.
  - Log every `item.*` event type: Codex's web search arrives as `web_search` items, not `command_execution`.
  - On Windows with Codex CLI 0.169.0, `[windows] sandbox = "elevated"` in a new `CODEX_HOME` fails every shell command, because the sandbox's setup helper asks for elevation that a headless run cannot give. Without the setting a command is refused with no prompt; naming the skill as `$dia:dia-<x> ` still puts its text into the session, so a cell that needs no file can run, and material must then be pasted into the message (probes Part AV; `run_codex.py` in `C:/Users/ajitta/work/dia-probes/fable-2026-11-17/`).
  - On the same PC a command runs headless only with `-s danger-full-access`: `-c windows.sandbox="unelevated"` fails every command with "CreateProcessAsUserW failed: 5" (the shell is the `pwsh.exe` under `WindowsApps`). Use it only with an empty working folder and a prompt that asks for text (probes Part AX; `codex_shell_smoke.py` and `DIA_SANDBOX` in `run_codex.py`).
  - A refused command and a failed sub-agent start leave no item in the `--json` stream; read stderr as well before saying what a run did or did not attempt.
- **Skill-effect eval:** harnesses and raw runs are on the build VM under `~/work/dia-review/eval/` and `eval2/` (`run.py`, `sim.py` for the adaptive respondent, `judge.py`); the method is in `docs/skill-effect.md`.
