## 2. Corrections

1. **The caller was very likely a Claude Code dynamic workflow (unconfirmed).** The record says "A workflow script started four reviewers", each returned an object under a schema the caller fixed, and the "review script" was rewritten as version 2. Claude Code's dynamic workflows are JavaScript scripts that Claude writes, in which `agent(prompt, {schema})` starts a sub-agent that returns JSON and plain code passes results on (Claude Code documentation, "Orchestrate subagents at scale with dynamic workflows"). If so, the fixed schema (C1) and forwarding only `findings` (C2) were code: no model read anything at run time, and text in the plugin could have mattered only when Claude wrote the script. The record's own fix, script version 2, was made that way, at writing time, on the owner's request.
2. Two of the six caller pitfalls go against advice the README already gives (since 2.8.0, spec D64, "Several skills as a review panel"): "do not prescribe an output table" (C1) and "Give the reports to `dia-adjudicate` twice, each time in a separate agent, and recheck the verdicts that differ" (C6, T4). The record mentions neither that item nor the 2026-11-08 field note, whose review (§2) measured a related effect: with a findings table asked for in the prompt, 1 of 8 lens runs carried out its method in full and in scope, against 8 of 8 without it. This session is consistent with that effect, but it has no arm without a schema, and the shared brief (C3) is a second cause. The advice is only in the repository README; the installed plugin's README has no such item.
3. T4 is partly overstated. Shuffling the labels and dropping author names (Inputs, item 1) and ignoring the reports' own severity labels (Rule 7) are steps the judge applies to whatever input it gets, so a caller that passes names and severities in a fixed order does not by itself bypass them. Whether the judge could have started its second run is unknown: Claude Code lets a sub-agent start sub-agents of its own by default, but "agents that other features run, such as workflow agents and agent team teammates, follow their own limits instead" (Claude Code sub-agent documentation). Skipping the second run when the brief asks for one result is what the 2026-11-08 review saw in 9 of 9 runs. The incomplete must-check list in round 2 is against Step 9's own check ("count the must-check rows against the qualifying rows"). An overturn resting on an earlier approval has no basis the skill accepts: Rule 3 asks for the source's words for a factual overturn and Rule 2 does not count agreement as evidence, although no rule names an earlier approval.
4. T6: the split is left out only "when the finished deliverable cannot fail to bring a stated outcome about". Materials saying the outcome could fail put the case under the sentence before it, which requires the split. The record's verifier calls this mainly an execution error; this review agrees. The first half of P5 restates the current text; its second half (a completion criterion met just by recording that something is unverified) is new, rests on one observation, and is recorded here, not adopted.
5. T2 and P4: the same rule, in other words ("Write the whole output in the language of the user's latest message"), is in nine skills (dia-adjudicate, dia-counterplan, dia-emend, dia-negative, dia-ratchet, dia-reductio, dia-skopos, dia-techne, dia-warrant). A clause in dia-reductio alone would make them differ, an explicit "Write in Korean" is the user's request under any reading, and one run does not justify a change in nine skills.
6. dia-reductio's "conditional" grade: by Rule 2 a fact is an [A] premise, so a refutation resting on one verified fact is "conditional" unless that fact alone entails not-T, which makes it "carried by added premises". The record should say which of the two the run missed; from the record alone the grade may have been right.
7. P1 as written would not have brought the lens output to the decision: in round 1 the caller forwarded only `findings` (C2), so a full output written into `notes` would still have stopped at the caller. No field is sure to be forwarded. On how much was lost: the record lists missing parts for all four lenses, its verifier upheld the skill-text cause for dia-negative only, and C1 says some parts went into `notes`, so part of the loss happened only on the way to the judge.

## 3. What reaches a calling agent

The owner's question (2026-11-09): a main session that starts agents will not follow the README, so can the calling side be reached at all?

- **Always, in the main session:** the fourteen skill descriptions (233–255 characters each, dia-router 459; listing 1,274 tokens, D57). None says anything about output format or forwarding. In the 21 parent runs of probes Part AH that started at least one agent, with these descriptions visible, a sub-agent prompt asked for a severity in 7 (counted by the word for severity, in English or Korean, in any sub-agent prompt; an earlier count with another rule gave 6 of 17).
- **On the `dia` route only:** dia-router's body, whose reviewer bullet passes each result on unchanged (D67). The router loaded in 3 of 6 and 2 of 5 runs of Part AH.
- **In the sub-agent only:** the skill body.
- **An agent caller, not a script:** the text a lens returns.
- **Never at run time:** the README.
- **A workflow script:** nothing at run time; only the moment Claude writes the script, which follows the person's request and the descriptions.

So the owner's point holds for this session: what the caller did (a fixed schema, partial forwarding, one judge run) could have been changed only by the person's request when the script was written, as the record's version 2 was. Plugin text acts only inside each sub-agent.

## 4. The proposals

- **P1** (the four lenses, "called by another agent"), revised after C2. An earlier draft of this review put the skill's whole output in the caller's free-text field and ruled out the caller's item list; that cannot survive a caller that forwards only the item list, as this one did, so the placement is reversed here. The README's advice to callers (do not prescribe an output table, D64) stands; P1 is what a lens does when a caller has not followed it. When a caller fixes the output format and no user will reply: carry out every step; give the method's own findings as the caller's items, with each finding's proof (own-standard quote and case, derivation with its rules, warrant record) in the item's evidence field; end the list with one item labelled as the method's result, not a finding, that holds the record (a null result such as "no contradiction found", "no key assumption found" or "no weak link found", the result and strength, the options and recommendation, or the counterplan itself); mark a severity field "not given by this method" unless the skill grades its own findings, and a fix field likewise, except that dia-warrant gives the kind of answer that would strengthen the link (Step 6); dia-counterplan gives no defect items (Rule 1) and no severity (Rule 5), so its counterplan travels in the closing item. If the format has a free-text field, the full layout also goes there. Field names in the skill text stay generic ("the caller's item list", "its evidence field"). Basis: C2 (the caller forwarded only `findings`); the risk is the one measured on 2026-11-08, that a caller's table cuts the method (1 of 8 against 8 of 8), so the smoke checks the method under this placement. Keep the rule in the body: in at least one run no Claude reviewer read `references/output-template.md` (C1). No file writing: a caller like this one names no path, and a report written into the user's project unasked is a side effect.
- **P2** (dia-adjudicate): (i) Rule 1: when asked for a fix, give the condition the fix must meet (an acceptance condition), not replacement text; it keeps the judge from co-writing the revision it will later judge. (ii) Rule 2, narrowed: "An earlier approval of T or of a report item records a decision, not that a claim is true: it never supports a factual verdict (Rule 3), and it settles a choice only when the material shows the choice was the approver's to make." The factual half restates Rule 3, which the record's overturn already broke; the choice half is new. Adopt (ii) only if the base judge in the smoke misuses the seeded approval. (iii) The second run: no change. "Running twice" already asks the judge to start one when it can start agents; whether a workflow agent can is unknown, and nothing reaches the script. Recorded as a limit.
- **P3**: folded into P1 for dia-negative, dia-reductio and dia-warrant (the method's items first, anything else the caller asks for in a separate labelled list). For dia-counterplan: no defect list at all (Rule 1); its counterplan goes in the closing item.
- **P4**: not adopted (correction 5).
- **P5**: not adopted (correction 4). T7 depends on one host's interface, and the Confirmation section already asks for the proceed instruction in the body.
- **P6**: the README item already covers C1 and C6, and the README does not reach a calling agent (§3). A different form: a copyable request for a review workflow that a person pastes when asking for one. It is the one measure that acts when a script is written (§3), whatever happens to P8, and its wording should match the lens behaviour the smoke settles, so it is written after the smoke.
- **P7** (a clause in the descriptions; proposed in an earlier draft of this review): not recommended. It would reverse D67, where the owner kept the description gate unchanged because a clause in thirteen descriptions would add to every session's listing. Measured cost: about 17 tokens per skill in cl100k and o200k, about 85 always-on for five skills (+6.7% on 1,274); it would also depart from the description convention (spec §7.2), touch the gate sentence (a shorter gate let a non-invocation load in D56), and need a Codex listing check. It could act only when a script is written, and the parent sessions in Part AH asked their sub-agents for a severity in 7 of 21 runs with the current descriptions.
- **P8** (new): ship the review panel as a workflow script, so that no caller writes the orchestration. Not inside dia: a workflow is a `.js` file, which AGENTS.md ("instructions only"), spec §7.1 and `tools/package.py` (`SHIPPED_SUFFIXES`) all exclude, and `main` syncs `plugins/dia` to claude.ai, so there is no Claude-Code-only dia package. A separate companion plugin in the same marketplace, declaring `dependencies: ["dia"]` (Claude Code plugins reference), keeps dia unchanged and answers `docs/research/dia-adjudicate.md` §3 ("cross-plugin references break when only one plugin is installed"). Unknowns: whether a workflow's `agent()` can start a plugin skill by name, the companion's always-on listing cost, and whether claude.ai offers or refuses a synced plugin with `workflows/` (a CLI run cannot test this; the owner checks before any merge). Owner ruling first (a companion plugin at all), then a spike (§5).
