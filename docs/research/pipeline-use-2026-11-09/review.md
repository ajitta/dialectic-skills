## 2. Corrections

1. Two of the six caller pitfalls go against advice the README already gives (since 2.8.0, spec D64, "Several skills as a review panel"): "do not prescribe an output table" (C1) and "Give the reports to `dia-adjudicate` twice, each time in a separate agent, and recheck the verdicts that differ" (C6, T4). The record mentions neither that item nor the 2026-11-08 field note, whose review (§2) measured the same effect: with a caller-imposed findings table, 1 of 8 lens runs carried out its method in full and in scope, against 8 of 8 without it. This session is a second observation of that effect, with a JSON schema in place of a Markdown table. What is new is where the advice failed: the caller was an agent, and the advice is only in the repository README; the installed plugin's README has no such item, so nothing the caller loaded carried it. Only the skill text reaches the agents that run the skills.
2. T4 is partly overstated. Shuffling the labels and dropping author names (Inputs, item 1) and ignoring the reports' own severity labels (Rule 7) are steps the judge applies to whatever input it gets, so a caller that passes names and severities in a fixed order does not by itself bypass them; the judge should have applied them. A judge that dropped names after reading them is still weaker than input the caller anonymized, which is a reason for README advice, not for a skill rule. On the second run: by default a Claude Code sub-agent can start sub-agents of its own, up to three layers below the main conversation (Claude Code sub-agent documentation, "Let subagents spawn their own subagents"), so "if you can start separate agents" was probably met; skipping the second run when the brief asks for one result is what the 2026-11-08 review saw in 9 of 9 runs. The incomplete must-check list in round 2 is against Step 9's own check ("count the must-check rows against the qualifying rows"). An overturn resting on an earlier approval is against Rule 3 (an overturn needs the source's words on the same point), although no rule names an earlier approval.
3. T6: the split is left out only "when the finished deliverable cannot fail to bring a stated outcome about". Materials saying the outcome could fail put the case under the sentence before it, which requires the split. The record's verifier calls this mainly an execution error; this review agrees, and the first half of P5 restates the current text.
4. T2 and P4: the rule "Write the whole output in the language of the user's latest message" is shared by seven skills (dia-adjudicate, dia-counterplan, dia-negative, dia-ratchet, dia-reductio, dia-skopos, dia-warrant). A clause in dia-reductio alone would make them differ, an explicit "Write in Korean" is the user's request under any reading, and one run does not justify a change in seven skills.
5. dia-reductio's "conditional" grade: by Rule 2 a fact is an [A] premise, so a refutation resting on one verified fact is "conditional" unless that fact alone entails not-T, which makes it "carried by added premises". The record should say which of the two the run missed; from the record alone the grade may have been right.
6. P1 as written would not have brought the lens output to the decision: in round 1 the caller forwarded only `findings` (C2), so a full output written into `notes` would still have stopped at the caller. No field is sure to be forwarded; P1 below weighs the placements.

## 3. The proposals

- **P1** (the four lenses, "called by another agent"): the only proposal that acts where the failure happens, because the agent running a lens reads the skill text and not the README. Untested, and the effect it targets is large (1 of 8 against 8 of 8), so a smoke comes first (§4). Placement: an extra item in the caller's main list survives a caller like this one, but it needs an invented severity and fix and inflates the counts, which is the record's own complaint in C5. So put the method's parts in the fields of the findings the lens already returns (a derivation, an own-standard quote or a warrant record in `evidence`), and what has no field (options, the record, the counterplan itself) in the free-text field, accepting that a caller that drops that field loses it. Keep the rule in the body: in at least one run no Claude reviewer read `references/output-template.md` (C1). Fold P3 into it (the method's output first and in full, then anything else the caller asks for in a separate labelled list), and extend it to dia-adjudicate for the parts T4 lost in the schema: the Inputs line with the single-run statement, the must-check list and the closing line.
- **P2** (dia-adjudicate), in three parts. (i) Rule 1: when asked for a fix, give the condition the fix must meet (an acceptance condition), not replacement text; small, consistent with Rule 1, and it keeps the judge from co-writing the revision it will later judge. (ii) Rule 2: an earlier approval of T or of a report item is not evidence either; one clause. (iii) Not a caller checklist: the calling agent reads neither the README nor this body. The second run is already the judge's own step: "Running twice" asks it to start one when it can start agents (Claude Code sub-agents can, by default), and it skipped that run when the brief asked for one result (9 of 9 on 2026-11-08). A change would make such a brief no reason to skip; it overrides the caller, doubles the judge's cost, and departs from 2.8.0, which left the second run to the caller through the README. A flag for reports cut to list items is not proposed: the judge drops author names (Inputs, item 1) and does not know each skill's own output, so it cannot tell a cut report from a plain review.
- **P3**: folded into P1.
- **P4**: not adopted (correction 4).
- **P5**: not adopted (correction 3). T7 depends on one host's interface, and the Confirmation section already asks for the proceed instruction in the body.
- **P6**: not proposed. The owner pointed out (2026-11-09) that a calling agent does not follow the README, and the installed plugin does not carry the item. The README item stays for people who build their own pipelines and already covers C1 and C6. Besides the skill descriptions, the only text a main session reads before starting reviewers is dia-router's, and only when the request goes through `dia`; since 2.10.0 (D67) it has each reviewer start its skill by name and answer in one response, and passes each result on unchanged. It says nothing against prescribing an output format; one clause there would reach the `dia` route only. What no skill text can fix: a caller that drops fields it was given.
