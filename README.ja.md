# Dialectic Skills (`dia`)

[English](README.md) | [한국어](README.ko.md) | **日本語** | [简体中文](README.zh-CN.md)

ウェブサイト: [ajitta.github.io/dialectic-skills](https://ajitta.github.io/dialectic-skills/)

推論とレビューのための 10 個のスキルを 1 つのプラグインにまとめたものです。Agent Skills を読み込めるアシスタントであれば、Claude（Web、デスクトップ、モバイル、Claude Code）、Codex、ChatGPT のいずれでも変更なしで動作するように書かれています。パッケージは指示文のみ（Markdown、YAML、JSON）で構成されているため、ツールのないチャットでもすべてのスキルが動作します。スキルファイルは英語で書かれていますが、各スキルはあなたのメッセージと同じ言語で応答します。スマートフォンでは `dia` とだけ入力してください。メニュー用のスキル（`dia-menu`、1.4.0 で追加）がスキルの一覧を表示し、番号、名前の先頭の文字、または依頼の内容でスキルを 1 つ選んで起動します。

| スキル | 内容 | 起動方法 |
|---|---|---|
| `dia-confirm` | 作業開始前に、目標を言い直し、重要な前提を開示し、あなたが下すべき判断だけを挙げたうえで、承認を待ちます。 | 名前指定のみ |
| `dia-elenchus` | プラトンのエレンコス（論駁）：「X とは何か」を問い、前提を一問ずつ合意し、矛盾を示します。修正するたびに、それがあなたの新しい考えになります。たいていアポリアで終わり、助言はしません。 | 名前指定、またはソクラテス式の対話を依頼 |
| `dia-brainstorm` | 現代的なソクラテス式の問いかけを一問ずつ行い、その後あなたの選択肢に最大 3 つのラベル付き選択肢を加え、基準によって絞り込み、結論と概要（ブリーフ）を示します。実装は一切しません。 | 名前指定、またはソクラテス式ブレインストーミングを依頼 |
| `dia-reductio` | 厳密な背理法（帰謬法）を 1 回の応答で行います：ラベル付きの前提、各行に規則を明記した Q と not-Q の導出、強度の評価、選択肢、記録。 | 名前指定、または言葉で依頼 |
| `dia-negative` | 内部批判（アドルノの内在的批判より範囲を絞ったもの）を 1 回の応答で行います：対象自身の基準、事例と「取りこぼされるもの」を伴う厳密なずれ、反証条件付きの実際の目的、そして統合を強いない選択肢。 | 名前指定、または言葉で依頼 |
| `dia-warrant` | トゥールミンの論証モデルとウォルトンの批判的問いを 1 回の応答で行います：データ、論拠（語られていない論拠は補ってラベルを付ける）、裏づけ、限定語、反駁を整理し、各問いにどの部分を試すかの印を付け、最も弱い環を示します。主張が正しいかどうかは判定しません。 | 名前指定、または言葉で依頼 |
| `dia-conjecture` | ラカトシュの「証明と論駁」を、あなたが掲げる「すべて／いつも／決して」の主張に対話形式で適用します：あなたの論証をステップに分け、1 メッセージに 1 つずつ反例を検証付きで示し、各事例をあなたが判定して修正方法を選びます。 | 名前指定、または言葉で依頼 |
| `dia-counterplan` | メイソンの弁証法的探究を計画や決定に適用します：鍵となる前提、それぞれのもっともらしい反対の前提、同じ事実にもとづく対抗計画を示し、いまどの前提を採るかをあなたが答えます。勝者は決めません。 | 名前指定、または言葉で依頼 |
| `dia-refine` | 直前の回答または草稿に対して 1 回のレビューを行います：事実誤り、論理の飛躍、要件の漏れ、重複。確認された欠陥だけを修正します。 | 最初の語を `dia-refine` にする、または名前指定 |
| `dia-iterate` | 外部検証を関門とするレビューのラウンドを繰り返します。後退（リグレッション）、欠陥ゼロ、検証手段の枯渇、不動点、または `--max N`（既定値 3）で停止します。 | 最初の語を `dia-iterate` にする、または名前指定のみ |
| `dia-menu` | 手法ではなく、短い入り口です。`dia` で番号付きのメニューを表示し、`dia 4 …` や `dia red …` で番号や先頭の文字からスキルを起動し、`dia <request>` では合うスキルを選んで、どれを選んだかを伝えます。`dia-confirm` や `dia-iterate` を自分から起動することはありません。 | 最初の語を `dia` にする |

## インストール

**どこでインストールするかで、dia が表示される場所が変わります。** Web（claude.ai、chatgpt.com）でインストールするとアカウントに保存され、Web 版とモバイルアプリに表示されます。デスクトップアプリ（Claude デスクトップ、ChatGPT デスクトップアプリの Codex）でインストールすると、そのコンピューターにだけ残ります。どこでも使うには、Web で 1 回、使うデスクトップアプリごとに 1 回インストールしてください。作者もこの方法で使っています。

### claude.ai Web 版と Claude デスクトップ

1. Settings › Capabilities で **Code execution and file creation** をオンにします。dia のスキルはコードを実行しませんが、スキル機能そのものにこの設定が必要です。
2. **マーケットプレイスを追加。** Customize › Plugins › Add › Add marketplace を開き、次を入力します：

   ```
   ajitta/dialectic-skills
   ```

   Git URL `https://github.com/ajitta/dialectic-skills.git` でもよく、Claude デスクトップではローカルフォルダー（このリポジトリのクローン）も指定できます。手入力せずにコピーして貼り付けてください。`dialectric` のような綴り間違いは「Repository not found」で失敗します。
3. **プラグインを追加。** マーケットプレイスを追加しただけでは、まだ何もインストールされません。Customize › Plugins で Discover を開き、`dia`（Dialectic Skills）を選んで Add を押します。
4. **確認。** メッセージ欄に `/dia` と入力します。`dia:dia-brainstorm` から `dia:dia-warrant` までの 11 項目（10 個のスキルと `dia:dia-menu`）が表示されるはずです。更新はマーケットプレイス経由で届きます（Check for updates、または Sync automatically）。

手順 2 と 3 の代わりに、プラグインをアップロードすることもできます。Customize › Plugins › Add › Upload plugin で最新リリースの [`dialectic-skills.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills.zip) をアップロードします。Customize › Skills ではなく Customize › Plugins を使ってください。Skills 画面はプラグインマニフェストを含む zip を受け付けません。アップロードしたものは自動では更新されないため、新しいリリースのたびにアップロードし直してください。

**Claude デスクトップ：** 同じ Customize › Plugins 画面でも、そのコンピューターにだけインストールされます。作者の確認では、Claude デスクトップで追加したプラグインはモバイルアプリに表示されず、claude.ai で追加したプラグインは Claude デスクトップに表示されませんでした。両方を使う場合は、それぞれにインストールしてください。

### Claude モバイル（iOS、Android）

インストール作業は不要です。claude.ai（Web）で追加したプラグインはアカウントに保存され、モバイルアプリに自動で届きます。Claude デスクトップで追加したものは届きません。モバイルの `/` メニューにはプラグインのスキルが表示されません。いちばん手短なのは、メッセージを `dia` で始める方法です（「呼び出し方」を参照）。名前を最後まで入力してもよく（例：`/dia-brainstorm`、または `dia-brainstorm` で始まるメッセージ）、言葉で頼むこともできます。

### Claude Code

```
/plugin marketplace add ajitta/dialectic-skills
/plugin install dia@dialectic-skills
```

- 更新：`/plugin marketplace update dialectic-skills` を実行してから、プラグインを更新します（またはマーケットプレイスの自動更新をオンにします）。
- アンインストール：`/plugin uninstall dia@dialectic-skills`。
- claude.ai で追加したプラグインは、同じアカウントでサインインすると Claude Code にも同期されます。コマンドラインから重ねてインストールしないでください。
- カタログ経由でインストールする場合：`/plugin marketplace add ajitta/claude-plugins` を実行してから `/plugin install dia@ajitta`。コードは同じで、インストール名だけが異なります。

### Codex CLI と IDE

```
codex plugin marketplace add ajitta/dialectic-skills
codex plugin add dia@dialectic-skills
```

- 更新：`codex plugin marketplace upgrade` でマーケットプレイスを更新し、`codex plugin list` でインストール済みのバージョンを確認できます。
- プラグインを使わない場合：`skills/dia-<x>/` フォルダーを `~/.agents/skills/` にコピーします。この方法でコピーしたスキルの名前は、`$dia:dia-<x>` ではなく `$dia-<x>` になります。

### ChatGPT デスクトップ（Codex を含む）とモバイル

方法は 2 つあります。Web 版とモバイルには 1 つ目、デスクトップアプリには 2 つ目を使ってください。作者は両方を使っています：

1. **Web で zip をアップロード（Web 版とモバイル）：** 最新リリースから [`dialectic-skills-openai.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills-openai.zip) をダウンロードし、chatgpt.com のプラグイン zip アップロードで追加します。プラグインはアカウントに保存されるため、ChatGPT の Web 版とモバイル版に表示されます。この zip には ChatGPT 用の掲載情報（説明、スタータープロンプト、ロゴ）が入っています。アップロードしたものは自動では更新されないため、新しいリリースのたびにアップロードし直してください。
2. **デスクトップアプリでマーケットプレイスを追加（このコンピューターのみ）：** Codex は ChatGPT デスクトップアプリに含まれています。GitHub リポジトリ（`ajitta/dialectic-skills`）、Git URL（`https://github.com/ajitta/dialectic-skills.git`）、ローカルフォルダー（このリポジトリのクローン）のいずれかでマーケットプレイスを追加し、そのプラグイン一覧で `dia` を選んでインストールします。デスクトップアプリのローカルな Codex フォルダーにインストールされるだけでアカウントには保存されないため、モバイル版や Web 版には表示されません。更新はマーケットプレイス経由で届きます。

Business と Enterprise のワークスペースでは、管理者がワークスペース全体にプラグインを追加することもできます（zip のアップロード、または GitHub マーケットプレイスのインポート）。

### Windows

上記の経路はすべて Windows でも使えます。スキルにはスクリプトが含まれていないため、Python やシェルの準備は不要です。

## 呼び出し方

方法は 4 つあり、どの環境でも少なくとも 1 つは使えます：

1. **メニュー：メッセージを `dia` で始める。** `dia` だけなら、スキルが番号付きで一覧表示されます。`dia 4 <your text>` や `dia red <your text>` は、そのスキル（ここでは `dia-reductio`）を起動します。先頭の文字が 2 つのスキルに当てはまる場合（`con`）は、どちらかを尋ねます。`dia <your text>` は合うスキルを選び、たいていはまず 1 行でその名前を示してから実行します。2 つが同じくらい合う場合は尋ねます。通常の依頼から `dia-confirm`（1）や `dia-iterate`（10）を起動することは決してないので、番号か名前を使ってください（例：`dia 10 --max 2 <draft>`）。スマートフォンではこれが最も手早い方法です：3 文字で、ハイフンもいりません。
2. **言葉で依頼する。** 手法を指定して頼みます：「〜を背理法で検証して」「〜を内在的批判して」「ソクラテス式の対話をお願いします」「この理由は結論をどのくらい支えている？」「私のルールの反例を探して」「この計画にあえて反対の立場で」。すべての環境で使え、モバイルではこれが無難な既定の方法です。`dia-reductio`、`dia-negative`、`dia-elenchus`、`dia-brainstorm`、`dia-warrant`、`dia-conjecture`、`dia-counterplan` で使えます。
3. **メッセージ内で名前を指定する。** メッセージをスキル名で始めます：`dia-confirm …`、`dia-refine …`、`dia-iterate …`。1.2.0 以降は Codex では `$` なしで、ChatGPT では `@` なしで（モバイルアプリでオーナー確認済み）この方法が使えます。`dia-refine` と `dia-iterate` は、この方法か明示的な選択で起動することを想定しています。`dia-iterate` は通常の依頼からは決して起動せず、Claude Code では「この草稿を直して」のような通常の依頼で `dia-refine` が読み込まれることはまれです。
4. **明示的に選択する。** 書き方は環境ごとに異なります：

| 環境 | 構文 | 例 |
|---|---|---|
| claude.ai、Claude デスクトップ、Claude Code | `/dia:dia-<x>` | `/dia:dia-reductio` |
| Claude モバイル | `/dia-<x>` または `/dia:dia-<x>` を最後まで入力（`/` メニューには表示されない） | `/dia-brainstorm`、`/dia:dia-brainstorm` |
| Codex（プラグイン） | `$dia:dia-<x>` の後にスペース | `$dia:dia-confirm バックアップスクリプトを書いて` |
| Codex（コピーしたフォルダー） | `$dia-<x>` | `$dia-refine` |
| ChatGPT | `@` を入力してスキルを選ぶ | `@dia-negative` |

1.2.0 以降、Codex と ChatGPT でも Claude と同じく、すべてのスキルがモデルから見えます。`dia-reductio`、`dia-negative`、`dia-elenchus`、`dia-brainstorm`、`dia-warrant`、`dia-conjecture`、`dia-counterplan`、`dia-refine` は依頼内容が合致すれば自動で起動することがあり、`dia-confirm` と `dia-iterate` はメッセージを名前で始めたときか、明示的に選択したとき（`$dia:dia-<x>`、`@`）にだけ起動する設計です。ただし Codex では、「まず目標を整理して、決めるべきことを挙げて」のように `dia-confirm` の手順をそのまま言葉で頼むと、このスキルが読み込まれることもあります。

### オプション

オプションはフラグでも普通の言葉でも、どの言語でも指定できます：

- `--target=user|claude|text|all`（`dia-reductio`、`dia-negative`、`dia-warrant`）：検討する対象です。`user` はあなたが述べた主張、`claude` はアシスタント自身の直前の回答（どのアシスタントでも同じ）、`text` は貼り付けたテキスト、`all` はそのうち存在するものすべてです。フラグがない場合は、スキルが対象を推定し、最初の行で明示します。
- `--target=user|claude|text`（`dia-counterplan`）：誰の計画を検討するかです。`claude` は、アシスタント自身の以前の提案をあなたが指したときだけ使います。
- `--mode=audit|ask`（`dia-warrant`）：`audit`（既定）はチェック全体を一度に示し、`ask` は各部分をあなた自身に埋めてもらうため、1 メッセージに 1 問ずつ尋ねます。
- `--max N`（`dia-iterate`）：ラウンドの上限で、既定値は 3 です。
- モードと深さ（`dia-brainstorm`）：`develop`（既定）または `stress`（「穴を探す」）、および `quick`、`standard`（既定）、`deep`。
- 基準（`dia-refine`、`dia-iterate`）：名前の後に書いた内容が基準になります。例：`dia-refine — 数値を確認して`、`dia-refine 文体を重視して`。

## スキルガイドと例

これらのスキルを使うのに、哲学の予備知識はまったく必要ありません。どれも昔から人々が使ってきた考え方で、それをアシスタントが一歩ずつたどる手順にしたものです。以下では、スキルごとにやさしい言葉での説明、試せるプロンプト、そして実際のセッション（短く省略したもの）を紹介します。

セッションはこのプラグインを入れた Claude Code（Sonnet）で実行したもので、対話例でのユーザーの返答は、台本ではなく、シミュレートしたユーザーによるものです。セッションは英語で行い、ここでは日本語に訳して載せています。実際に返ってくる言い回しは、実行のたびに変わります。どのプロンプトもどの言語でも使え、アシスタントはあなたが書いた言語で返答します。

**やりたいことからスキルを選ぶ**

| やりたいこと | 使うスキル |
|---|---|
| 作業を始める前に、アシスタントがタスクを正しく理解したか確かめたい | `dia-confirm` |
| ある言葉や考えで、自分が本当は何を言いたいのかを見極めたい | `dia-elenchus` |
| ざっくりしたアイデアを、選択肢と計画にまとめたい | `dia-brainstorm` |
| ある主張に筋が通っているか確かめたい | `dia-reductio` |
| スローガンや方針、約束が、その言葉どおりになっているか確かめたい | `dia-negative` |
| 結論を支える理由が、実際にどのくらい支えになっているか見たい | `dia-warrant` |
| 自分の「いつも」「決して」のルールを、反例で試したい | `dia-conjecture` |
| 決める前に、別の計画をいちばん強く推す意見を聞きたい | `dia-counterplan` |
| 回答や草稿の誤りを、1 回で直したい | `dia-refine` |
| 何かをラウンドごとに、徹底的にファクトチェックしたい | `dia-iterate` |
| どれを使えばいいか迷う、またはスマートフォンで入力したい | `dia` (`dia-menu`) |

### dia-confirm：作業開始前にタスクを合意する

**かんたんに言うと。** 腕のいい職人は、工事を始める前に仕事の中身を説明してくれます。「これを作ります」「こういう前提で考えています」「ここはあなたにしか決められません」。`dia-confirm` はアシスタントにそれをさせ、推測で進めずに、あなたのゴーサインを待たせます。

**使いどころは**、依頼は短いけれど、結果があなたしか知らないことに左右されるときです。スピーチ、計画、スクリプト、大切な相手へのメールなど。**不要なのは**、答えが 1 つに決まっている簡単な質問です。

**試してみましょう：**

```
dia-confirm 弟の結婚式で読む短いスピーチを書いてください。
```

**セッションの様子**（短縮版）：

> **アシスタント:**
> **目標と成功条件：** 弟さんについての短い結婚式スピーチ。そのまま読み上げられる形で、1〜2 分ほど、温かい雰囲気で、乾杯の言葉を入れます。
> **根拠と前提：** 弟さんや新郎新婦についての情報は、まだ何もありません。弟さんが新郎で、軽いユーモアを交えた温かいトーン、英語で書く、という前提で考えています。
> **ユーザーが決めるべき事項：** 1. お名前、2. 実際のエピソードを 1〜2 個（一緒の思い出など）、3. トーン、4. 避けたい話題。これがないと、空欄入りの汎用的なスピーチを書くしかありません。
> **確認：** 回答とあわせて「進めて」と返信するか、汎用テンプレートを使うよう指示してください。
>
> **あなた:** 弟はミンホで、サラと結婚します。私はベストマン（新郎付添人）です。弟なのに、私に自転車の乗り方を教えてくれたのは彼でした。温かい感じで、軽いジョークを 1 つ、3 分くらいで。進めて
>
> **アシスタント:** スピーチができました。400 語ほどです…… *（自転車のエピソードを軸にしたスピーチが続きます）* ……注：エピソードの細かい部分は私が創作しました。実際と違うところは書き換えてください。

**ヒント**

- 気になる質問にだけ答えて、「進めて」と添えれば十分です。修正に「進めて」を添えると、修正後のタスクを承認したことになります。
- 「よさそう」、無言、親指を立てた絵文字などは承認とはみなされず、アシスタントは待ち続けます。
- 対象になるのは、そのタスクとその直接の続きだけです。別のタスクでも同じ確認をしたいときは、もう一度 `dia-confirm` で始めてください。

### dia-elenchus：自分が本当に言いたいことを見極める

**かんたんに言うと。** プラトンの対話篇で、ソクラテスが使っている方法です。あなたが、あるものについて「こういうものだと思う」と言います（「良い先生とは……」）。アシスタントは反論もしなければ、自分の意見も言いません。具体的な場面を 1 つずつ尋ねていきます。その場面は、あなた自身の答えが、あなたの定義と食い違い始めるように選ばれています。そこであなたは、自分の言葉で定義を直します。最後は行き詰まることが多く、これをギリシア語で **アポリア** と言います。ここでは、行き詰まるのは失敗ではなく、ひとつの成果です。自分がどこを分かっていないのかがはっきりするので、間違った前提の上に物事を積み上げずにすみます。

**使いどころは**、当たり前に思えるのに、実際の判断を左右している言葉に頼っているときです。良い先生、公平な分け方、成功したプロジェクト、健全な関係など。**向かないのは**、助言がほしいときです。対話の間、助言は一切しません。

**試してみましょう：**

```
ソクラテス式の対話をお願いします。良い先生とは、生徒がテストで高得点を取る先生だと思います。
```

**セッションの様子**（実際の実行例、短縮版）：

> **アシスタント:** 私には良い先生が何なのか分からないので、あなたの定義を試させてください。ある先生が、前日に試験問題と答えを生徒に渡し、全員が高得点を取ったとします。これは良い先生でしょうか？
>
> **あなた:** いいえ、それはほとんどカンニングです。良い先生とは、生徒が *本当に内容を身につけたからこそ* 高得点を取る先生、かもしれません。
>
> **アシスタント:** あなたの言い方が、「テストで高得点」から「本当に内容を身につけたから高得点」へと変わりましたね。では、生徒は本当に身につけたのに、テストの出来が悪かったせいで点数が低くなった先生はどうでしょう。良い先生ですか？
>
> **あなた:** はい、悪いのはテストのほうです。ということは、先生の良し悪しを決めるのは、点数ではないんですね。
>
> **アシスタント:** …… 生徒全員がすべてを身につけたけれど、それは本と家庭教師だけで自力で学んだからで、先生は何も貢献していないクラスを考えてみてください。これは良い先生でしょうか？
>
> **あなた:** いいえ。だとすると、良い先生とは、その教え方が実際に生徒の学びを助けている先生です。
>
> *……さらに 3 つの場面：生徒が授業をさぼる先生、同じくらい分かりやすいのに受け持つクラスが違う 2 人の先生、あらゆる手を尽くしても何もうまくいかない先生……*
>
> **アシスタント:** 先ほどあなたは、生徒がさぼる先生も良い先生だと言いました。その生徒たちは「無理なく参加できる状態」にありましたか？
>
> **あなた:** 参加はできたけれど、しないことを選んだだけです。だから私の新しい考えでは、その先生は良い先生ではありません。でもそれは、前に言ったことと矛盾します。行き詰まりました。これって、どういうことになるんでしょう？
>
> **アシスタント:** あなたはアポリアにたどり着きました。これは失敗ではなく、ひとつの成果です。良い先生を決めるのは、生徒が最終的に何を学んだかなのか、それとも先生が何をするかなのか。それはあなたにとって、まだ答えの出ていない問いです…… *（続いて記録：定義がどう変わったか、あなたが同意した前提、分かっていないと分かったこと、持ち帰る問い。結果：アポリア）*

**ヒント**

- 短く正直な答えが、いちばんうまくいきます。「よく分かりません」も立派な答えです。
- 言い方が「変わった」と指摘されても、それは言葉がどう変わったかを見せているだけです。何を残すかは、あなたが決めます。
- いつでも「やめて」と言えば記録が出ます。そのあと提案がほしければ、頼んでください。アシスタントはソクラテス式の部分が終わったことを告げ、自分のアイデアにはアシスタント自身のものだとラベルを付けます。

### dia-brainstorm：ざっくりしたアイデアを育ててから決める

**かんたんに言うと。** 選択肢を渡す前に、まず良い質問をしてくれるコーチのようなものです。最初に 1 問ずつ質問して、あなたが何を望み、何を知っているのかをはっきりさせます（ソクラテス式の問いかけ）。次にあなたが選択肢を挙げ、アシスタントがいくつか自分の案を足し、あなたが何を重視するかを選びます。最後は結論と、そのまま行動に移せる短い概要（ブリーフ）で締めくくります。`dia-elenchus` と違い、質問のあとで提案もします。

**使いどころは**、目標はあるけれど、計画がまだないときです。副収入、キャリアの転機、小さなプロジェクト、旅行など。**向かないのは**、実際に作ることです。コードを書いたり、行動に移したりすることは決してありません。

**試してみましょう：**

```
ソクラテス式のブレインストーミングに付き合ってください。手短にお願いします。週末に少し副収入を得たいです。
```

**セッションの様子**（実際の実行例、短縮版）：

> **アシスタント:** クイックモードで、質問は 4 つほどです。あなたのアイデアは、今の仕事を続けながら、週末に少し副収入を得ること、ですね。合っていますか？ それとも、あなたが意図していないことを、私が勝手に想定していますか？
>
> **あなた:** 合っています。週末ごとに 8 時間くらい、月に 300 ドルほど。始めるのにかけるのは 200 ドルまでです。
>
> **アシスタント:** 週末 8 時間なら月に約 32 時間なので、300 ドルは時給にして約 9 ドルです。あなたがすでにできることで、誰かがお金を払ってくれそうなことは何ですか？
>
> **あなた:** 写真が得意で、そこそこ良いカメラを持っています。地元の小さなお店向けの写真とかでしょうか。
>
> **アシスタント:** 褒められるのは良い兆しですが、まだ誰からもお金をもらっていないので、いちばん分からないのは、お店が本当に…… これから数回の週末で、お店に声をかけていくとします。何が見えたら「これはうまくいっていない」と判断しますか？
>
> **あなた:** 3 週末で 10 店ほどに売り込んで、安いお試し撮影ですら 1 件も OK が出なければ、うまくいっていないと判断します。
>
> *……あなたが選択肢を追加（週末マーケットでのプリント販売、ストックフォト、プロフィール写真、「ペット撮影の朝」）。アシスタントも自分の案を追加（結婚式のセカンドカメラマン、初心者向けの写真散歩、何もしない）。あなたは基準を 3 つ選びます：初期費用が低いこと、無給の編集作業をあまり増やさずに約 300 ドル稼げること、楽しんでできること……*
>
> **アシスタント:** **結論：未決。** 試した範囲ではアイデアは持ちこたえましたが、中心となる前提、つまり誰かがあなたの写真にお金を払うかどうかは、まだ試されていません…… **次の一歩：** 今週、近所のグループ 2 か所に投稿して公園での撮影枠を 3〜4 つ募集し、予約数、支払われた金額、1 人あたりの編集時間（分）を記録してください。

**ヒント**

- どのくらい踏み込むかを伝えてください：「手短に」「じっくり」、もっと厳しく試すなら「穴を探して」。
- いつでも「まとめて」と言えば、結論と概要に進みます。
- 結論が「未決」なのは、カギとなる前提がまだ現実で試されていないという意味で、それがどの前提かは概要に書かれています。

### dia-reductio：主張に筋が通っているか確かめる

**かんたんに言うと。** 背理法（帰謬法）とは、ある主張を言葉どおりに受け取って一歩ずつたどり、両方が同時には成り立たない 2 つの文に行き着くかどうかを見る方法です。行き着いたなら、出発点のどこかを手放さなければなりません。アシスタントは使った前提をすべて挙げ、そのうち自分で補ったものに印を付け、何を手放すかはあなたに任せます。

**使いどころは**、「いつも」「絶対に」「誰もが」といった言葉が入った、自信たっぷりのルールを耳にしたとき。あるいは、自分の立場を人前で主張する前に、試しておきたいときです。**向かないのは**、アイデアが全体として賢明かどうかの判断です。調べるのは、つじつまが合っているかどうかだけです。

**試してみましょう：**

```
この主張を背理法で検証してください：お客様は常に正しい。
```

**得られる結果**（実際の実行例、短縮版）：

> **検証した読み方：** 「正しい」とは真であること、つまり客の言うことは何でも正しい、という読み方。
> **前提：** P1 [A] 「正しい」は「真である」という意味。P2 [A] 同じコートについて、客 C1 は「この店で買った」と言い、客 C2 は「この店で買ったのではない」と言う。P3 [L] not-p が真なら、p は真ではない。
> **導出：** 1. すべての客の主張は真である（主張そのもの）。…… 4. p は真である。…… 6. p は真ではない。
> **矛盾：** 4 行目と 6 行目。**強度：** 補った前提 P1 と P2 に依存しています。これらは論理ではなく、ごく普通の事実です。
> **選択肢：** 「常に」を手放す、「正しい」に別の意味を与える、客同士の言い分が食い違うことなどないと考える、あるいは主張を修正する：「客が誠意をもって申し立てた苦情は、公平に聞いてもらう価値があり、店にできる範囲で対応を受けるべきだ。」
> **推奨：** 修正した主張。スローガンが本来目指しているものを保てるからです。決めるのはあなたです。

ラベルの意味は次のとおりです：**[T]** は主張自身が述べていること、**[L]** は論理の規則、**[A]** はアシスタントが補ったもの。[A] の前提がないと成り立たない矛盾は、その前提と同じ強さしかなく、アシスタントはそのこともはっきり伝えます。

**ヒント**

- アシスタント自身の直前の回答を試すには、「直前の回答を背理法で確認して」と書くか、`--target=claude` を付けます。
- [A] の前提が間違っていると思ったら、そう伝えてください。アシスタントはその前提を外して、論証をもう一度やり直します。選択肢の 1 つを選んだ場合も同じです。

### dia-negative：主張をそれ自身の基準で問う

**かんたんに言うと。** 主張をあなたの価値観で裁くのではなく、その主張自身の言葉で測ります。主張が約束していること（「誰でもいつでも問題を提起できる」）を取り出し、その約束が果たされていない実際の場面を探します。そのうえで、その主張が実際には何をしているのかを、確かめられる推測として問います。名前は哲学者アドルノの「否定弁証法」から来ていますが、このスキルが使うのは、彼の考えを実用向けに絞ったもので、内部批判と呼ばれます。

**使いどころは**、スローガン、方針、企業理念、計画などが、聞こえは良いけれど何が抜け落ちているのかを見たいときです。**向かないのは**、コードやコマンド、設定が何をするのかの説明や、一般的なレビューです。

**試してみましょう：**

```
この主張を内在的批判してください：「当社にはオープンドア・ポリシーがあるので、社内の誰でも、いつでも経営陣に問題を提起できます。」
```

**得られる結果**（実際の実行例、短縮版）：

> **主張自身の基準：** 「誰でも」（例外なし）、「いつでも」（時間の制限なし）、「経営陣に問題を提起できる」（経営陣まで届く）、そして「ので」（この方針だけで十分）。
> **F1. 「誰でも」は、経営陣についての問題では成り立たない。** あなたの問題が上司に関するものなら、開いたドアの先にいるのは苦情の相手その人で、方針は別の経路を示していません。*取りこぼされるもの：* 最も声に出されにくい問題。
> **F2. 「いつでも」は、実際の勤務時間の前では成り立たない。** 夜勤やリモートの従業員は、午前 3 時に上司 *に* 直接問題を伝えることはできません。
> **F3. 「ので」は言いすぎ。** 方針は許可を与えるだけです。人が実際に声を上げられるかどうかは、その後に何が起きるか、たとえば反応がないことや報復にも左右されます。
> **実際の働き（推論）：** 黙っていたことの責任を、ドアをくぐらなかった本人に押しつける。*これが誤りだと示すもの：* 経営陣についての苦情がこの方針を通じて提起され、対応された記録。
> **選択肢：** 主張の範囲を狭める、運用を変える（2 つ目の窓口、時間外の報告手段、報復をしないという約束）、そのまま維持して限界を正直に示す、撤回する、実際の 1 件で試す。**推奨：** 運用を変えること。決めるのはあなたです。

**ヒント**

- 「条件付き」と記された指摘は、あなたの状況についての事実に左右されるので、その事実をアシスタントに伝えてください。ある基準が実はその主張のものではないと伝えると、その基準を使った指摘を取り下げて、もう一度やり直します。
- 選択肢を推奨はしますが、あなたの代わりに選ぶことはしません。

### dia-warrant：理由が結論をどのくらい支えているか見る

**かんたんに言うと。** 日常の論証のほとんどは、何かを証明するのではなく、結論をもっともらしくするだけです。専門家がそう言った、あの人にはうまくいった、これがあれを引き起こす、といった具合です。`dia-warrant` は哲学者スティーヴン・トゥールミンにならって、そうした論証を部品に分けて並べます。**主張**、主張のよりどころとなる**データ**、データから主張へ渡るための一般的なルールである**論拠**（たいてい口に出されない部分）、そのルールの**裏づけ**、主張がどのくらい確かかを示す**限定語**、そしてルールが当てはまらない場合を示す**反駁**です。そのうえで、議論研究者ダグラス・ウォルトンがまとめた、その種類の論証に向ける標準的な**批判的問い**を投げかけ、各問いにどの部分を試すかの印を付けて、最も弱い環を示します。支えがいちばん薄い部品を、「最も弱い環：論拠」のように名前で示します。判断するのは支えの強さであって、主張が正しいかどうかではありません。

**使いどころは**、「なぜなら」がどれだけの重みに耐えられるかを知りたいときです。専門家の助言、他人の経験との比較、これから起きることの予測など。主張に「いつも」「すべて」「決して」が入っていて厳密な意味で言っているなら `dia-conjecture`、主張が自己矛盾していないかを知りたいなら `dia-reductio`、決めようとしている計画なら `dia-counterplan` を**代わりに使います**。

**試してみましょう：**

```
この理由は結論をどのくらい支えていますか？「友人はパーソナルトレーナーで、ランニングは膝をだめにすると言っています。だから私がランニングを始めたら、膝を痛めるでしょう。」
```

**得られる結果**（実際の実行例、短縮版）：

> **対象：** user（推定）。述べられたとおりの論証を点検します。
> **主張（C）：** 「私がランニングを始めたら、膝を痛めるでしょう。」明示されていて、限定語はありません（「でしょう（will）」）。
> **中間の主張（C1）：** 「ランニングは膝をだめにする。」友人の見解として明示されています。この論証は鎖になっています：データ → C1 → C。
> **読み方の固定：** 「だめにする」はあいまいです。「走る人の膝に長く残る損傷を起こす」と読みます。
> **データ（明示）：** 「友人はパーソナルトレーナーで、ランニングは膝をだめにすると言っています。」
> **Wa（再構成）：** パーソナルトレーナーがランニングの膝への影響について言うことは、おおむね信頼できる。データから C1 へのステップです。**Wb（再構成）：** ランニングがおおむね膝をだめにするなら、ランニングを始めた人はおおむね膝を痛める。C1 から C へのステップです。
> **裏づけ：** なし。**反駁：** なし。**型：** 最初のステップは**専門家の意見**です。2 つ目は**一般的なルールを事例に当てはめる**もので、一般的な問いで試しました。
> **批判的問い** *（8 問、すべて未解決）*：1. [データ] 彼女はこの主張が属する分野の本当の専門家か？ 示されている役割はパーソナルトレーナーです。それが関節の健康やけがまで含むかは、論証からはわかりません。**未解決。** …… 3. [論拠／裏づけ] 彼女の主張は証拠にもとづいているか？ 論証は何も挙げておらず、「彼女が言っている」だけです。**未解決。** …… 7. [反駁] たとえば走る量、これまでの経歴、その他の要因によって、あなたが例外になることはありうるか？ **未解決。** …… どの問いにも、私の持っている事実では答えていません。どれも、あなたか情報源からの答えが必要です。
> **限定語のチェック：** C は「でしょう」と言っています。Wa と Wb が許すのは「おおむね」、つまり「おそらく」までです。したがって主張は**言いすぎ**です。どちらの論拠も私の再構成で、言いすぎは「おおむね」という初期設定から来ています。「必ず」という意味だったなら、そう言ってください。……
> **結果：** **最も弱い環：論拠（Wa）。「彼女の主張は証拠にもとづいているか？」が未解決のままだからです。** すべてが「彼女が言っている」にかかっているので、これが重要です。彼女の主張に示された根拠がなければ、データは C をほとんど支えません。彼女の主張が何にもとづくのか、たとえば研究、顧客の結果、けがについての訓練がわかれば、この環は強くなります。…… *（続いて記録：対象と主張、モード、型、どちらも再構成の論拠、尋ねた問い 8 問のうち答えのあったもの 0、結果、限定語のチェック、環を強くするもの、再構成した論拠についての決定：保留）*
> この点検は、ランニングが膝のトラブルを起こすかどうかを決めるものではありません。示された理由がその主張をどれだけ支えているかを評価するだけです。
> ご自分の論証をステップごとに確かめたければ、ask モードに切り替えられます。

「明示」は論証そのものが述べていること、「再構成」はそのステップに必要なのでアシスタントが補ったものです。ここでは理由が中間の主張（C1、「ランニングは膝をだめにする」）を経由するので、ステップごとに別々の論拠（Wa、Wb）が付き、結果も弱い環がどのステップにあるかを示します。試す前に、あいまいな「だめにする」の読み方も 1 つに固定しています。角かっこの印は、各問いがどの部分を試すかを示します：**[データ]**、**[論拠／裏づけ]**、**[反駁]**、**[結論]**。結果は、データ、論拠、裏づけ、限定語、反駁、主張のうち 1 つの部品を示します。

**ヒント**

- 未解決の問いには次のメッセージで答えてください（「走っている顧客のほとんどが膝が痛いと言っているそうです」）。アシスタントはその問いをあなたが答えたものとして記し、結果を出し直します。
- 再構成された論拠に実はよっていないなら、そう伝えてください。その論拠は外され、アシスタントは実際にどのルールによっているのかを尋ねます。
- 自分の論証を点検すると、最後に ask モード（`--mode=ask`）を勧めてきます。アシスタントが 1 回に 1 つの部品を尋ね、あなたが埋めていくやり方です。最初から頼んでもよく、組み立て中の論証に向いています。
- 「尋ねた問いの範囲では弱い環は見つからなかった」は証明ではなく、弱い環があっても主張が誤りになるわけではありません。

### dia-conjecture：「いつも」のルールを反例で試す

**かんたんに言うと。** 「いつも」「すべて」「決して」が入ったルールは、当てはまらない事例 1 つで崩れることがあります。このスキルは、哲学者イムレ・ラカトシュが『証明と論駁』で描いた方法に従います。まず、あなたがそのルールを信じる理由を、番号付きのステップに分けます。次に 1 メッセージに 1 つずつ反例を持ってきて、その事例がルールの条件に当てはまりながらルールを破る様子を 1 行ずつ示し、その事例が何にもとづくかも書きます（例のために作った数字での計算であることが多いです）。各事例を反例と認めるかどうかは、あなたが決めます。認めた場合も、ルールを捨てる必要はありません。アシスタントは、壊れたステップを条件としてルールに組み込むといった修正方法を並べて 1 つを勧めますが、選ぶのはあなたです。そうしてルールは、いつ成り立つのかを正確に言えるようになります。

**使いどころは**、頼りにしている経験則を厳密な意味で言っているときです。「まとめ買いはいつも節約になる」「エクスプレスレジの列はいつも速い」「高いワインはいつもおいしい」など。「たいてい」という意味なら `dia-warrant`、計画や方針、決定なら `dia-counterplan`（穴を探すなら `dia-brainstorm`）、本当の問題が言葉の意味なら `dia-elenchus` を**代わりに使います**。

**試してみましょう：**

```
私のルールの反例を探してください：まとめ買いはいつも節約になる。
```

**セッションの様子**（実際の実行例、短縮版）：

> **アシスタント:** あなた自身の主張です。私の言葉で言うと、C は次のとおりです：まとめ買い（一度にふだんより多く買うこと）はどれもお金を節約する。ここで「お金を節約する」とは、まとめ買いしなかった場合より合計で少なく払うという意味です。なぜこれを信じているのですか？ 論証を書き出していなければ、番号付きのステップとして再構成できますが、そうすると私は自分で書いた証明を攻撃することになります。どちらがいいですか？
>
> **あなた:** はい、理由は言えます。大きいパックのほうが 1 個あたり安いし、どうせ買うものだから、結局払う額が少なくなるんです。よければステップに書き出してください。どれに賛成か言います。
>
> **アシスタント:** 論証を番号付きのステップにしました。L1 と L2 はあなたの言葉です。L3 から L5 は、論証に必要なので私が書きました。1. [T]「大きいパックのほうが 1 個あたり安い」 2. [T]「どうせ買うもの」 3. [A] 大きいパックの中身は全部使う。傷んだり、期限が切れたり、なくしたり、捨てたりするものはなく、たくさんあるからといって早く使うこともない。…… 4. [A] まとめ買いに伴う追加の費用はゼロか、1 個あたりの節約分に比べて小さい。会費、置き場所、前払いのお金、運ぶ手間がこれに入る。…… 5. [A] 1 個あたりが安いのはまとめ買いのパックそのもののおかげで、小さいパックのセールのせいではない。…… いちばん疑わしいのは L3 です…… L3 から L5 は私が書いて私が攻撃するので、ここでは私が両方の側に立っています。これはあなたの論証ですか？ 違う行は直し、どの行を受け入れるか教えてください。
>
> **あなた:** はい、それが私の論証です。1、2、4、5 には賛成で、3 は本当に使い切るものだけのつもりだったので、使い切る前に傷むものは節約に入らないと思います。
>
> **アシスタント:** これはルールの変更なので、古い言い方と新しい言い方を書きます。**古い C：** まとめ買いはどれもお金を節約する。**新しい C′：** 実際に使い切るもののまとめ買いは、どれもお金を節約する。**C′ がもうカバーしないもの：** 使い切る前に傷む、期限が切れる、しける、なくすもの全部。…… 事例を出す前に聞きます。何があれば、このルールに反する証拠と認めますか？ ……
>
> *……あなたは、全部使い切ったのに小さいパックより合計で多く払った場合、たとえば会費やそこまで行くガソリン代が 1 個あたりの節約分より大きい場合だと答えます……*
>
> **アシスタント:** 事例 1（両方：C′ と L4 への反例）：1 回きりの会員制倉庫店への買い出し。キッチンペーパー 40 ロールのパックを 1 つ買うためだけに、年会費 $60 で会員制の倉庫店に入るとします。このパックは近所の店より 1 ロールあたり $0.25 安く、40 ロール全部を使います。**A、使い切るもののまとめ買いか？** はい。40 ロールのパックで、1 ロール残らず使います。**B は崩れるか、お金は節約されるか？** はい、崩れます。1 ロールあたりの節約は 40 × $0.25 = $10 ですが、入会に $60 払いました。…… **L4 も崩れます。** …… これは私が作った数字での計算にもとづくので、証拠の種類は本物のレシートではなく論理です。この事例は、あなたのルールへの反例と認められますか？
>
> **あなた:** はい、それは認めます。…… まとめ買いが節約になるのは、会費みたいな追加の費用が節約する額より小さいときだけ、と言わないといけないですね。
>
> **アシスタント:** あなたの直し方は、追加の費用が節約する額より小さいときだけまとめ買いは節約になる、というものです。それは正しいのですが、修正としては働きません。「まとめ買いは節約になるときに節約になる」と言っているので、どんな買い物も反例になりえないからです。…… 1. **この買い物に伴う追加の費用がないこと。** C′ は次のようになります：使い切るもののまとめ買いのうち、この買い物のためだけに会費、わざわざの買い出し、置き場所の費用がかからないものは、どれもお金を節約する。…… 2. **会費とわざわざの買い出しだけ。** …… 3. **C′ を捨てる。** …… 1 をおすすめします。L4 が隠していた費用を全部名指しするので、例外を 1 つずつ足していくことにならないからです。どれを選びますか？
>
> **あなた:** 1 にします。会費だけじゃなく置き場所やわざわざの買い出しも含むし、そういうのも同じように節約分を食ってしまうので、1 つずつ継ぎはぎするより、追加の費用を最初から全部挙げておきたいです。
>
> **アシスタント:** 選ばれたとおりの今の主張 C′：…… 事例 2（両方：C′ と L1 への反例）：1 個あたりが高いまとめ買いパック。ある店で、ある銘柄の電池が 12 本パック $9（1 本 $0.75）、48 本パック $42（1 本 $0.875）で売られているとします。電池は 48 本必要で、全部使います。…… **B は崩れるか、お金は節約されるか？** はい、崩れます。48 本パックは $42、12 本パック 4 つなら 4 × $9 = $36 です。$6 多く払います。**L1 も崩れます。** …… この事例は、あなたのルールへの反例と認められますか？
>
> **あなた:** はい、それも認めます。…… まず 1 個あたりの値段を確かめないといけないですね。私のルールは、大きいパックが本当に 1 個あたり安いときにしか通用しないので。
>
> **アシスタント:** まず 1 個あたりの値段を確かめる、というのは修正になっていて、前回と違って買う前に確かめられる条件があります。3 つの形があります：…… 1 をおすすめします…… 1 つ注意があります：ここまで組み込むと、ルールはほとんど計算だけで正しくなります。…… 残るのは、発見というよりチェックリストに近いものです。どれを選びますか？

**ヒント**

- 事例がルールに当てはまらないと思ったら、その検証のどの行が間違っているかを言ってください。ただ「違う」と言うだけだと、その事例は「係争中」として残ります。取り下げられも、反例と数えられもしません。
- 修正方法は毎回あなたが選びます。すでに自分の言葉で言ったものでも同じです。上の実行例では直し方を 2 回自分で言っていますが、アシスタントはどちらのときも番号付きの選択肢を並べて 1 つを勧め、選ぶよう求めています。「まとめ買いは節約になるときに節約になる」になってしまう直し方は、修正として受け入れられません。どんな買い物もそのルールの反例になりえないからです。
- 各事例には、何にもとづくかが書かれます。「私が作った数字での計算」は、数字は作りもので、確かめたのは計算だけという意味です。実際の値段がそうなっているかは、あなたが判断します。
- 上の実行例の「本当に使い切るものだけのつもり」のようにルールの言葉を狭めるのは、定義の変更です。アシスタントは古い言い方と新しい言い方を書き、ルールが何をカバーしなくなったかを示します。事例を締め出すために「それは本当のまとめ買いじゃない」と言うのも同じ扱いです。
- 3 ラウンドたつと終えるかどうか尋ね、「まとめて」と言えばいつでも終わります。最良の結果は「試した事例に対しては持ちこたえている」で、「証明された」になることはありません。「未決」は、係争中の事例があるか、反例と認めた事例があるのに修正方法をまだ選んでいないという意味です。

### dia-counterplan：別の計画を推す意見を聞く

**かんたんに言うと。** 大きな決断の前には、反対の前提に立った別の計画を誰かに推してもらうと役に立ちます。これは経営学の研究から生まれた計画手法、弁証法的探究です（リチャード・メイソン、1969 年）。アシスタントは、あなたの計画がよって立つ前提を挙げ、間違っていたら決定が変わる前提だけを残し、それぞれにもっともらしい反対の前提を立てて、同じ事実のうえに最も強い対抗計画を組み立てます。反対の前提はアシスタントが選んだもので、そこに添えた理由（「……と仮定すると」）は、あなたの状況についての事実ではなく仮定です。そのうえで、いまどの前提を信じるかをあなたが答え、その組み合わせが結果になります。アシスタントはどの段階でも判定を下さず、両方の側を自分で書いたことを率直に伝えます。

**使いどころは**、ある計画に踏み切ろうとしているときです。引っ越し、転職の誘い、大きな買い物、チームの次の一手など。自分のアイデアについて 1 問ずつ質問されたい、あるいは穴を探してほしいなら `dia-brainstorm`、計画がそれ自身の約束を守っているかを見たいなら `dia-negative`、1 つの論証の理由がどのくらい確かかを試したいなら `dia-warrant` を**代わりに使います**。ある主張 1 つが正しいかどうかなら、そのまま尋ねれば十分です。

**試してみましょう：**

```
この計画にあえて反対の立場で意見を出してください：子どもたち（6 歳と 3 歳）が来年 9 月に学校に上がる前に、都心の 2 部屋のアパートから郊外の広い一軒家に引っ越したいと考えています。月々のローンの支払いは今の家賃とほぼ同じで、子どもたちはそれぞれ自分の部屋と庭を持てますし、そこの学校は評判がいいです。気になるのは、私の通勤が片道 20 分から 1 時間ほどに延びることです。
```

**セッションの様子**（実際の実行例、短縮版）：

> **アシスタント:** **対象：** `user`（あなたの計画）。判定はしません。両方の側を私が書いたので、結果はあなたが選ぶ前提の組み合わせになります。
> **計画：** 「子どもたち（6 歳と 3 歳）が来年 9 月に学校に上がる前に、都心の 2 部屋のアパートから郊外の広い一軒家に引っ越したい」。データはすべてあなたの提供で、このセッションで確かめたものはありません：**D1：** 月々の支払いは今の家賃とほぼ同じ。…… **D4：** 通勤が片道 20 分から 1 時間ほどに延びる。……
> **前提：** *（7 個。すべて [A] アシスタントが補ったものと印付き。たとえば）* **A1 [A]：** 「支払いがほぼ同じ」とは、住まいにかかる費用の合計がほぼ同じという意味である。引っ越しで費用が増えないためには、計画にこれが必要です。…… **A6 [A]：** 通勤時間は、たとえば在宅勤務の日を作るなどして短くすることはできない。……
> **鍵となる前提：** それぞれについて尋ねました：反対が正しかったら、決定は変わるか？ **K1 = A2：** はい。通勤が続けられないなら、計画のいちばん大きなコストが得るものを上回ります。**K2 = A1：** はい。費用の合計が高ければ、「家賃と同じ」はもう成り立ちません。…… *（全部で 5 つ：通勤、費用、学校、時期、広さ）*
> **反対の前提（私の選択。どれも仮定で、報告された事実ではない）：** **C1：** 通勤は続けられないとわかる。1 日 2 時間ほどが朝と夕方からあなたを引き離し、その時間は有効に使えない。…… **C2：** 実際の月々の費用は家賃を上回る。維持費、税金、保険、光熱費、増えるガソリン代や運賃、もしかすると 2 台目の車を仮定しています。数字：提供なし。…… **C5：** 6 歳と 3 歳には、それぞれの部屋と庭よりも、親と過ごす時間とそばにいることのほうが大事だ。今は相部屋と公園で十分だ。
> **対抗計画：当面は都心にとどまる。** 項目ごとに計画と同じ細かさで書き、各部分にそれがよって立つ反対の前提を記しました。**住まいと費用：** 今の家賃のまま 2 部屋のアパートに住む（C2、C4）。…… **学校：** 来年 9 月に 2 人を都心の学校に入れる（C3、C4）。学校名、評判、距離：提供なし。**通勤：** 20 分の通勤を保つ（C1）。**時期：** 決定を保留し、12 か月後に見直す。その日付は私の選択です。……
> **並べて比べる：** 1. **K1（片道 1 時間ほどの通勤は続けられる）対 C1（続けられない）。** 計画に有利なのは：ラッシュ時に 2 週間通勤してみても、あなたも家族も平気な場合。対抗計画に有利なのは：試してみて大事な日課を逃すとわかる、またはパートナーの負担がずっと重くなる場合。……
> 両方の側を 1 つのアシスタントが書いたので、対抗計画は本物の推進役が書くものより練られていないかもしれません。
> **あなたの総合：** K1〜K5 の各組について、いまどの前提を採りますか：計画のもの、対抗計画のもの、あなた自身の言葉、または「わからない」？
>
> **あなた:** K1：まだわかりません。在宅勤務はできないので、片道 1 時間は本当にかかります。でもラッシュ時にその道を運転してみたことがないので、どのくらいきついかはわかりません。K2：まだわかりません。固定資産税や維持費をまだ計算していないので、本当に家賃と同じなのかわかりません。今のところ対抗計画の心配はもっともだと思いますが、数字がありません。…… *（学校はわからない、時期は対抗計画のもの）* …… K5：だいたい計画のものです。子どもたちはほとんど毎晩、相部屋のことでけんかしているので、広さは今の本当の問題です。…… なので全体としては、まだ引っ越しに賛成とは言えません。まず実際の月々の費用を計算して、その道を運転してみる必要があります。それから決められます。
>
> **アシスタント:** 判定はそろいました。K1〜K3 がまだ未解決なので、結果は**未決**です。**記録** …… 1. **K1、通勤は続けられる（計画）対 C1：** 未解決。…… 在宅勤務についての説明が、私の A6 に代わって [T] になります。2. **K2、費用の合計 ≈ 家賃（計画）対 C2：** 未解決。対抗計画の心配はもっともだと考えていますが、固定資産税と維持費をまだ計算していません。傾き：対抗計画。判定ではなく傾きとして記録します。…… 4. **K4、引っ越しは 9 月より前でなければならない（計画）対 C4：** 対抗計画側をとる。…… 5. **K5、今それぞれの部屋と庭にそれだけの価値がある（計画）対 C5：** 計画側をとる、だいたい。…… **結果：** 未決。3 組が未解決で、1 組は対抗計画側、1 組は但し書き付きで計画側です。**採らなかった側のために残すもの：** …… **K5**（残す側：対抗計画）：庭の効果は確かめられておらず、通勤は子どもたちと過ごす時間を 1 日約 80 分奪う。**書き手：** この比較の両方の側を 1 つのアシスタントが書きました。**試していないこと：** …… この 2 つ以外の選択肢、たとえばもっと近い郊外、あるいは都心のもっと広いアパートや部屋数の多いアパート。…… 両方の言い分を聞いたことは、計画が試されたという証拠にはなりません。…… それがそろったら、その 3 組だけを新しい数字でやり直すか、頼まれればあなたの組み合わせにもとづく計画をざっと描きます。

**ヒント**

- 組ごとに答えます：計画の前提、対抗計画の前提、自分の言葉、または「わからない」。「わからない」でもかまいません。記録に、何が決め手になるかが書かれます。結果が「未決」（*テイク*、タルムードの「そのままにしておけ」）なら、少なくとも 1 組がまだ未解決だという意味です。
- 片方に傾いているだけなら、そう言ってください。その組は傾きを書き添えて未解決として記録され、その側をとると言ったときだけ、とったものとして数えられます。上の実行例でも、「今のところ対抗計画の心配はもっともだと思います」という答えで、費用の組は「傾き：対抗計画」と添えて未解決のまま残りました。
- 自分の状況について伝えた事実は、記録に入ります。上の実行例では、「在宅勤務はできない」が、アシスタントが補った前提 A6 に代わって、あなた自身の [T] の行になりました。計画がよって立つ新しいことを持ち出すと、反対の前提が付いた新しい組になります。
- 反対の前提を退けると、それはあなたの判定として記録されます。アシスタントは記録するだけで反論しません。書き直すのは、その前提があなたの事実を取り違えている、または別の反対の前提とぶつかっていると示されたときだけです。
- 「どちらの計画が勝ち？」と聞いても、探究の途中でも終わった後でも判定はしません。同じアシスタントが両方を書いたからです。代わりに、あなたがいちばん決めかねている組を決め手になる観察を示します。

### dia-refine：回答や草稿を 1 回、丁寧に見直す

**かんたんに言うと。** 注意深い編集者による、1 回きりの見直しです。アシスタントは問題点を挙げ、1 つずつ確かめ、確認できた誤りだけを直します。疑わしいけれど確認できなかった誤りは、ありそうな修正案とともに別に挙げるので、知らないうちに何かが変わることはありません。

**使いどころは**、草稿やアシスタントの直前の回答があって、事実の誤り、論理の穴、抜けている点を 1 回で直したいときです。メッセージを `dia-refine` で始め、重点を置いてほしい点があれば、続けて書きます。

**試してみましょう：**

```
dia-refine 事実を確認して：万里の長城は、月から肉眼で見える唯一の人工建造物であり、すべて明の時代に建てられた。
```

**得られる結果**（ウェブ検索ありの実際の実行例、短縮版）：

> **① 確認された誤り：** 「月から見える」は誤りです（検索で確認）。約 38 万 4,000 km 離れた場所からは、人工建造物はどれ 1 つとして見えず、宇宙飛行士も、宇宙から長城を肉眼では見られないと述べています。「すべて明の時代に建てられた」も誤りです。紀元前 220 年ごろの秦の時代に城壁がつなげられ、ほかの王朝も区間を付け加えました。
> **② 漏れている要件：** なし。
> **③ 維持した正しい内容：** 現在見られる石造りの長城の大部分は、明が築いたものです。
> **④ 残る不確実性：** 秦と漢の正確な年代は、資料によって異なります。確認したのは二次資料だけです。
> **修正版：** 万里の長城は月から肉眼では見えず、そもそも見える人工建造物は 1 つもありません。また、すべてが明の時代に建てられたわけではありません…… *（出典の一覧）*

**ヒント**

- 検索ツールがなくても、論理や計算は自分で導き直して直せます。確かめられない事実は ④ に入れます。
- 「このタスクを dia-refine のやり方でやって」と頼むと、回答を書いて 1 回見直し、最終版だけを示します。

### dia-iterate：ラウンドごとに確かめて直す

**かんたんに言うと。** `dia-refine` に似ていますが、ラウンドを重ねて進み、どの修正にも外部の根拠が必要です：検索、ツールの実行、あなたが提供した情報源。確認をパスした事実は固定され、後のラウンドで覆されることはありません。直すものがなくなったとき、それ以上検証できなくなったとき、またはラウンドの上限に達したときに、ループは自動で止まります。

**使いどころは**、スピードより正確さが大事なときです。たとえば、これから公開する事実や日付。メッセージを `dia-iterate` で始めてください。普通の依頼からは決して始まりません。

**試してみましょう：**

```
dia-iterate --max 2 この段落の日付と事実を確認して：「初代 iPhone は 2008 年に発売され、同じ日に App Store が 500 本のアプリとともにオープンした。」
```

**得られる結果**（ウェブ検索ありの実際の実行例、短縮版）：

> **変更点：** 「2008 年に発売され」→「2007 年」（2007 年 6 月 29 日発売）。「同じ日に App Store がオープンした」→「約 1 年後の 2008 年 7 月」。
> **ラウンドの要約：** ラウンド 1：ウェブ検索で 3 つの主張を確認し、2 つが誤り、1 つが正しいと判明。固定：iPhone の発売日、App Store の開始日、開始時のアプリ約 500 本。欠陥が残らなかったため停止し、ラウンド 2 は不要でした。
> **未検証：** 開始時の正確なアプリ数（資料により 500〜552 本）と、App Store のオープンが 2008 年 7 月 10 日か 11 日か。
> **修正後の段落：** 「初代 iPhone は 2007 年に発売され、App Store はその約 1 年後の 2008 年 7 月に、500 本のアプリとともにオープンした。」

**ヒント**

- `--max N` で、ラウンドの上限を設定します（既定値 3）。
- 検索もツールもないチャットでは、ラウンド 1 の後で止まり、推測する代わりに、検証できなかった項目を挙げます。

### dia-menu：短いひと言ですべてのスキルを呼ぶ

**かんたんに言うと。** それ自体は手法ではなく、早く入るための入り口にすぎません。メッセージを `dia` で始めてください。`dia` だけなら、10 個のスキルを番号付きで一覧表示します。後ろに番号か名前の最初の数文字を付けるとそのスキルが起動し、やりたいことをそのまま書けば合うスキルを選んで、たいていはまず 1 行でどれを選んだかを伝えます。先頭の文字が 2 つのスキルに当てはまるときや、2 つのスキルが依頼に同じくらい合うときは、推測せずに尋ねます。

**使いどころは**、スマートフォンで入力しているときや、どのスキルが必要かわからないときです。`dia-confirm`（1）と `dia-iterate`（10）は番号か名前でしか起動せず、`dia` が推測して起動することはありません。

**試してみましょう：**

```
dia
dia 4 すべての素数は奇数だと仮定して、どこで破綻するか示して。
dia オンボーディングメールを追加してから解約率が下がったので、メールが解約を減らした。私の理由はこれをどのくらい支えている？
```

**得られる結果**（Claude Code での実際の実行例、短縮版）：

> `dia` → 番号付きの一覧：「1. **dia-confirm**：作業開始前に、目標、前提、未決の判断を言い直す（名前か番号でのみ）。2. **dia-brainstorm**：…… 10. **dia-iterate**：外部の確認を関門とするレビューのラウンドを繰り返す（名前か番号でのみ）」、続いて選び方の説明。
> `dia 4 …` → `dia-reductio` がすぐに始まります：「**対象：** ユーザー（推定）。**命題 T：**『すべての素数は奇数である』。**方向：** 反駁。……」
> `dia オンボーディングメールを …` → `dia-warrant` が始まります：「**配置** – **主張：** 『メールが解約を減らした』（明示）。…… **データ：** 『オンボーディングメールを追加してから解約率が下がった』（明示）。……」
> `dia con …`（`dia-confirm` と `dia-conjecture` の両方に当てはまる。韓国語での実行例を翻訳）→「『con』で始まるスキルが 2 つあるため、1 つに決められません。番号で選んでください。」と、両方の一覧。

**ヒント**

- 番号は固定です：1 confirm、2 brainstorm、3 elenchus、4 reductio、5 negative、6 warrant、7 conjecture、8 counterplan、9 refine、10 iterate。
- オプションはそのまま渡されます：`dia 10 --max 2 <draft>` は `dia-iterate --max 2 <draft>` と同じです。
- `dia` は単独で最初の語にする必要があります。`dia-refine …` などの正式な名前は、これまでどおり直接そのスキルに届きます。
- 先頭の文字は 3 文字以上が必要です（`re` ではなく `red`）。明らかに文の一部である語（`dia red flags in my plan?`）は、選択ではなく依頼として読まれます。
- アシスタントが 2 つ目のスキルを開けない環境では、`dia` はメニューを表示し、送るべき正式な形（`dia-reductio …` など）を返します。このケースはまだ試していません。

## 複数のスキルを組み合わせる

- **`dia-elenchus` と `dia-brainstorm` を 1 つの依頼で：** 定義の対話が先に行われ、最初のメッセージでその旨が伝えられます。ブレインストーミングは、あなたが選択肢を求めたとき、または対話が終わったときに始まります。2 つが交互に行われることはありません。
- **`dia-refine` と `dia-iterate` を 1 つの依頼で：** 別々の 2 つのパスとして実行され、出力も別々です。refine パスでの再導出は、iterate のラウンドにおける検証とはみなされません。
- **`dia-reductio` と `dia-negative` を 1 つの依頼で：** 両方が実行され、どちらの回答も完全な形で出るため、出力は長くなります（テストでは約 9,000 文字）。スマートフォンでは 1 つずつ依頼してください。
- **`dia-warrant`、`dia-conjecture`、`dia-counterplan` は、まず受け取った依頼を確かめます。** 依頼が別のスキル向きなら、1 行でそう伝えてそのスキルを示します。`dia-conjecture` は「たいてい」の意味のルールを `dia-warrant` へ、計画を `dia-counterplan` か `dia-brainstorm` へ回します。`dia-warrant` は厳密な「いつも」の主張を `dia-conjecture` へ、計画の前提を `dia-counterplan` へ回します。`dia-counterplan` は、計画について質問してほしいという依頼を `dia-brainstorm` へ回します。示されたスキルで依頼し直してください。
- **`dia-elenchus` の後：** 続けて助言を求めると、アシスタントはソクラテス式の部分が終わったことを告げ、各提案にアシスタント自身のものであるとラベルを付けます。選択肢と計画まで含めた本格的なセッションには `dia-brainstorm` を指定すると、それまでの記録を引き継ぎます。

## トラブルシューティング

- **マーケットプレイスの追加時に `Repository not found` が出る。** 綴りを確認してください：`ajitta/dialectic-skills`（dialectric ではなく dialectic）。リポジトリは公開されており、GitHub へのログインは不要です。
- **Claude モバイルの `/` に dia のスキルが表示されない。** 想定どおりの動作です。モバイルのメニューにはプラグインのスキルが表示されません。メッセージを `dia` で始めるか、名前を最後まで入力する（例：`/dia-brainstorm`）か、言葉で依頼するか、メッセージをスキル名で始めてください。
- **ある端末では dia が使えるのに、別の端末では使えない。** デスクトップでのインストールはそのコンピューターにだけ残り、Web でのインストールはアカウントに保存されてモバイルアプリにも届きます。Web 版とモバイル用に Web で 1 回、使うデスクトップアプリごとに 1 回インストールしてください（インストールを参照）。
- **すべてのスキルが 2 つずつ表示される。** プラグインが 2 つの経路でインストールされています（たとえば `dia@dialectic-skills` と `dia@ajitta`、またはアップロードとマーケットプレイス）。どちらかを削除してください。
- **claude.ai で Skills セクションがない、またはグレー表示になっている。** Settings › Capabilities › Code execution and file creation をオンにしてください。
- **`dia-intent` が見つからない。** 1.1.0 で `dia-confirm` に名前が変わりました。
- **`dia-iterate` が起動しない。** `dia-iterate` がメッセージの最初の語である場合か、明示的に選択した場合（`/dia:dia-iterate`、`$dia:dia-iterate`、`@dia-iterate`、`dia 10`、`dia iterate`）にのみ起動します。`dia <request>` だけで選ばれることはありません。
- **Codex で `$dia:dia-confirm:` が解決されない。** スキル名の後にはコロンではなくスペースを入れてください。
- **claude.ai でアップロードが拒否される。** Customize › Skills ではなく、Customize › Plugins › Upload plugin を使ってください。
- **claude.ai で Check for updates 後も古いバージョンのまま。** Customize › Plugins で `dia` を削除し、`dialectic-skills` マーケットプレイスから再インストールしてください。以後のリリースを自動で受け取るには Sync automatically をオンにします。

どの経路をどのように検証したかは、[docs/probes.md](docs/probes.md) に記録されています。

## 開発

```bash
python tools/package.py            # validate, write plugins/dia/ and the zip
python tools/package.py --check    # validate; fail if the committed output lags the source
python -m unittest discover -s tests -v
claude plugin validate --strict plugins/dia
```

生成された出力ではなく、`skills/` を編集してください。スキルファイルを変更したら、`plugin-manifest.json` の `version`（およびそのスキルの `metadata.version`）を新しくする必要があります。Claude Code はバージョンが変わったときにしかインストール済みのプラグインを更新せず、そうでなければチェックが失敗します。配布パッケージ内では、ハングルは `skills/<skill>/references/ko/` 以下でのみ許可されます。この README を変更したときは、同じコミットで翻訳も更新してください。同じ構造が保たれているかをテストで確認しています。
