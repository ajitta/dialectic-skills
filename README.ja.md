# Dialectic Skills (`dia`)

[English](README.md) | [한국어](README.ko.md) | **日本語** | [简体中文](README.zh-CN.md)

ウェブサイト: [ajitta.github.io/dialectic-skills](https://ajitta.github.io/dialectic-skills/)

推論とレビューのための 13 個のスキルを 1 つのプラグインにまとめたものです。Agent Skills を読み込めるアシスタントであれば、Claude（Web、デスクトップ、モバイル、Claude Code）、Codex、ChatGPT のいずれでも変更なしで動作するように書かれています。パッケージは指示文のみ（Markdown、YAML、JSON）で構成されているため、ツールのないチャットでもすべてのスキルが動作します。スキルファイルは英語で書かれていますが、各スキルはあなたのメッセージと同じ言語で応答します。スキルが起動するのは、メッセージが `dia` かスキルの正式な名前で始まるとき、またはスキルを明示的に選択したときだけで、普通の言葉による依頼ではどのスキルも起動しません。スマートフォンでは `dia` とだけ入力してください。ルーター用のスキル（`dia-router`）がスキルの一覧を表示し、`dia` の後にスキルの名前を付けるとそのスキルが起動し、`dia` の後に依頼を書くと合うスキルを選びます。

| スキル | 内容 | 起動方法 |
|---|---|---|
| `dia-skopos` | 作業開始前に、頼まれたことをどう読んだかと、その仕事がどんな成果のためのものと考えるかを示し、あなたにしか決められないことだけを挙げ、頼まれたものを作るか、その成果のために動くかを尋ねます。そのうえで、あなたの返事を待ちます。 | `dia-skopos …` または `dia skopos …`。通常の `dia <request>` からは選ばれない |
| `dia-elenchus` | プラトンのエレンコス（論駁）：「X とは何か」を問い、前提を一問ずつ合意し、矛盾を示します。修正するたびに、それがあなたの新しい考えになります。たいていアポリアで終わり、助言はしません。 | `dia-elenchus …`、`dia elenchus …`、または `dia <request>` |
| `dia-quaestio` | 現代的なソクラテス式の問いかけを一問ずつ行い、その後あなたの選択肢に最大 3 つのラベル付き選択肢を加え、基準によって絞り込み、結論と概要（ブリーフ）を示します。実装は一切しません。 | `dia-quaestio …`、`dia quaestio …`、または `dia <request>` |
| `dia-reductio` | 背理法（帰謬法）：ある立場がよりどころにしているものをすべて挙げ、語られていない前提に印を付け、厳密な矛盾（ある文とそのちょうどの否定）を示し、そのうえで逃げ道を 1 つずつ試して、自分ならどれをとるかを示します。 | `dia-reductio …`、`dia reductio …`、または `dia <request>` |
| `dia-negative` | 内部批判（アドルノの内在的批判より範囲を絞ったもの）を 1 回の応答で行います：対象自身の基準、事例と「取りこぼされるもの」を伴う厳密なずれ、反証条件付きの実際の目的、そして統合を強いない選択肢。 | `dia-negative …`、`dia negative …`、または `dia <request>` |
| `dia-warrant` | トゥールミンの論拠：理由から結論への各ステップがよって立つ、たいてい語られないルールと、その種類のステップに向けられる問いを示し、問いには記憶ではなく証拠で答え、そのうえで結論にどこまで頼れるかを示します。支えが弱いことと誤りであることを区別します。 | `dia-warrant …`、`dia warrant …`、または `dia <request>` |
| `dia-conjecture` | ラカトシュの「証明と論駁」を「すべて／いつも／決して」の主張に適用します：論証を番号付きのステップにし、反例を検証付きで示し（あなた自身の資料を先に）、欠けていた条件を主張に組み込む修正をし、そのうえで「すべて」が成り立つかと、それに頼っていたものがどうなるかを示します。 | `dia-conjecture …`、`dia conjecture …`、または `dia <request>` |
| `dia-counterplan` | メイソンの弁証法的探究を計画や決定に適用します：鍵となる前提、それぞれのもっともらしい反対の前提とどちらが正しいかを示すもの、同じ事実にもとづく対抗計画を示し、そのうえでいまとる道と、何があればそれを変えるかを示します。両方の側を自分で書いたと明示します。 | `dia-counterplan …`、`dia counterplan …`、または `dia <request>` |
| `dia-emend` | 直前の回答または草稿に対して 1 回のレビューを行います：事実誤り、論理の飛躍、要件の漏れ、重複。確認された欠陥だけを修正します。 | `dia-emend …`、`dia emend …`、または `dia <request>` |
| `dia-ratchet` | レビューのラウンドを繰り返しますが、根拠として認めるのは外部の確認（検索、ツールの実行、あなたが提供した情報源）だけで、アシスタント自身の再導出は認めません。確認をパスした項目は固定します。後退（リグレッション）、欠陥ゼロ、検証手段の枯渇、不動点、または `--max N`（既定値 3）で停止します。 | `dia-ratchet …` または `dia ratchet …`。通常の `dia <request>` からは選ばれない |
| `dia-adjudicate` | 人や別のアシスタントがある文章について書いた報告（批判、レビュー、検証報告）を判定します。文章の主張と報告の各指摘を情報源と照らし合わせて項目ごとに判定し、判定の結果、文章の結論に何が残るかと、どの報告も挙げなかったことを示し、自分の判定が誤りうる箇所を挙げます。 | `dia-adjudicate …` または `dia adjudicate …`。通常の `dia <request>` からは選ばれない |
| `dia-regula` | モデルが読んで従う文章（スキルファイル、エージェントへのプロンプト、エージェント用指示ファイル）を 4 つのルールで点検し、または書きます：条件と代替を含む 1 つの式としての段落、意図どおりの狭さのスコープ語、それぞれ理由を添えたより少ない指示、1 つの対象に 1 つの名前。レビューだけを頼むと違反を挙げ、あなたが選ぶまで何も変えません。 | `dia-regula …`、`dia regula …`、または `dia <request>` |
| `dia-techne` | その分野の第一人者がするように、依頼をそれが目指す成果まで持っていきます。頼まれたものをそこへ至るほかのやり方と比べ、成果に必要なものを作り、アシスタント以外のものに確かめさせます。取り消せない手順の前では止まります。 | `dia-techne …` または `dia techne …`。通常の `dia <request>` からは選ばれない |
| `dia-router` | 手法ではなく、短い入り口です。`dia` でメニューを表示し、`dia reductio …` で名前からスキルを起動し、`dia <request>` では合うスキルを選んで、どれを選んだかを伝えます。通常の依頼から `dia-skopos`、`dia-ratchet`、`dia-adjudicate`、`dia-techne` を起動することはありません。 | 最初の語を `dia` にする |

## インストール

**どこでインストールするかで、dia が表示される場所が変わります。** Web（claude.ai、chatgpt.com）でインストールするとアカウントに保存され、Web 版とモバイルアプリに表示されます。デスクトップアプリ（Claude デスクトップ、ChatGPT デスクトップアプリの Codex）でインストールすると、そのコンピューターにだけ残ります。どこでも使うには、Web で 1 回、使うデスクトップアプリごとに 1 回インストールしてください。作者もこの方法で使っています。

### claude.ai Web 版と Claude デスクトップ

1. Settings › Capabilities で **Code execution and file creation** をオンにします。dia のスキルはコードを実行しませんが、スキル機能そのものにこの設定が必要です。
2. **マーケットプレイスを追加。** Customize › Plugins › Add › Add marketplace を開き、次を入力します：

   ```
   ajitta/dialectic-skills
   ```

   Git URL `https://github.com/ajitta/dialectic-skills.git` でもよく、Claude デスクトップではローカルフォルダー（このリポジトリのクローン）も指定できます。手入力せずにコピーして貼り付けてください。`dialectric` のような綴り間違いは「Repository not found」で失敗します。
3. **プラグインを追加。** マーケットプレイスを追加しただけでは、まだ何もインストールされません。Customize › Plugins で Discover を開き、`dia`（Dialectic Skills）を選んで Add を押します。
4. **確認。** メッセージ欄に `/dia` と入力します。`dia:dia-adjudicate` から `dia:dia-warrant` までの 14 項目（13 個のスキルと `dia:dia-router`）が表示されるはずです。更新はマーケットプレイス経由で届きます（Check for updates、または Sync automatically）。

手順 2 と 3 の代わりに、プラグインをアップロードすることもできます。Customize › Plugins › Add › Upload plugin で最新リリースの [`dialectic-skills.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills.zip) をアップロードします。Customize › Skills ではなく Customize › Plugins を使ってください。Skills 画面はプラグインマニフェストを含む zip を受け付けません。アップロードしたものは自動では更新されないため、新しいリリースのたびにアップロードし直してください。

**Claude デスクトップ：** 同じ Customize › Plugins 画面でも、そのコンピューターにだけインストールされます。作者の確認では、Claude デスクトップで追加したプラグインはモバイルアプリに表示されず、claude.ai で追加したプラグインは Claude デスクトップに表示されませんでした。両方を使う場合は、それぞれにインストールしてください。

### Claude モバイル（iOS、Android）

インストール作業は不要です。claude.ai（Web）で追加したプラグインはアカウントに保存され、モバイルアプリに自動で届きます。Claude デスクトップで追加したものは届きません。モバイルの `/` メニューにはプラグインのスキルが表示されません。いちばん手短なのは、メッセージを `dia` で始める方法です（「呼び出し方」を参照）。名前を最後まで入力しても起動します（例：`/dia-quaestio`、または `dia-quaestio` で始まるメッセージ）。

### ChatGPT デスクトップ（Codex を含む）とモバイル

方法は 2 つあります。Web 版とモバイルには 1 つ目、デスクトップアプリには 2 つ目を使ってください。作者は両方を使っています：

1. **Web で zip をアップロード（Web 版とモバイル）：** 最新リリースから [`dialectic-skills-openai.zip`](https://github.com/ajitta/dialectic-skills/releases/latest/download/dialectic-skills-openai.zip) をダウンロードし、chatgpt.com のプラグイン zip アップロードで追加します。プラグインはアカウントに保存されるため、ChatGPT の Web 版とモバイル版に表示されます。この zip には ChatGPT 用の掲載情報（説明、スタータープロンプト、ロゴ）が入っています。アップロードしたものは自動では更新されないため、新しいリリースのたびにアップロードし直してください。
2. **デスクトップアプリでマーケットプレイスを追加（このコンピューターのみ）：** Codex は ChatGPT デスクトップアプリに含まれています。GitHub リポジトリ（`ajitta/dialectic-skills`）、Git URL（`https://github.com/ajitta/dialectic-skills.git`）、ローカルフォルダー（このリポジトリのクローン）のいずれかでマーケットプレイスを追加し、そのプラグイン一覧で `dia` を選んでインストールします。デスクトップアプリのローカルな Codex フォルダーにインストールされるだけでアカウントには保存されないため、モバイル版や Web 版には表示されません。更新はマーケットプレイス経由で届きます。

Business と Enterprise のワークスペースでは、管理者がワークスペース全体にプラグインを追加することもできます（zip のアップロード、または GitHub マーケットプレイスのインポート）。

### Windows

上記の経路はすべて Windows でも使えます。スキルにはスクリプトが含まれていないため、Python やシェルの準備は不要です。

## 呼び出し方

方法は 3 つあり、どの環境でも少なくとも 1 つは使えます。このどれでも始まらないメッセージでは、スキルの手法を言葉で頼んでも（「〜を背理法で検証して」）dia のスキルは起動しません。1.x では、9 つのスキルがこうした依頼からも起動していました。

1. **ルーター：メッセージを `dia` で始める。** `dia` だけ（または `dia help`、`dia menu`、`dia ?`）なら、スキルが一覧表示されます。`dia reductio <your text>`（`dia dia-reductio …` も可）は、そのスキル（ここでは `dia-reductio`）を起動します。`dia <your text>` は説明が合うスキルを選び、1 行でどれかを伝えてから実行します。2 つが同じくらい合うときは尋ね、合うものがなければ dia スキルを使わずに答えます。通常の依頼から `dia-skopos`、`dia-ratchet`、`dia-adjudicate`、`dia-techne` を起動することはなく、送るべき形（たとえば `dia ratchet --max 2 <draft>`）を返します。スマートフォンではこれが最も手早い方法です：3 文字で、ハイフンもいりません。
2. **メッセージ内で名前を指定する。** メッセージをスキルの正式な名前で始めます：`dia-skopos …`、`dia-emend …`、`dia-ratchet …`、`dia-adjudicate …`、`dia-techne …` など、13 個すべて同じです。1.2.0 以降は Codex では `$` なしで、ChatGPT では `@` なしで（モバイルアプリでオーナー確認済み）この方法が使えます。
3. **明示的に選択する。** 書き方は環境ごとに異なります：

| 環境 | 構文 | 例 |
|---|---|---|
| claude.ai、Claude デスクトップ、Claude Code | `/dia:dia-<x>` | `/dia:dia-reductio` |
| Claude モバイル | `/dia-<x>` または `/dia:dia-<x>` を最後まで入力（`/` メニューには表示されない） | `/dia-quaestio`、`/dia:dia-quaestio` |
| Codex（プラグイン） | `$dia:dia-<x>` の後にスペース | `$dia:dia-skopos バックアップスクリプトを書いて` |
| Codex（コピーしたフォルダー） | `$dia-<x>` | `$dia-emend` |
| ChatGPT | `@` を入力してスキルを選ぶ | `@dia-negative` |

`dia` の後では、スキルの正式な名前（`dia-` は付けても付けなくてもよい）だけがスキルを選びます。短くした名前では選ばれません。文の一部として読める名前（`dia negative feedback on my draft?`）は依頼として読まれ、`dia` がそれに合うスキルを選びます。

### オプション

オプションはスキル名か `dia` の選択語の後に、フラグでも普通の言葉でも、どの言語でも指定できます：

- `--target=user|claude|text|all`（`dia-negative`）：検討する対象です。`user` はあなたが述べた主張、`claude` はアシスタント自身の直前の回答（どのアシスタントでも同じ）、`text` は貼り付けたテキスト、`all` はそのうち存在するものすべてです。フラグがない場合は、スキルが対象を推定し、最初の行で明示します。
- フラグなし（`dia-reductio`、`dia-warrant`、`dia-conjecture`、`dia-counterplan`）：どれも、何を対象としたかを最初の行で伝えます。アシスタント自身の直前の回答を検討させるには、言葉でそう頼みます（`dia reductio 直前の回答を確認して`）。
- 質問を受ける（`dia-warrant`）：質問してほしいと頼むと、各部分をあなた自身が 1 メッセージに 1 問ずつ埋めていき、最後にアシスタントが判断します。
- `--max N`（`dia-ratchet`）：ラウンドの上限で、既定値は 3 です。
- モードと深さ（`dia-quaestio`）：`develop`（既定）または `stress`（「穴を探す」）、および `quick`、`standard`（既定）、`deep`。
- 基準（`dia-emend`、`dia-ratchet`）：名前の後に書いた内容が基準になります。例：`dia-emend — 数値を確認して`、`dia-emend 文体を重視して`。

### 1 つの会話のあいだ守らせるルール

dia のスキルは 1 つの作業のために呼び出す方法で、会話全体にルールを設けるスキルはありません。そうしたルールが必要なときは、会話の最初に次のような文を貼り付けてください。この文は、確認を頼んだ回答がアシスタントの記憶に基づく場合に、そう明示させます。

```
この会話のあいだ：私が何かの確認やレビューを頼んだときだけ、回答が記憶に基づくならそう言い、記憶を「確認済み」と呼ばないでください。確認しなかったことも伝えてください。ついでに尋ねた一般的な事実には、こうした注記を付けないでください。
```

このルールが続くのはその会話のあいだだけなので、新しい会話ではもう一度貼り付けてください。

## スキルガイドと例

これらのスキルを使うのに、哲学の予備知識はまったく必要ありません。どれも昔から人々が使ってきた考え方で、それをアシスタントが一歩ずつたどる手順にしたものです。以下では、スキルごとにやさしい言葉での説明、試せるプロンプト、そして実際のセッション（短く省略したもの）を紹介します。

セッションはこのプラグインを入れた Claude Code で実行したもので、対話例でのユーザーの返答は、台本ではなく、シミュレートしたユーザーによるものです。各セッションの下の注記に、記録したバージョンとモデルを示しています。韓国語で行ったと記したもの以外のセッションは英語で行い、ここでは日本語に訳して載せています。実際に返ってくる言い回しは、実行のたびに変わります。どのプロンプトもどの言語でも使え、アシスタントはあなたが書いた言語で返答します。

**やりたいことからスキルを選ぶ**

| やりたいこと | 使うスキル |
|---|---|
| 作業を始める前に、アシスタントがタスクを正しく理解したか確かめたい | `dia-skopos` |
| ある言葉や考えで、自分が本当は何を言いたいのかを見極めたい | `dia-elenchus` |
| ざっくりしたアイデアを、選択肢と計画にまとめたい | `dia-quaestio` |
| ある主張に筋が通っているか確かめたい | `dia-reductio` |
| スローガンや方針、約束が、その言葉どおりになっているか確かめたい | `dia-negative` |
| 結論を支える理由が、実際にどのくらい支えになっているか見たい | `dia-warrant` |
| 「いつも」「決して」のルールを、反例で試したい | `dia-conjecture` |

### dia-skopos：作業開始前にタスクを合意する

**かんたんに言うと。** 腕のいい職人は、工事を始める前に仕事の中身を説明してくれます。「こう理解しました」「これは何のための仕事だと考えています」「ここはあなたにしか決められません」。`dia-skopos` はアシスタントにそれをさせたうえで、1 つだけ尋ねさせます。頼まれたものを作るか、それとも、あなたが求める成果のために動くか。推測で進めずに、あなたの返事を待ちます。

**使いどころは**、依頼は短いけれど、あなたが求めるものがその言葉より大きいときです。スピーチ、計画、テスト、大切な相手へのメールなど。**不要なのは**、答えが 1 つに決まっている簡単な質問です。

**試してみましょう：**

```
dia-skopos 弟の結婚式で読む短いスピーチを書いてください。
```

**セッションの様子**（短縮版）：

> **アシスタント:**
> **作るもの:** 2〜3分ほどでご自身が話せる乾杯のスピーチです。… 温かさと軽いユーモアを交え、自己紹介から始めて、弟さんについての個人的な話を一つ語り、パートナーを迎え入れ、乾杯で締めます。私の読みは、「短い」を話して3分未満とし、調子を織り交ぜることを加えています。お務めでない限り、正式な役割(ベストマン、司式者)は外しています。…
> **結果(私の読み):** 弟さんとパートナーが、あなたに本当に理解され祝福されていると感じ、会場が二人に温かい気持ちを寄せ、あなたは怖がらずに自信を持って立てることです。これを最も制限するのは、あなただけが持っている材料です。実際の名前、本当の話、そして人前で話すことにどれだけ慣れているかです。
> **あなただけが決められること**(私の既定値つき): 名前、話を一つか二つ、調子、あなたの役割と長さの上限、避けること。
> **選択。** **「頼まれたとおり」:** 今ある材料でできる限り磨いた短い結婚式のスピーチ。送信も支出もありません。**結果のために(提案):** 「弟の結婚式で、弟とパートナーが本当に祝福されていると感じ、私が自信を持って話せる乾杯のスピーチができるよう手伝ってください。」この場合、書いたスピーチはそこへ至る方法の一つになります。…
> 私の文が合わなければ、求める結果をご自身の言葉で教えてください。「進めて」とだけ言えば私の文で進め、「頼まれたとおり」と言えばスピーチだけを書きます。
>
> **あなた:** dia-techne お願いします。弟はミンホで、サラと結婚します。私はベストマン（新郎付添人）です。弟なのに、私に自転車の乗り方を教えてくれたのは彼でした。温かい感じで、軽いジョークを 1 つ、3 分くらいで。私が求めているのは、会場が一度笑って、ミンホが胸を打たれることです。
>
> **アシスタント:** **目指した結果(あなたのもの):** 会場が一度笑い、ミンホが胸を打たれること。以下のすべてをこの二つの瞬間で判断しました。… 全文の原稿と、要点だけのカードで話す方法を比べました。カードのほうが自然に聞こえることもありますが、ミンホの胸を打つはずの一文は言い回しが正確でなければ効かず、緊張するとぼやけがちです。そこで全文の原稿を書きました。… **笑い:** 弟が兄に教えるというのが、ご依頼どおり唯一の冗談です。… **胸を打つ瞬間:** 「ちゃんと持ってるよ」が最後に戻ってきて、今度は彼に返す言葉になります。… 会場が一度笑い、ミンホが胸を打たれるかどうかは、結婚式当日までわかりません。それまでは、上の声に出して読む確認が最良の点検です。
> *（4.2.0、Claude Opus 5.5 で記録した実行です。）*

**ヒント**

- **求めるものを、自分の言葉で 1 文にして伝えてください**（「私が求めているのは……」）。仕事はその 1 文のために行われ、これが結果を左右するいちばん大きな要因です。私たちの実行では、同じ依頼でも、ユーザーがこの 1 文を加えるとはっきりよい結果になりました。「進めて」とだけ返すとアシスタントの推測を採ることになり、依頼が精密なほど、その推測はあなたの求めるものより狭くなりがちです。
- 「頼まれたとおり」は名指ししたものにとどまり、それをその道の第一人者が作るように作ります。修正に「進めて」を添えると、修正後の依頼を承認したことになります。
- 「よさそう」、質問、無言は承認とはみなされず、アシスタントは待ち続け、タスクには一切手をつけません。
- ゴーサインを出すと、`dia-techne` がインストールされていれば仕事はそちらに引き継がれます。確実にするには、返信を `dia-techne` で始めてください。レビューの対象はそのタスク 1 つです。別のタスクでも同じ確認をしたいときは、もう一度 `dia-skopos` で始めてください。

### dia-elenchus：自分が本当に言いたいことを見極める

**かんたんに言うと。** プラトンの対話篇で、ソクラテスが使っている方法です。あなたが、あるものについて「こういうものだと思う」と言います（「良い先生とは……」）。アシスタントは反論もしなければ、自分の意見も言いません。具体的な場面を 1 つずつ尋ねていきます。その場面は、あなた自身の答えが、あなたの定義と食い違い始めるように選ばれています。そこであなたは、自分の言葉で定義を直します。最後は行き詰まることが多く、これをギリシア語で **アポリア** と言います。ここでは、行き詰まるのは失敗ではなく、ひとつの成果です。自分がどこを分かっていないのかがはっきりするので、間違った前提の上に物事を積み上げずにすみます。

**使いどころは**、当たり前に思えるのに、実際の判断を左右している言葉に頼っているときです。良い先生、公平な分け方、成功したプロジェクト、健全な関係など。**向かないのは**、助言がほしいときです。対話の間、助言は一切しません。

**試してみましょう：**

```
dia elenchus 良い先生とは、生徒がテストで高得点を取る先生だと思います。
```

**セッションの様子**（実際の実行例、短縮版）：

> **アシスタント:** 考えるのは **良い先生** です。あなたの言葉では、良い先生とは、生徒がテストで高得点を取る先生です。ある先生が、年度が始まる前からすでにトップの点数を取っていた生徒のクラスを受け持ったとします。その先生はほとんど何もせず、生徒は年度末にも同じように高得点を取ります。これは良い先生でしょうか？
>
> **あなた:** うーん、そうでもないですね。どうせ高得点だったでしょうから。点数がその先生のおかげで上がるかどうか、のほうが大事なんでしょうか？
>
> **アシスタント:** ① 良い先生とは、生徒がテストで高得点を取る先生である（定義） ② ほとんど何もせず、生徒がどうせ高得点を取っていたはずの先生は、良い先生ではない（合意）。したがって ① と ② は両立しません。あなたは ① を変えることを選びました。変化：「テストで高得点」→「点数がその先生のおかげで上がる」。…… ある先生が、テストの形式と解答のコツを繰り返し練習させて点数を上げたとします。テストの 1 か月後、生徒はほとんど何も覚えていません…… これは良い先生でしょうか？
>
> *……出来の悪いテスト、恐怖で教える先生、「点数はほとんど上がらなかったけれど、数学が好きになった」というユーザーの娘の数学の先生、どうせよくできたはずのクラス……*
>
> **あなた:** ざっくり言うと、良い先生とは、その教え方によって、その先生がいなかった場合よりも、生徒が本物の何かを学び、もっと続けたいと思うようになる先生です。でも、家庭教師がついている子について、それをどうやって見分けるのか正直わからないので、そこで行き詰まっていると思います。
>
> *……この定義は 1 つの検証には耐えますが、30 人中 3 人にしか届かない先生で崩れます。その修正「生徒の大半」は、ほかに頼る人のいない 3 人にだけ先生が届くクラスで崩れます……*
>
> **あなた:** いいえ、それは違います。その先生は良い先生です。その 3 人こそ、先生を必要としていた子たちです。だから「生徒の大半」もだめで、むしろ実際にその先生に頼っていた子たち、という感じです。それでまた行き詰まりました。
>
> **アシスタント:** …… 私たちは、良い先生が何なのかを知らないと分かったようです。それは失敗ではなく、成果です。どこがまだ言えないのかが分かったので、「テストで高得点」を、問題が片付いたかのように土台にすることはもうないでしょう。…… **結果：アポリア。あなたはもう良い先生の定義を 1 つも持っておらず、持ち帰る問いは、どの生徒にとっての違いが重要なのか、そしてそれはなぜか、です。** *（続いて記録：8 つの定義とそれぞれがどう崩れたか、合意した 10 の前提、生まれたアイデア、分かっていないと分かったこと、次の定義が果たすべきこと（たとえば「⑩ ほかの生徒には別の助けがあったときに、ほかに頼る人のいない 3 人に届く先生を含める」）、検討しなかったこと、確かめること、持ち帰る問い）*
> *（5.1.0 で、Claude Opus 5.5（effort medium）により記録。ユーザーはシミュレートしたものです。）*

**ヒント**

- 短く正直な答えが、いちばんうまくいきます。「よく分かりません」も立派な答えです。
- 言い方が「変わった」と指摘されても、それは言葉がどう変わったかを見せているだけです。何を残すかは、あなたが決めます。
- いつでも「やめて」と言えば記録が出ます。そのあと提案がほしければ、頼んでください。アシスタントはソクラテス式の部分が終わったことを告げ、自分のアイデアにはアシスタント自身のものだとラベルを付けます。

### dia-quaestio：ざっくりしたアイデアを育ててから決める

**かんたんに言うと。** 選択肢を渡す前に、まず良い質問をしてくれるコーチのようなものです。最初に 1 問ずつ質問して、あなたが何を望み、何を知っているのかをはっきりさせます（ソクラテス式の問いかけ）。次にあなたが選択肢を挙げ、アシスタントがいくつか自分の案を足し、あなたが何を重視するかを選びます。最後は結論と、そのまま行動に移せる短い概要（ブリーフ）で締めくくります。`dia-elenchus` と違い、質問のあとで提案もします。

**使いどころは**、目標はあるけれど、計画がまだないときです。副収入、キャリアの転機、小さなプロジェクト、旅行など。**向かないのは**、実際に作ることです。コードを書いたり、行動に移したりすることは決してありません。

**試してみましょう：**

```
dia quaestio 手短にお願いします。週末に少し副収入を得たいです。
```

**セッションの様子**（実際の実行例、短縮版）：

> **アシスタント:** 質問 4 つほどの短いセッションにします。…… あなたのアイデアは、こう理解しています：今していることと並行して、週末を使って副収入を得たい。…… いくら稼ぎたいか、どんな仕事か、そのお金を何に使うかは聞いていないので、そこは決めずにおきました。合っていますか？ それとも、あなたが意図していないことを、私が勝手に想定していますか？
>
> **あなた:** はい、合っています。平日はオフィスでフルタイムで働いています。お金は来年の夏の旅行用で、貯金に手をつけずに済ませたいんです。
>
> *……月に約 300 ドル、週末に約 8 時間、主に土曜日……*
>
> **アシスタント:** もう少しです。あと 2 つ質問します。あなたがすでにできることで、誰かがお金を払ってくれたこと、あるいはよく手伝いを頼まれることは何ですか？
>
> **あなた:** お金をもらったことはありませんが、写真が得意で、そこそこ良いカメラとレンズを 2 本持っています。友人はいつも私の写真を褒めてくれます。
>
> *……あなたが自分の選択肢（地元のお店向けの写真、週末マーケットでのプリント販売、公園でのペットのポートレート）、いちばん安い案、いちばん大胆な案、何もしない案、そして 2 つの制約（知らない人に対面で売らない、夜遅くまで編集しない）を挙げます。アシスタントは自分の案を 3 つ追加（イベントカメラマンのセカンドカメラマン、ストックフォトのライセンス販売、土曜日のシフト勤務）。あなたは基準を 3 つ選びます：初期費用 200 ドル未満、無給の編集作業をたくさん抱えずに約 300 ドル、楽しんでできること……*
>
> **アシスタント:** **結論：未決。** 上位 2 つ、地元のお店向けの写真とセカンドカメラマンのどちらを先に試すかを決める準備はできています。その前に 1 つ確かめてください：パン屋や花屋は本当に写真にお金を払うでしょうか？ …… **危うい前提：** パン屋と花屋が写真を欲しがり、あなたの作品を気に入るだけでなく、お金を払う。…… **このセッションで試していないこと：** 反例でアイデアを突き詰めることも、何があればやめるかを尋ねることもしていません。…… **次の一歩：** 次の土曜日、予定どおりパン屋か花屋に写真を何枚か無料で渡してください。渡すときに、こういう写真に毎月お金を払う気があるか、だいたいいくらかを聞いてください。
> *（5.1.0 で、Claude Opus 5.5（effort medium）により記録。ユーザーはシミュレートしたものです。）*

**ヒント**

- どのくらい踏み込むかを伝えてください：「手短に」「じっくり」、もっと厳しく試すなら「穴を探して」。
- いつでも「まとめて」と言えば、結論と概要に進みます。
- 結論が「未決」なのは、カギとなる前提がまだ現実で試されていないという意味で、それがどの前提かは概要に書かれています。

### dia-reductio：主張に筋が通っているか確かめる

**かんたんに言うと。** 背理法（帰謬法）とは、ある立場（主張、計画、ルールの集まり、論証）を言葉どおりに受け取り、それがよりどころにしなければならないものをすべて挙げて、それが全部同時に真でありうるかを見る方法です。アシスタントは、自分で補わなければならなかった前提に 1 つずつ印を付けます。立場に必要なのに誰も口にしていない前提こそ、見つかるもののなかでいちばん役に立つことが多いからです。矛盾として数えるのは厳密なものだけです。つまり、ある文とそのちょうどの否定で、論理、定義、または計算によって導かれ、ツールがあればツールで実行したものです。そのうえで、アシスタントは自分の判断を示します。逃げ道（ある約束を手放す、または立場をちょうど必要なだけ狭める）を 1 つずつ同じやり方で試し、それぞれが立場の目指すものに何を失わせるかを示して、自分ならどれをとるかを言います。修正した文言のように、そのもの自体が必要な場合は、それを書きます。

**使いどころは**、数字の入ったルールや約束、計画に頼ろうとしていて、それが全部同時に成り立ちうるかを知りたいときです。お知らせ、方針、「いつも」「絶対に」「誰もが」といった言葉が入った自信たっぷりのルール、あるいは人前で主張する前の自分の立場など。**向かないのは**、理由がもっともらしい結論をどのくらい強く支えるかの判断です。それは `dia-warrant` の仕事です。

**試してみましょう：**

```
dia reductio 12 月のカップ戦について、グループチャットに投稿する前に見てください。リーグ戦のときと同じく、11 月の練習に全部来た子は、どの試合でも少なくとも半分は出場する、と書いています。子どもは 16 人、フィールドには 8 人、20 分ハーフが 2 本なので、ちょうど収まるし、問題はないと思います。保護者は出場時間に敏感なので、このまま投稿していいか、どこを直すべきか教えてください。
```

**セッションの様子**（韓国語での実際の実行例を訳したもの、短縮版）：

> **アシスタント:** **検討の対象：** 説明していただいたとおりのお知らせ。本文はまだ見ていません。貼り付けてくだされば、言葉の 1 つ 1 つまで見ます。
> **このまま投稿するのはおすすめしません。** 「ちょうど収まる」とは、余裕が 0 分ということです。なので、約束が破れる道は 3 つあります：1. どれか 1 試合でもフィールドの人数が 8 人を下回った場合（退場、交代できないけが、試合の短縮）。2. 1 人のゴールキーパーが 40 分全部出ると、ほかの子の分が 20 分を下回る。3. カップ戦で試合ごとの登録メンバー数に上限があれば、メンバーから外れた子はその試合にまったく出られない。どの場合でも、**例外の条項を加える必要があります。** ……
> **お知らせが前提にしていること：** …… 使える出場時間：8 枠 × 40 分 = **320 分**（計算）。約束した出場時間：16 人 × 20 分 = **320 分**（計算）。私が補った前提 ①：16 人全員が 11 月の練習に全部来た。「ちょうど収まる」はこれを前提にしているようです。**確認が必要です。** 私が補った前提 ②：試合中にフィールドの人数が減ることがある。……
> **矛盾がどう生じるか：** 1. 16 人がそれぞれ 20 分以上出なければならないので、少なくとも 320 分が必要（約束 + ①）。2. 1 人が退場して 7 人で 10 分戦うと、実際に出場した時間は 310 分（② + 計算）。3. 320 分以上が必要なのに 310 分しかないので、約束は守れない。…… この矛盾は、① と ② の両方が正しいときにだけ成り立ちます。…… 計算は手で確かめました。ツールは使っていません。
> **すぐに加えられる文言：** 「ただし、退場、けが、試合の短縮などやむを得ない場合や、大会規定（登録メンバー、交代）により不可能な場合は例外とし、その場合は次の試合でできるかぎり埋め合わせます。」 ……

### dia-negative：主張をそれ自身の基準で問う

### dia-warrant：理由が結論をどのくらい支えているか見る

### dia-conjecture：「いつも」のルールを反例で試す

**かんたんに言うと。** すべての場合についての主張（「すべて」「いつも」「決して」「1 つも〜ない」）は、当てはまらない事例 1 つで崩れることがあります。このスキルは、哲学者イムレ・ラカトシュが『証明と論駁』で描いた方法に従います。主張がなぜ信じられているかをいくつかの番号付きのステップにし、自分で補ったステップに印を付けます。世の中についての主張なら、何があれば主張に反するかを前もって言います。次に、反例になりそうな事例を、まずあなた自身の資料（記録、ファイル、例）から持ってきて、条件ごとの検証と、その事例が何にもとづくかを添えます。事例が反例になるかどうかは、検証で決まるところではアシスタントが言います。反例になる事例は、言葉どおりの主張を崩します。修正は、その事例を例外として並べるのではなく、欠けていた条件を主張に組み込み（「……である A はすべて B だ」）、修正した主張をもう一度事例にかけます。そのうえで、「すべて」が成り立つか、代わりに何が言えるか、それに頼っていた決定がどうなるかを判断し、動くために必要なものを作ります。

**使いどころは**、あなた自身や、あなたがその言葉にもとづいて動こうとしている誰かが、あるルールに頼っていて、それを厳密な意味で言っているときです。「リマインダーを受け取った予約は 1 件もノーショーにならなかった」「まとめ買いはいつも節約になる」「エクスプレスレジの列はいつも速い」など。「たいてい」という意味なら `dia-warrant`、計画や方針、決定なら `dia-counterplan`（穴を探すなら `dia-quaestio`）、本当の問題が言葉の意味なら `dia-elenchus` を**代わりに使います**。

### dia-counterplan：別の計画を推す意見を聞く

**かんたんに言うと。** 大きな決断の前には、反対の前提に立った別の計画を推す意見を聞くと役に立ちます。これは経営学の研究から生まれた計画手法、弁証法的探究です（リチャード・メイソン、1969 年）。アシスタントは、あなたの計画が成り立つために必要なこと（そのほとんどは口に出されていません）を挙げ、決定を左右するいくつかだけを残します。反対が正しかったら、別の道が正しくなるか、という基準です。それぞれに、十分ありうる具体的な反対の前提を立て、組ごとに、どちらが正しいかを示すいちばん安上がりな観察を挙げます。そのうえで、あなたのデータとあなたの答えで決まることを決め（反対の前提のもとで計画自身の数字を計算し直します）、残った反対の前提が求める道を計画と同じ細かさで組み立て、自分ならいまどの道をとるか、何があれば考えを変えるかを言います。計画がそのまま残るのも、計画がひっくり返るのと同じくらい良い結果です。両方の側を自分で書いたことを率直に伝えるので、これはあなたの計画の独立した検証ではありません。

**使いどころは**、ある計画に踏み切ろうとしているときです。価格の変更、引っ越し、転職の誘い、大きな買い物、チームの次の一手など。自分のアイデアについて 1 問ずつ質問されたい、あるいは穴を探してほしいなら `dia-quaestio`、計画がそれ自身の約束を守っているかを見たいなら `dia-negative`、1 つの論証の理由がどのくらい確かかを試したいなら `dia-warrant` を**代わりに使います**。ある主張 1 つが正しいかどうかなら、そのまま尋ねれば十分です。

### dia-regula：モデルが従う文章を書く

**かんたんに言うと。** AI に渡す指示文の書き方を点検します。スキルファイル、エージェント向けのプロンプト、プロジェクトのエージェント用指示ファイル、ルールファイルが対象です。文章を 4 つのルールに照らします。段落ごとに求める結果を書き、その条件と代替を同じ文に入れて、条件が別の行に取り残されないようにします。範囲を決める語（「触る」「変える」など）は、意図した狭さにとどめます。指示はより少なくし、1 つずつに理由を添えます。1 つの対象には 1 つの名前だけを使います。レビューだけを頼むと、ルールに反する箇所を重い順に挙げ、あなたが選ぶまで何も変えません。

**試してみましょう：**

```

```

> 1. **編集の範囲がエージェント自身の判断に任されている**（ルール 2）。2 行目：`タスクに必要なファイルだけを触る。` タスクに何が「必要」かを決めるのはエージェントなので、この文はエージェントが自分の許可を自分で広げられるようにしています。…… 正確なパス（たとえば `docs/cli.md`）を挙げれば、エージェントが広げる余地はなくなります。

**得られる結果**（Claude Code での実際の実行例、短縮版。英語での実行を翻訳）：

> `dia` → メニュー（13 個のスキルの表）：「dia-skopos | 作業の前に：依頼をどう読んだかと、それが目指す結果を示し、どちらをするかはあなたが選ぶ」から「dia-techne | 一回限りの依頼をその分野の第一人者のように深めてから実行する」まで、続いて「`dia <name> <request>` でそのスキルを実行します。例：`dia reductio …`。」
> `dia reductio …` → `dia-reductio` がすぐに始まります：「**判断：**『すべての素数は奇数である』は偽です。それ自身の定義が、反例 **2** によってこれを反駁します。…… 4. よって 2 は奇数である。*(3, C1)* …… 6. よって 2 は奇数ではない。*(5, C3)* 7. ステップ 4 と 6 は『2 は奇数である』と『2 は奇数ではない』を述べています。これは厳密な矛盾です。…… **私なら A を選びます**［主張を 2 以外のすべての素数に狭める］。最小の変更で、上で証明されています……」
> `dia オンボーディングメールを …` → 「→ dia-warrant：この依頼は、示された理由が結論をどのくらい支えているかを尋ねています。」続いて：「あなたの理由が示しているのは、メールを始めた後に解約率が下がったということです。それでメールはもっともらしい原因になります。でも、メールが下落を引き起こしたことまでは、まだ示していません。…… 論証は 1 ステップだけで、しかも弱い種類のもの、つまり『後に起きたのだから、それが原因だ』です。…… おそらく、もともと比較対象があります：開始の直前に登録した顧客は、メールを一度も受け取っていません。……」
> *（5.1.0 で、Claude Opus 5.5（effort medium）により記録。）*

**ヒント**

- スキルは正式な名前で選びます。`dia-` は付けても付けなくてもかまいません（`dia reductio …`、`dia dia-reductio …`）。短くした名前では選べません。
- オプションはそのまま渡されます：`dia ratchet --max 2 <draft>` は `dia-ratchet --max 2 <draft>` と同じです。
- `dia` は単独で最初の語にする必要があります。`dia-emend …` などの正式な名前は、直接そのスキルに届きます。
- 明らかに文の一部である名前（`dia negative feedback on my draft?`）は選択ではなく、全体が依頼として読まれます。
- アシスタントが 2 つ目のスキルを開けない環境では、`dia` はメニューを表示し、送るべき正式な形（`dia-reductio …` など）を返します。このケースはまだ試していません。

## 複数のスキルを組み合わせる

- **`dia-elenchus` と `dia-quaestio` を 1 つの依頼で：** 定義の対話が先に行われ、最初のメッセージでその旨が伝えられます。ブレインストーミングは、あなたが選択肢を求めたとき、または対話が終わったときに始まります。2 つが交互に行われることはありません。
- **`dia-emend` と `dia-ratchet` を 1 つの依頼で：** 別々の 2 つのパスとして実行され、出力も別々です。emend パスでの再導出は、ratchet のラウンドにおける検証とはみなされません。
- **`dia-reductio` と `dia-negative` を 1 つの依頼で：** 両方が実行されるため、出力は長くなります。スマートフォンでは 1 つずつ依頼してください。
- **`dia-warrant`、`dia-conjecture`、`dia-counterplan` は、まず受け取った依頼を確かめます。** 依頼が別の手法の仕事なら、1 行でそう伝えます。`dia-warrant` は厳密な矛盾や、すべての場合についての主張への反例のとき、`dia-conjecture` は「たいてい」「ほとんど」として言われたルールのとき、`dia-counterplan` は行動の道を含まない、ある主張 1 つが正しいかどうかの問いのときです。その 1 行が使うべきスキルを示すとは限りません。合うスキル（上の表を参照）でメッセージを始めて、依頼し直してください。
- **`dia-elenchus` の後：** 続けて助言を求めると、アシスタントはソクラテス式の部分が終わったことを告げ、各提案にアシスタント自身のものであるとラベルを付けます。選択肢と計画まで含めた本格的なセッションには メッセージを `dia-quaestio` で始めると、それまでの記録を引き継ぎます。
- **複数のスキルをレビュー役として使う：** サブエージェントを起動できるアシスタントで一つのテキストに複数のスキルを使うときは、サブエージェントごとにスキルを一つ割り当てます。計画や推奨には `dia-counterplan`、自ら掲げる規則や基準に照らして見るテキストには `dia-negative`、論証には `dia-warrant`、テキストの整合性には `dia-reductio` を使います。各スキルは中心となる主張を一つ検討するので、どの主張かが重要なら指定してください。メッセージはスキル名とテキストで始め、結果全体を質問なしで一回の応答で求めてください（このとき `dia-counterplan` は今あるものにもとづいて判断します。資料で決着しない組はそれぞれ、何が決め手になるかを添えて未解決のまま残り、対抗計画は省かずに示されます）。出力の形式はできるだけスキルに任せてください。ワークフローのスクリプトや別のエージェントが形式を決めている場合、この四つのスキルは 2.11.0 から結果をその形式に合わせて入れます。指摘は項目として出して証明は根拠の欄に入れ、形式に場所のない内容は方法の結果と記した最後の項目に入れ（`dia-counterplan` は組が欠陥ではないので、出力全体を一つの項目に入れます）、方法が出さない値（重大度など）を形式が強制する場合は、項目にそう書きます。最後の項目も含めてすべての項目を渡してください。Claude Code のテストで決まった指摘の形式を指定したとき、渡される項目に方法の結果が残っていたのは 2.10.0 で 4 回中 0 回、2.11.0 で 7 回中 7 回でした（spec D68）。報告は `dia-adjudicate` に二回、毎回、二回のうちの一回だと伝えた別のエージェントで渡し（そうすれば自分で二回目の実行を始めません）、判定が分かれた項目を確認し直してください。対抗計画の組は判定の対象ではなく、決める人が選ぶものです。テストでは、`dia-adjudicate` はテキストにある、別のセッションのツールの説明についての主張を、自分のセッションで見たものから判定しました。別のセッション、バージョン、実行モード（たとえば `claude -p`）についての主張の判定は、自分で確認し直してください。別のアシスタント（Codex、ChatGPT）で書いた報告も同じように貼り付けられます。Claude Code では、同じマーケットプレイスの補助プラグイン `dia-panel` がこのレビュー役を一つのワークフローで実行します。`claude plugin install dia-panel@dialectic-skills` でインストールし、`Run /dia-panel:review-panel on <ファイル>` のように頼むと、スキルごとに別のエージェントを起動し、`dia-adjudicate` を報告の順序を変えて二回実行し、判定が分かれた項目を自分で確認できるように一覧にします。報告がすでにある場合は、`Run /dia-panel:judge on <ファイル> with the reports <報告ファイル>` のように頼むと、`dia-adjudicate` の二回の実行と、判定が分かれた項目の一覧だけを行います。
- **エージェントに dia スキルを使わせる：** サブエージェントやレビュー役に渡すプロンプトにスキル名を書き、1 回の応答で返すよう頼みます。例：`Use the dia-negative skill (dia:dia-negative) on design.md and give the whole result in one response, with no questions.`「独立したレビュー役に dia スキルで design.md を確認させて」のような依頼でもかまいません。先頭に `dia` を付けても付けなくても、アシスタントがレビュー役ごとにスキルを一つ割り当て、名前で起動させます。ツール一覧に Skill ツールがないエージェント（Claude Code ではエージェントの `tools` に `Skill` を加えるか、`skills` にスキルを挙げて事前に読み込ませます）や、プラグインが入っていない環境で動くエージェントは、スキルを使えません。

## トラブルシューティング

- **マーケットプレイスの追加時に `Repository not found` が出る。** 綴りを確認してください：`ajitta/dialectic-skills`（dialectric ではなく dialectic）。リポジトリは公開されており、GitHub へのログインは不要です。
- **Claude モバイルの `/` に dia のスキルが表示されない。** 想定どおりの動作です。モバイルのメニューにはプラグインのスキルが表示されません。メッセージを `dia` かスキルの正式な名前で始めるか、選択の形を最後まで入力してください（例：`/dia-quaestio`）。
- **スキルが起動しなかった。** 2.0.0 以降、普通の言葉による依頼ではどの dia スキルも起動しません。メッセージを `dia`（`dia <request>`、またはスキルを決めて `dia reductio …` のような `dia <name> <request>`）か、スキルの正式な名前（`dia-reductio …`）で始めてください。メッセージをスキルの名前で始めたのに起動しなかった場合は、アシスタントがその名前を文の一部として読んだ可能性があります（韓国語で名前の直後に「フォルダー」にあたる語が来ると、名前がそのフォルダーの名前として読まれ、スキルは起動しません。ほかの名詞ではそうなりませんでした）。名前の後で改行するか、明示的な選択を使ってください。
- **ある端末では dia が使えるのに、別の端末では使えない。** デスクトップでのインストールはそのコンピューターにだけ残り、Web でのインストールはアカウントに保存されてモバイルアプリにも届きます。Web 版とモバイル用に Web で 1 回、使うデスクトップアプリごとに 1 回インストールしてください（インストールを参照）。
- **すべてのスキルが 2 つずつ表示される。** プラグインが 2 つの経路でインストールされています（たとえば `dia@dialectic-skills` と `dia@ajitta`、またはアップロードとマーケットプレイス）。どちらかを削除してください。
- **claude.ai で Skills セクションがない、またはグレー表示になっている。** Settings › Capabilities › Code execution and file creation をオンにしてください。
- **`dia-ratchet`、`dia-adjudicate`、`dia-techne` が起動しない。** スキル名がメッセージの最初の語である場合か、明示的に選択した場合（`/dia:dia-ratchet`、`$dia:dia-ratchet`、`@dia-ratchet`、`dia ratchet`。`dia-adjudicate` と `dia-techne` も同じ形式と `dia adjudicate`、`dia techne`）にのみ起動します。`dia <request>` だけで選ばれることはなく、送るべき形が返されます。
- **Codex で `$dia:dia-skopos:` が解決されない。** スキル名の後にはコロンではなくスペースを入れてください。
- **claude.ai でアップロードが拒否される。** Customize › Skills ではなく、Customize › Plugins › Upload plugin を使ってください。
- **claude.ai で Check for updates 後も古いバージョンのまま。** Customize › Plugins で `dia` を削除し、`dialectic-skills` マーケットプレイスから再インストールしてください。以後のリリースを自動で受け取るには Sync automatically をオンにします。

どの経路をどのように検証したかは、[docs/probes.md](docs/probes.md) に記録されています。

## 開発

```bash
python tools/package.py            # validate, write plugins/dia/ and the zip
python tools/package.py --check    # validate; fail if the committed output lags the source
python -m unittest discover -s tests -v
claude plugin validate --strict plugins/dia
```

生成された出力ではなく、`skills/` を編集してください。スキルファイルを変更したら、`plugin-manifest.json` の `version`（およびそのスキルの `metadata.version`）を新しくする必要があります。Claude Code はバージョンが変わったときにしかインストール済みのプラグインを更新せず、そうでなければチェックが失敗します。配布パッケージ内では、ハングルは `skills/<skill>/references/ko/` 以下でのみ許可されます。この README を変更したときは、同じコミットで翻訳も更新してください。同じ構造が保たれているかをテストで確認しています。
